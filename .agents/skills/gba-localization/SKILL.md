# GBA localization (ledger-based, game-agnostic)

This skill generalizes the workflow the project's first two games (`golden-sun-the-broken-seal`, `golden-sun-the-lost-age`) proved out, minus their Golden-Sun-specific mechanics (Huffman decoding, `{HH}` control markers, shared codepage). Use it for every *other* GBA game.

## Scope: what this skill does not cover

`games/golden-sun-the-broken-seal/` and `games/golden-sun-the-lost-age/` are explicitly out of scope. Both are grandfathered out of the ledger scheme (their `translations/*.draft.jsonl` files still embed source text directly, by project-owner decision recorded 2026-08-15 — see `docs/TRANSLATION-LEDGER.md` "既有例外" and the `GRANDFATHERED_SOURCE_TEXT_PATHS` comment in `scripts/check-repository-safety.rb`) and are under active, separate translation work. Use the `golden-sun-localization` skill for those two games instead. Do not port this skill's ledger flow onto them, and do not treat their existing format as a bug to fix — that cleanup is a deliberately separate, deferred decision for the project owner to make.

## Why the ledger split exists

A `translations/*.jsonl` file that embeds the original game script (`source.text`) and gets pushed to a public repo is a verbatim reproduction of copyrighted text — a much larger legal exposure than distributing a BPS patch (which requires the user's own ROM to mean anything). `docs/TRANSLATION-LEDGER.md` is the authoritative spec for why and how; read it before starting any translation batch for a new game. The short version: original text only ever lives in files under `.gitignore`'s `research/` and `work/` patterns, on the contributor's own machine, regenerated from their own legally-dumped ROM. Nothing that reaches Git carries source text — only a `source_hash` for drift detection.

## Establish scope

1. Read the workspace `AGENTS.md`, `docs/PROJECT_CHARTER.md`, `docs/PIPELINE.md`, `docs/TRANSLATION-LEDGER.md`, and the target game's own `README.md`/`ROADMAP.md` (create them, matching the style of the two existing games' docs, if this is a brand-new game workspace under `games/<game>/`).
2. Inspect `git status --short`. Preserve unrelated and user-owned changes.
3. Treat ROMs, extracted/decoded text, rendered glyph images, OCR output, and build artifacts as local research data. `roms/` and `work/` are fully gitignored (`**/roms/`, `**/work/`), but `research/` is **not** blanket-ignored — only specific shapes inside it are (`*-decoded.jsonl`, `*-text-ids.tsv`, `*.pgm`/`.ppm`/`.png`, `vendor/`, `ocr-samples/`; see `.gitignore`). Committed analysis prose belongs in `research/` too (e.g. `games/golden-sun-the-lost-age/research/baseline-20260814.md` is tracked on purpose) — check each new file with `git check-ignore -v <path>` before assuming it's protected, and never assume a raw scan dump or decoded-text file is safe just because it lives under `research/`.
4. Keep game-specific revisions, offsets, pointers, hashes, compression format, and terminology in the game's own `games/<game>/` documentation and tools, not in this skill or in `core/`.

Before writing a game-specific ROM fingerprint helper, use the shared identity
gate. It implements the GBA header complement once, emits only safe metadata,
and rejects misspelled expectations instead of silently dropping a check:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 scripts/gba-rom-identity.py GAME.gba \
  --expect-size BYTES --expect-game-code CODE --expect-crc32 CRC32 \
  --expect-sha256 SHA256 --output /private/tmp/GAME-identity.json
```

Keep the reviewed expected values in the game's documentation or manifest;
keep the ROM path local. Do not copy header parsing, CRC/SHA helpers, GDB
transport, mGBA ownership, rendering, ledger, or BPS code into each game. Add
new game-agnostic behavior to `core/` only after a second independent game
proves the same contract; offsets, codepages, compression, pointer formats,
glyph identities, and script semantics remain game adapters.

## Recover source text locally

Every new game has its own text system — do not assume it resembles Golden Sun's Huffman format. First figure out, and record in the game's `README.md`:

- Where the text lives (fixed pointer table, compressed blob, script-engine bytecode, …) and what compression, if any, is used.
- Whether a byte-accurate codepage/decoder can be derived (preferred — deterministic and cheap to rerun), or whether the text needs to be recovered by rendering the game's own font glyphs and reading them back with OCR. `core/ocr/vision_ocr.swift` (see `core/ocr/README.md`) is the game-agnostic tool for this — Apple's on-device Vision text recognizer, macOS only. OCR output is candidate evidence, not ground truth — cross-check it against a strict decoder once one exists, and never copy OCR output directly into a translation record.
- Write whichever method you land on to `research/<game>-decoded.jsonl`, one JSON object per line: `{"string_id": …, "locale": …, "text": …, "provenance": …}`. This is the **local source table** that `core/ledger/restore_translations.rb` reads — see `core/ledger/README.md` for the exact contract.

Reverse-engineering the text system is the long pole for any new game and cannot be shortcut by this skill or the ledger tooling — budget real time for it, and report what's confirmed vs. still guessed rather than assuming a first pass is complete.

**"Glyph addressing is solved" and "glyph identities are known" are different completion states — track them separately, not as one binary "codepage done" checkbox.** It's easy to feel a codepage is finished once you've derived `address = base + index * stride` for every glyph pool and confirmed it with a couple of zero-free-parameter address matches — that only proves the *pool* is real and located, not that you know what each of its (often 100+) populated entries actually *is* in Unicode. A pixel render that a human reads as "looks like plausible kanji" is not the same evidence as an individually cross-referenced identity (e.g. a specific index confirmed via a known on-screen word). When you finally build the decoder that turns glyph-ID sequences into real text (not another pixel render), the gap becomes unavoidable: Shining Soul I's session 12 had 100%-located pixel tables for five glyph pools but only 12 individually-confirmed kanji identities across all of them, so ~90% of real dialogue lines carried at least one `unmapped_glyph:<category>:<index>` placeholder even though "the codepage" had been reported as functionally complete for several sessions. Track completeness as *identities confirmed / non-empty table entries*, not "addressing formula solved y/n" — and when reporting decoder output, separate placeholders (no known identity at all) from lower-confidence tiers (a single supporting data point, or an ordered-layout hypothesis with no independent cross-check) rather than collapsing everything into one clean/dirty binary; annotate which tier each record used so a translator knows how much to trust it.

### Two separate problems: finding the text structure, and mapping glyph IDs to Unicode

These are genuinely different problems with different tools, and conflating them wastes effort. Golden Sun's own history makes the split clear (see `games/golden-sun-the-lost-age/research/baseline-20260814.md` and `games/golden-sun-the-broken-seal/research/jp-codepage-derivation.md` for the full record):

1. **Finding the structure** — where strings live, how they're indexed, what compression (if any) wraps them, where the font-rendering function is. For Golden Sun this leaned heavily on *pre-existing public reverse-engineering* for that exact game (a Huffman-scheme writeup, a decompression reference implementation, a partial decompilation project with named functions) — the hard structural work had already been done by someone else and just needed confirming against this project's own clean ROM. **Check for this first** (romhacking.net, GBAtemp, a franchise-specific fan wiki or decompilation repo) before assuming you're starting from zero — but many games, especially ones without an existing fan-translation scene, genuinely have nothing public to lean on, in which case this step *is* the long pole and the disassembly/emulator techniques in the section above are what fill the gap no community reference is filling.
2. **Mapping glyph IDs to Unicode, once you can already extract "string N is this ordered sequence of glyph-ID codes."** Two distinct methods exist for this, and which one applies depends on whether a sibling game's codepage is already solved:
   - **Raster byte-matching (fast, exact, no OCR needed)** — only possible when another game shares the same font asset and *its* codepage is already confirmed. Render each known glyph's raw pixel bytes, search for the identical byte run in the new game's ROM, and the position tells you the new game's glyph ID for that character. This was Golden Sun's second game's shortcut once the first game's table already existed (`derive_codepage_by_raster.py`) — cheap and precise, but only available the second time around within a franchise.
   - **Render-whole-string + OCR + corpus-wide statistical alignment (slower, needed the first time)** — the actual "from scratch" method, and the one worth generalizing. Once you can render a full string (not a single glyph in isolation — OCR does much better with real word/phrase context) from its glyph-ID sequence into an image using the confirmed font-rendering format, run OCR on it (`core/ocr/vision_ocr.swift`), then align the OCR'd characters against the string's glyph-ID sequence with an edit-distance algorithm that treats *already-known* glyph IDs (e.g. base kana/ASCII) as anchors and lets *unknown* glyph IDs float to whatever OCR character lines up in that position. Do this across the *entire* corpus, not one string at a time, and accumulate votes per unknown glyph ID — a single OCR misread is noise, but the same glyph ID landing on the same character across dozens of independently-OCR'd strings is a real signal. Discard low-quality alignments (a string whose overall edit distance to the OCR reading is too high probably has other problems — wrong font offset, wrong string boundary — and its votes aren't trustworthy) and discard votes that aren't even plausible characters for the target script (filters obvious OCR noise). `games/golden-sun-the-lost-age/tools/infer_ja_codepage.rb` is the reference implementation of this pattern — read it before reimplementing something similar from scratch. It has not yet been generalized into `core/`, because it's only been used once; if a second game needs the same pattern, that's the signal to promote it.
   - **Known-ground-truth screen content (fastest, opportunistic, no OCR)** — when a reachable screen displays text whose content you already know from context (a fixed UI label, or — the strongest case — a *systematic, conventionally-ordered layout* like an on-screen kana/character input keyboard), read the tilemap or OBJ tile-index array directly and match position to known content; skip OCR and statistical voting entirely, since the answer is already known. A single systematic-layout screen (e.g. a name-entry kana grid, which follows the same fixed gojuon ordering across virtually every Japanese game that has one) can yield an order of magnitude more confirmed glyph mappings in one pass than accumulating scattered known UI labels one at a time — worth actively navigating toward such screens (menus that imply an input grid, options screens with an obvious fixed vocabulary) rather than only opportunistically noticing them. Only applies when such a screen is reachable and its content is genuinely known ahead of time; treat it as a third tool alongside the two above, not a replacement.
   - **A glyph table's own internal ordering can BE the known ground truth, with no screen or OCR needed at all** — many glyph tables place a kana/kanji block first and then continue with punctuation, then the full ASCII/Latin alphabet, then digits, all in their universally standard order (comma-then-period, A-through-Z, 0-through-9). Once you have a handful of confirmed addresses bracketing such a block, render the whole span as a labelled grid (index number under each glyph) and read it directly — a clean "P" sitting in the correct alphabetical position between confirmed "O" and "Q" neighbors is close to unambiguous, categorically more reliable than kanji shape-matching (where multiple real characters can look similar) or OCR (which can misread the same glyph the same wrong way every time). This is cheap: no emulator, no OCR run, just rendering+reading pixels you can already address. Shining Soul I's session 14 found its highest-value untranslated glyph this way (a bare frequency count over already-decoded corpus output pointed at char_idx 151+, a region nobody had looked at because eleven prior sessions were focused on kanji) and picked up 7 punctuation/Latin identities in one pass this way. **Still corroborate with real-corpus context before accepting, not shape alone** — the ambiguous cases are real (a solid vertical bar could be "!" or literal "|"; two visually-near-identical dash glyphs at different table positions could be the same character duplicated or two genuinely different ones (hyphen vs. em-dash vs. chōonpu) — check byte-identity, not just eyeball similarity, before assuming a duplicate). The strongest version of this corroboration is a fixed, repeated *pair* of unknown glyphs landing in a real, semantically-obvious template across many independent corpus lines (session 14's "U"+"P" always appeared adjacent, always right after a known "力", across 13 lines forming "...力UP" — a completely standard JP-RPG stat message using literal Roman letters) - that is real-sentence cross-reference evidence, not a shape guess, even though the source technique was direct pixel-reading rather than OCR.

Do not skip straight to per-glyph OCR guessing on isolated single characters — it's both less accurate (no context for the recognizer) and throws away the statistical-power advantage of voting across a large corpus.

**Verification needs a third layer beyond the quality gate and the plausible-character filter — reading the decoded output back in context.** Shining Soul I's session 13 was this pattern's first real execution outside Golden Sun (ported `infer_ja_codepage.rb`'s algorithm — same edit-distance/NFKD/vote-accumulation approach — onto a glyph-ID system keyed by `(pool, index)` pairs instead of single-byte codepage units; the port was mechanical once the vote key was generalized). Two verification layers were already in the skill text (discard low-quality alignments; discard implausible-script votes) plus an obvious third (eyeball each accepted candidate's raw ROM pixels next to a normal font's rendering of the claimed character, to catch outright shape mismatches). All three still let four wrong, high-vote, shape-plausible identities through — because OCR's failure mode here wasn't random noise, it was a *consistent* misread (the same wrong character every time a particular glyph appeared), which produces internally-coherent, high-confidence-looking vote tallies that neither a vote-count/ratio bar nor a shape comparison can distinguish from a correct one. What did catch it: after provisionally adding the accepted candidates to the decoder, re-running it over the *whole* corpus and reading newly-unlocked real sentences for fluency. A wrong identity shows up as a broken word or an impossible grammatical construction in an otherwise-clean sentence (e.g. a candidate meaning "drink" sitting in a slot that takes damage and has a defense stat — nothing to do with drinking) even when the same wrong candidate reads as merely "plausible-looking" in isolation. One correction went the other way: a *rejected* (below-threshold) candidate turned out to be very likely correct once read in a real sentence's context (`防[X]力が上がる` next to an already-confirmed `防` is unmistakably `防御力` — "defense power" — a completely standard RPG stat message), and was added as a distinctly-flagged, non-vote-derived provisional entry rather than silently promoted to the same tier as a statistical winner. Track vote-derived and context-derived provisional entries as different evidential shapes in the same tier, not as one undifferentiated bucket — a future session deciding whether an entry is worth an independent address cross-reference needs to know which kind of evidence it's already standing on. Budget real time for this third pass — it is not optional cleanup, it is where this session's four real false positives were actually caught, after two earlier layers had already let them through.

### When you don't even know where the text lives yet

For a game with no prior public reverse-engineering (check romhacking.net, GBAtemp, and any franchise-specific fan wiki before assuming you're starting from zero), static byte-pattern scanning alone is not enough — it produces plausible-looking candidates that are mostly false positives, and there is no way to tell which without cross-referencing against something that actually runs. This project's second real use of this skill validated a concrete escalation path, in order:

1. **Structural byte scans first** (cheap, always start here): does the ROM contain plain Shift-JIS anywhere (search for common UI/menu words in their exact byte encoding)? Are there runs of 4-byte little-endian values that fall inside the ROM's own address space (`0x08000000`-`0x08FFFFFF`), which would suggest a pointer table? Both can come back empty on a real game — that is itself a useful, reportable negative result (it rules out the two most common "obvious" designs), not a dead end.
2. **Disassemble compression-call candidates before trusting them.** THUMB's 16-bit encoding is dense enough that almost any byte sequence decodes to *some* syntactically valid instruction — "capstone didn't error" is a near-worthless signal on its own. Confirm candidates by checking whether the surrounding "function" contains instructions that don't exist on the GBA's ARM7TDMI (no coprocessor instructions, no ARMv8-M-only opcodes) and whether branch targets land in sane code regions. A candidate that fails this is data that got lucky, not a real call site.
3. **Run the ROM in an emulator and read live memory when static analysis stalls.** `mgba -g <rom>` opens a GDB remote-protocol server (default port 2345). If no `gdb`/`lldb` setup is available or convenient, the protocol is simple enough to script directly over a raw TCP socket in Python — write a minimal client rather than blocking on tooling. Known `mgba` GDB-stub quirks worth not rediscovering: it will not cleanly accept a second connection after one drops (kill and restart `mgba` per session, don't try to reconnect on the same port), and sending two packets back-to-back with no delay has a real chance of a dropped/unanswered packet (add a small delay before send, and retry once on read timeout).
4. **Render VRAM yourself if you can't get a screenshot.** A headless environment may have no display (`screencapture` failing is the tell) — that doesn't block visual verification. Read `DISPCNT`/`BGxCNT` to know the video mode and which layers are active, then pull VRAM + palette (+ OAM for sprites) over the same memory connection and decode tiles into an image. This produces the same kind of "does this actually look like the game" confirmation a screenshot would. Two decoding traps to know about going in: (a) **charblock vs. screenblock** — part of VRAM holds raw tile pixel data (charblock) and another part holds tilemap entries (screenblock: tile index + flip flags + palette bank, not pixels); decoding a screenblock region as if it were pixels can produce structured-looking noise that *coincidentally* resembles a glyph table at thumbnail scale — verify which region you're in from the layer's actual `charbase`/`screenbase` registers before trusting what you rendered. (b) **sprite tiles must be composited using their actual OAM placement** (position, size, tile index, 1D/2D mapping mode), not laid out as a naive grid — a naive grid fractures multi-tile characters/sprites into unreadable fragments and can make you think the tile data is garbage when it isn't.
5. **A visually-confirmed render plus a byte-identical ROM-to-VRAM match is strong evidence; a "looks plausible" render is not.** If you find candidate font/text data, check whether the exact bytes exist unmodified somewhere in the ROM (rules out compression for that data) and whether repeated on-screen characters map back to the *same* source bytes (a real shared-glyph font does this; independently-drawn per-screen art does not). Report a find as confirmed only once you have this kind of corroboration — and if an earlier "confirmed" turns out to be a screenblock-as-pixels mistake or similar, retract it explicitly in the game's docs rather than quietly dropping it. A documented false lead saves the next session real time; a silently-abandoned one gets rediscovered from scratch.

6. **Once you have a handful of confirmed glyph addresses, try fitting them algebraically against the script's conventional ordering before reaching for the emulator again.** If several known glyph addresses share a constant stride, check whether `address = base + conventional_index * stride` fits all of them with zero free parameters once the base is fixed (e.g. Japanese games very often lay out kana tables in standard gojūon order). This is pure arithmetic on data you may already have recorded from earlier sessions — it can solve an entire table's addressing formula in seconds, before any new mGBA/GDB pass, and is worth trying even when the emulator-based recon techniques above are available and working. Shining Soul I's session 7 found its largest glyph table's addressing formula this way from just 7 previously-recorded points, and only used the emulator afterward to confirm the call chain that consumes it. Relatedly: a candidate function "tested and rejected" during one recon session may not actually be wrong — it may simply have been tested in the wrong moment (e.g. an idle/steady-state screen instead of the specific transition that triggers the behavior in question). Record the *test context* alongside a rejection, not just the verdict, so a later session can judge whether it's worth re-testing in a different context rather than treating "already tested" as settled.

7. **When a piece of data is known to be *consumed* somewhere (a confirmed call site, a confirmed destination write) but its *source* isn't found by static scanning, walk the call chain upward from the consumer rather than continuing to scan statically.** Static byte-pattern scanning (searching for a plausible source-string encoding, a literal-pool constant equal to a table base, a fixed-stride delta between known values) implicitly assumes the source data appears in ROM in a form that resembles the final consumed value. That assumption breaks down as soon as the value passes through multiple function calls with intermediate transforms (bit-field packing, indirection through a small lookup table, per-category dispatch) — at that point the data's *shape* in ROM has nothing in common with its shape at the consumption point, and no amount of clever static searching will find it, because there is nothing to match against. The reliable alternative: set a breakpoint on the entry of the function containing the known consumer, read the caller's argument registers and `lr` (return address) when it hits, then set a breakpoint on *that* caller's own entry and repeat — climbing one call frame at a time — until a function's argument is no longer "some other register's computed value" but is instead a raw pointer/index read directly from a named memory location. This is a general reverse-data-flow technique, not specific to text systems (it applies equally to finding the source of any indirectly-computed value — animation frame tables, item stat lookups, anything), and it converges quickly (often 1-3 call frames) because each hop either confirms a known consumer more precisely or hands you a strictly-earlier fact to chase. Shining Soul I's session 8 used exactly this to go from a single known BIOS-copy call site to a full NUL-terminated string of character codes two call frames up, after session 7's purely-static searches (adjacency-delta scan, exact substring search, literal-pool search) had all come back empty on the very same data — the static searches weren't wrong to try (they're cheap and sometimes work), but their failure was itself the signal to switch techniques rather than try yet another static variant.

8. **When a disassembled "lookup table" load resolves to an address outside ROM space, the table is runtime-only and static analysis will never find its contents — go read live memory instead.** A `ldr rX, [pc, #imm]` (or any PC-relative literal load) that resolves to a small dispatch/lookup table is easy to mistake for "just another ROM constant to dereference and keep tracing." Before spending more effort on it, check whether the *loaded pointer itself* falls inside the ROM's address range (`0x08000000`-`0x09FFFFFF` on GBA) or inside RAM (EWRAM `0x02000000`+, IWRAM `0x03000000`+). If it's RAM, the table is populated at boot/runtime and by definition has no fixed byte representation in the ROM file — no amount of clever static scanning will recover its contents, because there is nothing in the ROM to find. The only way to read it is to connect to a running emulator and read that memory address directly. Shining Soul I's session 11 found a 16-entry "category -> glyph-pool-struct pointer" dispatch table this way: the literal resolved to `0x030065f0` (IWRAM), not a ROM address, which explained why treating it as a ROM constant made no sense.
9. **To resolve rare/hard-to-trigger data, hijack a known-working consumer call instead of hunting for the screen that would naturally display it.** If a function that renders some piece of data (a string, a sprite, an item) is already confirmed and gets called repeatedly on some easily-reached screen (e.g. once per frame on a redraw loop), you don't need to find or script navigation to whatever screen would naturally exercise the *specific* data you care about. Instead: set a breakpoint on that function's entry, wait for a hit with the already-known argument value, then overwrite the argument register (e.g. via the GDB stub's register-write packet) to point at your target data before letting execution continue. The already-validated pipeline downstream does the rest — decoding, table lookups, rendering — exactly as it would for real data, giving you a live, ground-truth answer (e.g. "what ROM address does the renderer actually read for this specific rare code") without needing to reverse-engineer or manually trigger whatever game state would normally produce it. This is the complement to technique 7 above: walking the call chain upward is for "I don't know where this data comes from"; hijacking a call argument is for "I know where candidate data lives in ROM, but reaching the specific screen/state that would exercise it is expensive or impractical." Combine both freely — Shining Soul I's session 11 used this to get a second, fully independent confirmation of a rare glyph-table base from real corpus text, without navigating anywhere beyond a screen already reachable by an existing script.

One more recurring, non-technical gotcha worth checking early: some ROM catalog `.zip` archives store filenames in a legacy CJK codepage (e.g. GBK) rather than UTF-8, which makes standard `unzip` fail with an encoding error. Extract with a tool that lets you specify the source encoding (e.g. Python's `zipfile` with a manual codepage decode) rather than assuming the archive is corrupt.

## Prepare a translation batch

1. Run `ruby core/ledger/restore_translations.rb LEDGER.jsonl research/<game>-decoded.jsonl games/<game>/work/BATCH.jsonl` to produce a local, source+target working file for the batch you're picking up (an empty or partial `LEDGER.jsonl` is fine for a first batch — every `string_id` present only in the source table becomes untranslated in the working file). If this is the very first batch for the game, there may be no ledger file yet; start from the source table directly and give every record `"status": "untranslated"`.
2. Select a coherent, reachable batch — e.g. one scene, one menu, one item category — rather than the whole game at once.
3. Write `zh-Hans` and `zh-TW` explicitly in the working file. Keep terminology consistent with the game's glossary (`games/<game>/translations/glossary.zh-TW.tsv` or equivalent); mark unreviewed work `ai_draft`.
4. Preserve control codes and structural markers exactly as the game's format requires — define the game's own convention for this (Golden Sun's uppercase `{HH}` markers were specific to its engine; a new game may use something else entirely) and document it in the game's README before translating.
5. Run `ruby core/ledger/strip_translations.rb games/<game>/work/BATCH.jsonl games/<game>/translations/BATCH.jsonl`. Only the output of this step is safe to `git add`.

Do not keep adding equivalent short static batches merely because they are
easy. Once one representative batch proves the same-length encoder,
re-extraction, adjacent-record guard, and BPS round trip, switch effort to the
next unproven release gate: natural or controlled consumer, layout/width,
changed-glyph render path, terminology review, or full-corpus coverage. A
larger row count does not compensate for a missing runtime or release contract.

## Build safely

1. Build the game-specific extractor/encoder/builder the same way the two existing games did: read `core/README.md` for what's reusable (patch tools, font subsetting) versus what must live under `games/<game>/tools/` (pointers, compression, codepage — all game-specific).
2. Let the builder reject source mismatches, missing glyphs, and control-code mismatches rather than weakening checks to make a batch pass.
3. Re-extract from the rebuilt ROM and confirm it matches the source table plus the intended translations — write a game-specific equivalent of `scripts/verify_text_delta.rb` if the text-system shape doesn't fit the existing one.

**First real test of this section on a non-Golden-Sun, non-Huffman game** (Shining Soul I session 15, first write-to-ROM attempt after 14 read-only recon sessions): the section's shape mostly transferred, but two things needed adapting for a game whose text system is a fixed-stride glyph-index table (`address = base + index * stride`, no Huffman, no pointer table) rather than Golden Sun's context-Huffman + pointer-table design.

- **Before assuming new-glyph insertion requires ROM expansion, scan every known glyph table's own *addressable* range for already-blank slots.** A fixed-stride table's on-disk size and its *code-format-addressable* size can differ — Shining Soul I's string format only exposes an 8-bit index field (`(code & 0xFF) - 1`, max 254), while the physical gap between one table's base and the next table's base was ~308 slots; the 255-307 range physically exists and is readable by static tools but can never be *referenced* by a real string, so it's useless for insertion and must be excluded from the scan. Within the addressable 0-254 range, a per-slot all-zero-bytes scan across all known tables found that four of five tables were >99% full but one (the table this game's rarest, lightest-used category mapped to) had 215 contiguous blank slots — enough for a real proof-of-concept insertion with **zero ROM expansion, zero displacement of existing content**, just filling in already-blank space. Try this before reaching for `expand_rom.rb`-style ROM padding (still likely needed eventually for a full translation's full character set, but not for a first proof of concept).
- **A bitmap font whose native glyph cell size exactly matches the target game's tile format needs no scaling at all — check for that match before reaching for a general-purpose rasterizer.** GNU Unifont's wide (CJK) glyphs are natively 16x16 monochrome; this game's glyph slot format (confirmed via the same pixel-decode function used throughout its recon sessions) is also exactly 16x16 (4 tiles of 8x8 4bpp, 2x2 arrangement). Converting was a straight 1bpp-to-4bpp palette-index remap with no resampling, which avoids the antialiasing/legibility judgment calls a scaled font would introduce. A simple edge-detection two-tone remap (foreground pixel with a background 4-neighbor → outline palette index, else → fill index), calibrated by frequency-counting the palette indices actually used across the game's own already-decoded real glyphs, was enough to produce a legible, in-style result without reverse-engineering the game's exact shading algorithm.
- **When the game's "extractor" is pixel-render/OCR-based rather than a clean byte-for-byte decoder, "re-extract and confirm a match" (as written above, and as Golden Sun's `verify_text_delta.rb` does) doesn't have a direct equivalent — verify with a static re-render plus a live-emulator re-render instead.** There is no golden decoded-text round-trip to compare against when the source table itself was built from provisional, tiered-confidence glyph identities. What worked: (a) a static render of the patched ROM's new string through the same rendering-format code the game's other recon tools already use (a pixel-level "does this decode and look right" check with no emulator), then (b) booting the actual patched ROM in the emulator and using the *already-validated, unmodified* render pipeline (the same VRAM/OAM composite tooling used throughout this game's recon) to confirm the real on-screen result, AND a render of an adjacent, untouched string to confirm the patch didn't corrupt neighboring data. Two independent renders (static + live) of both the changed and an adjacent unchanged string is a reasonable substitute verification bar when a byte-level round-trip tool doesn't apply.
- **On a shared machine running several concurrent, unrelated mGBA/GDB sessions for other games, the GDB stub can fail to start listening at all on a freshly-launched, otherwise-healthy mGBA process** — this is a *different* failure mode from the already-documented "won't accept a second connection cleanly" issue (that one is about *reusing* a connection; this one is about a fresh process's stub never binding its port in the first place, seemingly due to Qt event-loop startup timing contention under CPU load from sibling emulator processes). Symptoms: the process is alive and burning CPU, but `connect()` times out, and a raw `socket.bind()` test on the same port succeeds (proving nothing is actually listening — don't trust `lsof -i :<port>` for this on a sandboxed host; it can report empty even when something else's process legitimately holds the port, and its silence on your own not-yet-listening process is expected, not evidence of a problem elsewhere). One `-C ports.qt.gdbPort=<port>` attempt to move the GDB port off the 2345 default failed to bind that port at all — but that single data point is confounded by the same startup race described above (the process never got past "alive but nothing listening," and this session never went back to check whether it had silently bound 2345 instead). Other concurrent sessions on the same host *were* observed running with distinct `-C`-specified ports in their process listings, so treat "`-C` can't actually move the port" as unconfirmed, not established — don't generalize from one confounded attempt. Fix for the startup race itself: kill and cleanly relaunch (not reuse) the mGBA process and retry the connection; this is usually transient and resolves within one or two retries. Don't misattribute a connection failure to a ROM patch being corrupt without first ruling out this startup race — confirm separately (e.g., the same ROM reaching a known-good screen on a clean retry) before suspecting the patch itself.

## Verify the patch

1. Generate a BPS patch from the verified clean ROM and the rebuilt ROM (`core/patches/bps_create.rb`); apply it back (`core/patches/bps_apply.rb`) and compare byte-for-byte.
2. Record target CRC32, patch size, and SHA-256 in the game's README, the same way the two existing games do.
3. Perform mGBA runtime QA for reachable screens. Preserve test save data; report untested screens honestly instead of inferring success.

## Commit boundary

Stage explicit paths only. Include: game documentation, codepages/tools, tests, the game's `translations/*.jsonl` **ledger** files (never working files), and any `research/` analysis prose you intend to keep (offsets, counts, methodology, confirmed-vs-unconfirmed writeups — no raw decoded text or bulk scan dumps). Exclude: ROMs, patches, `work/`, screenshots, raw OCR output, condensed-but-still-bulky scan dumps, and any file `scripts/check-repository-safety.rb` would flag — run it before every commit that touches a new game's translation files; it will fail the build if a ledger file for a non-grandfathered game carries a `source` key. `git check-ignore -v <path>` before staging anything under `research/` you're not sure about.

Report the translated `string_id` set, source-recovery method and confidence, reverse-extraction result, BPS round-trip result, runtime coverage, remaining risks, and commit hash.

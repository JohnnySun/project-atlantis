# A9HJ 唯讀偵察與既有英文 patch 審計（2026-08-16）

## 結論摘要

目前最重要的結果不是「已找到文本」，而是**手上的 32 MiB 候選不能當 clean 日版基底**。它的標頭確實是 A9HJ／Rev.00 且標頭補數校驗正確，但公開資料列出的 clean dump 是 8 MiB、CRC32 `3C24ABCC`、MD5 `FC6A66C32B91FA0E526AE7782F29E86A`、SHA-1 `430A7062844888E68BD5587ED53A769BA548ADB3`、SHA-256 `FB388539B95FDAF6009BAD879E9BBB25955DAF8D4D438486A9213D407B2B48CE`。本機候選為 32 MiB、CRC32 `EC167D8B`、MD5 `6d93a0e224f040779ce898a6e917ce50`、SHA-256 `98c96d1f0753d22985c89fc3dd0e80ed5cbcd93eb09f880bb4418654347f7d58`；連前 8 MiB 也不符合公開 clean 指紋。它只能保留在本機作為候選／負面偵察資料。

## 本機候選 ROM

來源是本機暫存 ZIP `/private/tmp/v2-gba/Roms/GBA/勇者斗恶龙 旅团之心.zip`；ZIP 只有一個 33,554,432-byte ROM entry，已抽到被 `.gitignore` 保護的 `roms/base/dragon-quest-monsters-caravan-heart-jp-candidate.gba`。沒有把 ZIP、ROM 或原文檔案加入 Git。

另外對本機 `/private/tmp/v2-gba/Roms/GBA/` 與 `/private/tmp/gba-readback/` 的 483 個 ZIP entry 做了只讀標頭掃描：只有這一個 entry 的 game code 是 `A9HJ`，因此目前本機沒有第二份可直接交叉核對的 A9HJ ROM。

## 第一輪靜態掃描

工具只報告結構統計與 offset，不輸出可重組的原文：

- 以常見 UI 詞彙的標準 Shift-JIS bytes 搜尋：`はい`、`いいえ`、`レベル`、`たたかう`、`にげる`、`どうぐ`、`セーブ`、`ロード`、`なまえ`、`モンスター`、`キャラバン`、`ドラゴンクエスト` 全部 **0 命中**。
- Shift-JIS 合法位元組規則的結構掃描找到大量長片段，最長約 378 KiB；這種結果在圖形、程式表與壓縮資料中很容易發生，沒有字詞命中或執行期渲染交叉證據前，全部標成假陽性候選。
- 以 `0x08000000`／`0x09000000` ROM address window 搜尋 4-byte little-endian 指標，找到 244,711 個對齊候選；最大群聚重複出現在多個資料區段。數量與重複結構不足以單獨證明是文字指標表，還沒有可確認的字符串邊界。
- BIOS 壓縮 magic 的全域 byte scan 噪音極大：`0x10`、`0x11`、`0x20`、`0x30` 均有大量合理大小欄位候選。尚未反組譯驗證誰實際呼叫、誰實際消費，故目前不能說文字使用 LZ77／Huffman／RLE，也不能說完全沒有壓縮。
- ASCII 可列印長片段主要呈現程式／資料規律，沒有以明文 ASCII 形式出現的英文劇本 sentinel；這只排除一小類儲存方式，不等同於找到了日文 codepage。

目前的正確結論是「標準 Shift-JIS 直存未獲支持；文本可能是自訂單／雙位元組碼頁、壓縮資料或腳本引擎資料」，而不是套用《黃金太陽》或《光明之魂》的格式。

## mGBA／GDB 動態偵察（只限本機候選）

本輪使用 mGBA 0.10.5 Qt build 的 GDB stub；官方文件說明 `-g` 預設使用 2345 埠，而 Qt `GDBController` 的預設整數埠也是 2345（[官方文件](https://github.com/mgba-emu/mgba/blob/master/doc/mgba-qt.6)、[官方原始碼](https://raw.githubusercontent.com/mgba-emu/mgba/master/src/platform/qt/GDBController.h)）。因為其他 session 已占用 2345，本 session 只在 `/private/tmp/mgba-a9hj-2387/mGBA` 副本把 `GDBController` 的預設整數與顯示字串改成 2387，重新簽署該暫存副本；Homebrew 原檔與其他 mGBA 進程沒有改動或停止。

`tools/gdb_dynamic_recon.py` 的可重現流程是：

1. 在 `0x080000C0` 設軟體 breakpoint，收到 `S05k`，證明 BIOS 已進入 A9HJ ROM entry；entry 時 `PC=0x080000C0`、`CPSR=0x2000001F`。
2. 移除 entry breakpoint，執行指定秒數後送 GDB interrupt；一次 2 秒基線落在 `PC=0x02000358`，`r12=0x06000000`，顯示遊戲初始化已開始使用 VRAM。
3. 另在 `0x06000000` 設 GDB 寫入 watchpoint，收到 `T05watch:06000000;`；該停點的 `PC=0x00000244`，屬 BIOS 的首次 VRAM 寫入，不可誤標成劇本渲染器或文字 writer。
4. watchpoint 後再執行 0.5 秒的 capture 讀回 `DISPCNT=0x0100`、`BG0CNT=0x1D0C`：這是 Mode 0、BG0、4bpp，char base `0xC000`、screen base `0xE800`、32x32 regular tilemap。該次 live dump 的 VRAM 非零範圍包含 `0xC020..0xD540` 與 `0xE800` 起始的 screen block；palette 1024 bytes 全非零、OAM 384 bytes 非零。
5. 以標準 GBA tile／palette／screen-entry 規則離線渲染 `BG0`，畫面可重現為「enix presents」開機畫面。這證明目前開機圖像可以由 tile mode 路徑解碼；它沒有證明日文文本 codepage、控制碼或 VWF。原始 VRAM／PPM 只留在 `/private/tmp`，未提交。

前一個未設 watchpoint 的 2 秒 capture 曾讀到 `DISPCNT=0x0403`（Mode 3、BG2）且 VRAM 73,126 bytes 非零；這是啟動時序不同的另一個開機階段，不與後來的 Mode 0 結果合併成單一路徑。現階段應把「Mode 3 bitmap／直接 VRAM 寫入」與「BG0 4bpp tilemap」都保留為候選，直到 title、menu、事件對話畫面逐一追蹤。

目前尚未找到：劇本文本消費者、日文 glyph identity、壓縮函式的實際 caller、控制碼、字寬表或 VWF writer。動態結果只建立了入口／VRAM／開機 BG0 的證據鏈，且全部綁定候選 ROM 雜湊，不得回填為 clean 基底結論。

## 既有英文 fan translation 審計

公開的 KaioShin patch 是 1.0、2008-03-16 發布、IPS 格式，頁面宣稱完整翻譯，目標 clean ROM 指紋與上述 8 MiB 基準一致。其 readme 提供了可參考的工程時間線：2006-05 完成 script dump、2007-01 VWF code 可用、2007-12 完成 formatting／script insertion、2008-01 完成 menu hacking 並開始 beta test。

公開資料還確認幾項工程風險：

- 英文版引入自訂 VWF；NeoROMhacking 另有 KaioShin 的 16px DQM Caravan Heart VWF 字型條目，但這不是本專案可直接採用的字型或授權證明。
- 技能選擇畫面可能因每幀重畫整個文字 VRAM 而出現 VWF flicker；舊版 VBA／部分 flashcart 的 world-map timing 也有已知風險。
- 有兩個對話框消失問題被作者標成原版 event code 行為，沒有為了修補它而解完整事件碼；Luin 頭髮變黑也被標成原版 glitch。
- 怪物英文名沿用前兩款 DQM 的英文命名傳統，並對空間受限名稱做過英文側重譯。這只能作為英文工程／覆蓋審計的線索，不能當成 `zh-TW` 名稱來源。

本輪嘗試取得公開 IPS／RAR 二進位時，GameBrew download endpoint 回應 403；因此**尚未**做英文 patch 的 IPS record-level diff、實際改寫區域統計、英文 script 覆蓋率或回插路徑驗證。公開頁面宣稱「complete／100%」目前只記為外部聲明，不升格為本專案已驗證事實。

## 尚未確認與下一步

1. 由合法來源取得 clean A9HJ 日版 ROM，優先核對 `game.yml` 的公開指紋；若使用不同的 verified dump，必須完整記錄其 revision／size／hash，不能只以 game code 判定相同。
2. 對 clean ROM 重跑 `recon_rom.py`，比較候選與 clean 的差異區段，判斷目前候選是中文改版、擴容資料、不同 dump 或其他修改版本；這項比較只能作研究，不回填成翻譯基準。
3. 在取得 clean ROM 前，繼續用獨立 GDB 埠追蹤候選的 title／menu／事件輸入，並把每個停點的 ROM 雜湊、PC、顯示模式與記憶體摘要記入研究紀錄；必須避免使用被其他 session 占用的 2345 埠，且不得終止別人的偵察行程。
4. 找到文本消費者後，先確定字符串結構、控制碼、字型 addressing，再分開累積 glyph identity 證據。只有解碼器能輸出本機 `research/*-decoded.jsonl` 且 round-trip 可驗證，才進入 `restore_translations.rb`／`strip_translations.rb` 的有限翻譯批次。

#### clean ROM 的文字消費者與字型路徑

- `0x08012500` 是文字 state parser／stream consumer：從 literal pool 取得全域 state `0x03002830`，讀取 state flags、`+0x20` 的 current byte，並沿 `+0x18` script pointer 前進；`0x0801266C` 是同一 state 的字元／控制分支 handler。
- 在 `0x08012728` 附近，normal path 已讀出下一個 byte 後才呼叫 `0x08013738`。clean runtime trace 在 `0x08013738` 收到成對 byte code unit：`92 6F`、`93 7C`、`92 34`、`92 7A`、`92 31`（這些是 consumer 呼叫參數的證據，不可直接當作標準 Shift-JIS）。
- `0x08013738` 內部將兩個輸入 byte 分別放入 `r7`／`r8`，從 literal state `0x03002830` 取得 active glyph table（state `+0x04`），依 state `+0x10` 的模式計算每 glyph 的 32-byte stride，分別索引兩個 table-derived positions，再合成寫往 active output（state `+0x08`）。這證明「兩 byte → glyph table → 輸出」的 clean 路徑；它不是開機圖形解壓器。
- `0x08013E00` 是相鄰的單 byte glyph 路徑：把 parser 傳入的 `r0` 以同一 stride 索引 state `+0x04` glyph table，將單一 glyph 與 state `+0x16` output index 組成相同的 output queue。因而目前 codepage 應標成 mixed-byte，而非全雙 byte；穩定 menu 看到的十個假名位置可包含單 byte 與 paired glyph 兩類。
- `0x08013E00` 與 `0x08013E4C` 為同一文字 state 的座標／版面分支，會在 glyph 呼叫周圍被命中；parser 另有 `0xDF` 以上的 control／dispatch 分流。控制 byte 的完整語法、跳躍／指標邊界與寬度表仍未以 round-trip 證明。
- `E0`／`E1` 是目前第一個已收斂的 alternate-glyph consumer：dispatch table 的兩個 entry
  都指向 `0x0801284A`；該 handler 在一般 state branch 從 `state+0x18` 取一 byte、前進
  script pointer，再呼叫 `0x08013E4C`。layout branch 的 clean literal 是 alternate glyph
  pool `0x082E0BD4`；handler 以 lead 選擇 bank，`E0` 使用 base、`E1` 將 state `+0x10.bit1`
  設起來並提供 `0x4000` source bias。以同一 clean
  record `g02:v00:m0000` 的 raw sequence 與 alt pool 離線渲染，可看到 `EA` 前綴後的 speaker
  decoration、普通假名，以及 `E0` 消費的兩個漢字 glyph 位置；這只證明「E0/E1 + one byte
  → alternate glyph pool」的 consumer path（含 E0/E1 bank 分流），不替任何 alt glyph index 猜 Unicode，也不把
  OCR／視覺讀字直接寫入 source table。`tools/render_script_record.py` 已對這兩個 control
  做一 byte look-ahead 並按 lead 選 pool bank，其他 control 仍保留 marker。
- 一次文字 breakpoint trace 的 final IWRAM snapshot 中，`0x03002830` 的欄位為 `+0x04=0x082DF3D4`（active glyph table pointer）、`+0x08=0x0600C800`（active VRAM/output pointer）、`+0x18=0x082866A9`（當時 snapshot 的 script pointer）。另一個穩定 menu snapshot 的 `+0x18=0x08286574`；這些是 state pointer／時序證據，不能把任一 snapshot 位址直接宣稱為完整劇本 blob 起點。

### Clean script pointer table／extractor evidence（2026-08-16）

靜態反組譯把 script source 的選擇路徑再收斂一層。`0x080122AC`／`0x08012444` 的初始化 routine 會從 literal `0x08266240` 取第一層表，以 state `[0]` 選 group、state `[1]` 選 variant，再以 little-endian `u16(state + 2)` 選第三層 pointer entry，最後把取得的 ROM pointer 寫入 state `+0x18`。這與 `0x08012628`／`0x08012720` 每次沿 state `+0x18` 前進一 byte 的 parser 行為一致；它不是固定長度字串表，也不是可直接套用標準 Shift-JIS 的單層指標。

在 clean ROM 的三層 table 中，第一層 `0x08266240` 有 group `0..7`；group 6 的 variant 0 pointer table 位於 `0x082880FC`。其中 entry 8 指向 `0x08286574`，entry 16 指向 `0x0828667D`，後者的 byte span 到下一個 distinct pointer `0x082866A9`，包含 static extractor 識別的五組 pair `92 6F`、`93 7C`、`92 34`、`92 7A`、`92 31`；這五組正是 clean runtime trace 在 `0x08013738` 觀察到的 glyph-combiner 參數。pointer `0x082866A9` 本身是 `FF` 控制候選與大量重複空記錄的共同目標，不能僅由此斷言 `FF` 的完整語義。

`tools/extract_text.py` 對 clean ROM 的目前重現輸出只寫到 `/private/tmp/dqmch-clean-script-decoded-alt-v1.jsonl`：clean identity 為 size `8388608`、CRC32 `3C24ABCC`、SHA-256 `FB388539B95FDAF6009BAD879E9BBB25955DAF8D4D438486A9213D407B2B48CE`；以 `0x10000` max-span 設定得到 37,600 筆 pointer records、4,879 個 unique pointers、103,209 個 pair tokens、39,225 個 `E0/E1` alt-glyph tokens、217,774 個 control candidates、0 個截斷 pair。以 32 MiB candidate 執行同一工具會在輸出前因 size gate 拒絕，保留正式基準邊界。

這個 extractor 的 JSONL 是 source-bearing 研究輸出，`.gitignore` 以 `**/research/*-decoded.jsonl` 排除；目前 token 類型包括 `pair`、`alt-glyph`、`single-byte-candidate`、`control-candidate`，span 主要以同一 pointer table 的下一個 distinct pointer 作 boundary candidate。它已足以建立可重跑的本機原文表骨架，但尚未完成 terminator／jump／bank／其他 control 語義、mixed-byte glyph identity 對照或 encoder，因此不能宣稱已完成可逆抽取與翻譯。

### Script boundary candidate profile（2026-08-16）

`tools/profile_script_records.py` 對同一份 clean extractor JSONL 只做聚合統計，沒有把 raw
bytes 或 source text 寫進 committed research。重跑 receipt：

```text

records 37600
terminated-candidate 36509
no-terminator-candidate 1091

post-terminator-bytes 558656
pair-tokens 103209

```

這個數據把目前的 boundary 限制具體化：大多數候選 span 的第一個 `FF` 位於 span 最後一個
token，但 318 筆仍在其後有資料，另有 1,091 筆完全沒有 `FF`。因此不能把第一個 `FF` 當成
所有文字的終止碼，也不能用它直接產生 ledger string；下一步仍需從 caller 的 state／layout
行為、jump／bank 參數與未修改內容 round-trip 證明真正的 record boundary。

另外，clean parser 的 outer loop 在 `0x0801265A` 會以 state `+0x10` 的 bit 3
判斷是否繼續消費；`0x08013668` 的 `FF` handler 則依 state `+0x10` bit 5 與
state `+0x11` bit 7 分支清 flags，只有其中一條路徑清除 bit 3。這是「FF 會影響
pass／layout 狀態」的 caller／callee 靜態證據，但不是固定的 row terminator；不同
context 仍可能回到共同 flush path 或繼續 outer loop。因此本階段把 `FF` 保留為
context-dependent control candidate，尚未提升為 encoder 的終止指令。

### 局部 glyph output round-trip（2026-08-16）

對同一個 clean pointer record `0x0828667D`，`tools/verify_glyph_output.py` 讀取本機 decoded JSONL，從 clean ROM `0x082DF3D4` 依 32-byte stride 重建 38 個 single／pair glyph tile，並與 text breakpoint capture 的 VRAM offset `0xC800` 比對。執行時 state `+0x10=0x0C`（bit 0 為 0），輸出為：`glyph-tokens 38`、`exact-matches 38 / 38`、`mismatch-indices []`。

這個 exact 結果同時核對了 `0x08013738` 的特殊 pair mask：一般 `0x92` pair 的第二 dword 使用 `0xFF1FFFFF`，`0x93` pair 使用 `0xF1FFFFFF`，`0x92 0x30` 且 state bit 0 為 0 時使用 `0xF1F1FFFF`。未套 mask 時五個 paired glyph 各有一個差異 byte；套用後全部 38 個 tile 一致。這是 clean glyph addressing／identity／writer 的局部 round-trip 證據，仍不包含所有 script block、control semantics、width／line layout 或 ROM 回插。

同一 font table 的本機視覺 atlas 也已重現：file offset `0x2DF3D4` 起的 256 個 32-byte tile，使用穩定 menu capture 的 palette bank 3，以共享 `core/gba/render_vram.py` grid renderer 生成的 ignored PNG SHA-256 為 `7621bc944b2fcf9e7fa966783dfb558ef3a119463152f780cb0f2b482ce5eb87`。atlas 可直接核對數字、拉丁字母、平假名、片假名、標點與後段的額外字形區；這證實 table 是實際 glyph pool，而不是壓縮 blob，但 `0xC0+` 字形的完整 Unicode mapping、paired glyph 的語義與寬度仍不可由 atlas 排列臆測。用同一模型渲染 pointer `0x0828667D` 的 38 tiles，ignored PPM SHA-256 為 `55d9c476ff77b03240e0c0c41bd1b8c2667e86fa7011b62caea370ac7e9b5592`；視覺上形成連貫的日文文字列，且 tile bytes 已由上述 38/38 exact verification 交叉確認。

### 穩定 menu 的 glyph identity cross-check（2026-08-16）

`tools/verify_menu_glyphs.py` 讀取穩定第二次 A capture 的本機 VRAM，固定核對 BG0 screenblock offset `0xE844`、十個連續 tile ID `0x100..0x109` 與 char base `0xC000`；不把 raw VRAM 或完整日文 source 寫入輸出。clean extractor 另外在 group 6／variant 0 的 pointer entry 0 找到 `0x0828647C`，其 script prefix 與十個畫面位置一致。十個位置對應的 clean table code units 是：`0x33`、`0x26`、`0x34`、`0x52`、`0x2E`、`0x53`、`0x43`、pair `0x92 0x34`、`0x4B`、`0x55`；每個位置都只有一組 matcher 結果（pair 位置使用已驗證的 `0x08013738` mask）。把已知 menu 畫面讀作 `さいしょからはじめる` 時，這提供十個 glyph identity 的第三層交叉證據：script prefix、screen content、tile bytes、ROM table／pair model 互相一致。

`さ`、`い`、`し`、`ょ` 分別落在 `0x33`、`0x26`、`0x34`、`0x52`。目前已把可驗證的
大小假名區、已證明 punctuation／separator 與 valid diacritic pair 規則放入 v4 provisional decoder，但 glyph table

### Control dispatch 的參數寬度證據（partial）

parser 在 `0x08012768..0x0801277C` 對 `0xDF..0xFF` 建立 33-entry dispatch table。`0x08012776` 的 literal 位於 file offset `0x12780`（CPU `0x08012780`），其值是 table CPU address `0x08012784`；實際 entries 從 file offset `0x12784` 開始。caller 使用 Thumb `mov pc, r0`，所以 entry target 的 bit0 清除並不代表切換到 ARM state。`tools/audit_control_dispatch.py` 會對 clean ROM 驗證 literal、33 個 handler target 與以下 shape 表。對 handler 的 clean 靜態反組譯目前可安全整理為：

| control 範圍／byte | 已觀察的 source read | 證據邊界 |
| --- | --- | --- |
| `DF`, `E0/E1`, `E4`, `E6/E7` | `may-read-1`：在 state flag 分支中，可能從 state `+0x18` 取一 byte 並前進 pointer；另一分支操作 state `+0x1C` 等已存在欄位。 | 這是參數形狀，不是固定語義；必須保留 branch context。 |
| `E2`, `E3`, `E5`, `E9..EF`, `F1..F3`, `F5..F8`, `FB..FF` | `none`：在目前 handler entry 到共同尾端的 clean 靜態路徑中，未見固定從 state `+0x18` 取 source byte；主要修改 flags、cursor、VRAM queue 或 layout state。 | 未見 source read 不等於已命名為 terminator／newline／jump；仍需確認 caller 的停止條件。 |
| `E8` | `conditional-2`：部分 state branch 由 state `+0x18` 取兩個 byte 並前進 2；其他 branch 從 state `+0x1C` 等待中資料。 | `0x080129EE..0x08012A6C` 的 branch context 與 `0x13662` 呼叫關係仍未轉成 encoder contract。 |
| `F0` | `read-1`：從 state `+0x18` 取一 byte、pointer 前進 1，加入 state `+0x1C`。 | 數值用途已見，控制碼的上層語義仍未定名。 |
| `F4`、`FA` | `conditional-2`：state `+0x17 == 0` 時從 state `+0x18` 取 little-endian low/high 兩 byte、pointer 前進 2；否則消費 state `+0x22` pending counter。 | `+0x22` 的事件／loop 語義仍未完整還原。 |
| `F9` | `conditional-1`：state `+0x10` bit 7 清除時從 state `+0x18` 取一 byte、pointer 前進 1；另一 branch 不讀 source。 | 不能把它簡化成固定一 byte 指令。 |
| `FF` (`0x08013668`) | `none`；目前 entry 只清理 state flags 並回到共同 flush path，未見 source pointer read。 | 這排除「FF 必然是字串 terminator」；實際 row／cursor／layout 停止條件尚未由 caller 證明。 |

因此 extractor 目前保留 control byte 原值與相鄰 candidate bytes，不強行消費 context-dependent 參數、不替 handler 命名；這是為了避免在 encoder 尚未證明前破壞 pointer／event semantics。先前把 `F4/F5/FB` 統稱為 2-byte path 的記錄已由這次 entry-base 校正撤回：clean table 中真正的 2-byte candidates 是 `E8`、`F4`、`FA`，且都帶狀態條件。

### Glyph writer／DMA3／layout 靜態 receipt（partial）

`tools/audit_text_layout.py` 對同一份 clean A9HJ ROM 做 literal-level audit；它只讀取已確認的程式常數，不讀取或輸出 script source。重跑結果如下：

rom-sha256 fb388539b95fdaf6009bad879e9bbb25955daf8d4d438486a9213d407b2b48ce
combiner 0x08013738 single 0x08013E00 layout 0x08013E4C
state-pointer 0x03002830

這組常數與前述 38-token clean output check 相互吻合：雙 glyph 路徑以 8 個 dword 做 OR 合成，單 glyph 路徑使用同一個 glyph table／output queue，最後以 DMA3 將 `glyph_stride / 4` 個 word 寫入 state `+0x08` 的 output slot；`state[0x16]` 是 output index。`0x08013E4C` 另有 state bit 1 控制的 layout destination branch，alternate source bias 為 `0x4000`。`E0`／`E1` 的 handler 在 `0x0801284A` 以 lead 的低位導出該 state bit，故 `E0` 取 `0x082E0BD4 + 0x0000`、`E1` 取 `0x082E0BD4 + 0x4000`；本機 renderer 的 clean `g00:v00:m1171` 記錄含兩個 E1 token，作為非 debug atlas 的第二 bank smoke check。

## 候選 ROM 第一輪靜態掃描（歷史負面資料）

工具只報告結構統計與 offset，不輸出可重組的原文：

- 以常見 UI 詞彙的標準 Shift-JIS bytes 搜尋：`はい`、`いいえ`、`レベル`、`たたかう`、`にげる`、`どうぐ`、`セーブ`、`ロード`、`なまえ`、`モンスター`、`キャラバン`、`ドラゴンクエスト` 全部 **0 命中**。
- Shift-JIS 合法位元組規則的結構掃描找到大量長片段，最長約 378 KiB；這種結果在圖形、程式表與壓縮資料中很容易發生，沒有字詞命中或執行期渲染交叉證據前，全部標成假陽性候選。
- 以 `0x08000000`／`0x09000000` ROM address window 搜尋 4-byte little-endian 指標，找到 244,711 個對齊候選；最大群聚重複出現在多個資料區段。數量與重複結構不足以單獨證明是文字指標表，還沒有可確認的字符串邊界。
- BIOS 壓縮 magic 的全域 byte scan 噪音極大：`0x10`、`0x11`、`0x20`、`0x30` 均有大量合理大小欄位候選。尚未反組譯驗證誰實際呼叫、誰實際消費，故目前不能說文字使用 LZ77／Huffman／RLE，也不能說完全沒有壓縮。
- ASCII 可列印長片段主要呈現程式／資料規律，沒有以明文 ASCII 形式出現的英文劇本 sentinel；這只排除一小類儲存方式，不等同於找到了日文 codepage。

目前的正確結論是「標準 Shift-JIS 直存未獲支持；文本可能是自訂單／雙位元組碼頁、壓縮資料或腳本引擎資料」，而不是套用《黃金太陽》或《光明之魂》的格式。

## mGBA／GDB 動態偵察（只限本機候選）

本輪使用 mGBA 0.10.5 Qt build 的 GDB stub；官方文件說明 `-g` 預設使用 2345 埠，而 Qt `GDBController` 的預設整數埠也是 2345（[官方文件](https://github.com/mgba-emu/mgba/blob/master/doc/mgba-qt.6)、[官方原始碼](https://raw.githubusercontent.com/mgba-emu/mgba/master/src/platform/qt/GDBController.h)）。因為其他 session 已占用 2345，本 session 只在 `/private/tmp/mgba-a9hj-2387/mGBA` 副本把 `GDBController` 的預設整數與顯示字串改成 2387，重新簽署該暫存副本；Homebrew 原檔與其他 mGBA 進程沒有改動或停止。

`tools/gdb_dynamic_recon.py` 的可重現流程是：

1. 在 `0x080000C0` 設軟體 breakpoint，收到 `S05k`，證明 BIOS 已進入 A9HJ ROM entry；entry 時 `PC=0x080000C0`、`CPSR=0x2000001F`。
2. 移除 entry breakpoint，執行指定秒數後送 GDB interrupt；一次 2 秒基線落在 `PC=0x02000358`，`r12=0x06000000`，顯示遊戲初始化已開始使用 VRAM。
3. 另在 `0x06000000` 設 GDB 寫入 watchpoint，收到 `T05watch:06000000;`；該停點的 `PC=0x00000244`，屬 BIOS 的首次 VRAM 寫入，不可誤標成劇本渲染器或文字 writer。
4. watchpoint 後再執行 0.5 秒的 capture 讀回 `DISPCNT=0x0100`、`BG0CNT=0x1D0C`：這是 Mode 0、BG0、4bpp，char base `0xC000`、screen base `0xE800`、32x32 regular tilemap。該次 live dump 的 VRAM 非零範圍包含 `0xC020..0xD540` 與 `0xE800` 起始的 screen block；palette 1024 bytes 全非零、OAM 384 bytes 非零。
5. 以標準 GBA tile／palette／screen-entry 規則離線渲染 `BG0`，畫面可重現為「enix presents」開機畫面。這證明目前開機圖像可以由 tile mode 路徑解碼；它沒有證明日文文本 codepage、控制碼或 VWF。原始 VRAM／PPM 只留在 `/private/tmp`，未提交。

該次 0.5 秒 dump 的摘要雜湊可作為本機重跑比對：VRAM `0fdd5e16d85df1deb4890b039e3d2c7da2b7457e81da476927a62b165c09f70b`、palette `adf8356f4dab5e0fe8c24a8544e4e5472253b201a55979b808db306b3fa1514f`、OAM `ac39c4bb2c8699336aa8227f31b1834079bfb5c70cd22cc0d2bd0adc8478a3b1`、IWRAM `be4729a377e63095a2971044577e0f92bce21d58509926e428f5969cfaf621a9`。這些是候選 ROM 的時序性執行狀態，不是可提交的原始來源。

### 單一 VRAM consumer 追蹤與證據邊界

為了避免把任意 VRAM 寫入誤標成文字 writer，本輪改用共用 `core/gba/gdbstub_client.py`，只保留一條可重跑的 watchpoint 證據鏈；所有 live 結果仍綁定上述候選 SHA-256。

- 在 `0x04000130` 設 read-watchpoint 時，停止點落在 IWRAM `0x02000354`。候選 ROM 的對應 Thumb routine 位於 `0x08011D34`，讀取 active-low `KEYINPUT` 後以 `MVNS`／遮罩形成按鍵位元；將停止時的 `r0` 覆寫為 `0x03FE` 可重現 A 鍵輸入。這是輸入 consumer 證據，不是文本 consumer。
- 在 `0x06008000` 設單 byte write-watchpoint，第一次停止為 `T05watch:06008000;`，`PC=0x00000244`（BIOS），當下 `r0=0x03007E58`、`r1=0x06008004`、`r2=0x05006000`、`SP=0x03007E38`。stack 上的 `0x03007E48` 保存返回位址 `0x080121B1`，回到候選 ROM 的 `0x08012178` 初始化 routine；其 `0x080121AC` 呼叫 `0x080F6E60`，而 `0x080F6E60` 是 `SWI #0x0B` 的 `CpuSet` wrapper，目的區段是 BG char data。這證明目前命中的路徑是 tile／VRAM loader（含 IWRAM staging），不是字元索引解碼器或 VWF writer。
- 注入兩次 A 後，畫面穩定在 `DISPCNT=0x1240`、`BG1CNT=0x1F09` 的 4bpp title/logo tilemap（char base `0x8000`、screen base `0xF800`）；對 `0x0600F800` 的 screenblock write-watchpoint 連續觀察 5 秒沒有新命中。這個畫面可證明 tilemap 消費者，但沒有提供日文 glyph identity、文字控制碼或字寬資料。
- title/logo 使用的 124 個 tile 中，只有 2 個能與候選 ROM 以完整 32-byte tile 做精確比對；其餘不能直接視為 ROM 原始 tile，較符合 runtime staging／轉換或非對齊資料的假設。這是圖像路徑的負面結構證據，不能反推 codepage。

因此在**候選 ROM 的歷史偵察範圍**內，文字系統狀態固定為：`codepage=unknown`、`glyph identity=unproven`、`control codes=unknown`、`VWF writer=unproven`。公開英文 patch 的工程紀錄可作為待驗證假設：作者曾描述自訂 VWF 需要 width table，並指出 Kanji 另有一張表、script block 的 jump／pointer 邊界不固定，且濁音前有控制碼（[KaioShin 工程紀錄](https://kaioshin.wordpress.com/)）。這些是外部工程線索，不是本候選 ROM 的 runtime 證明，也不會被當成 `zh-TW` 翻譯來源；clean A9HJ 的目前證據以上方 clean 專節為準。

前一個未設 watchpoint 的 2 秒 capture 曾讀到 `DISPCNT=0x0403`（Mode 3、BG2）且 VRAM 73,126 bytes 非零；這是啟動時序不同的另一個開機階段，不與後來的 Mode 0 結果合併成單一路徑。現階段應把「Mode 3 bitmap／直接 VRAM 寫入」與「BG0 4bpp tilemap」都保留為候選，直到 title、menu、事件對話畫面逐一追蹤。

候選 ROM 的歷史偵察仍未找到可採用的劇本文本 consumer、日文 glyph identity、壓縮函式實際 caller、控制碼、字寬表或 VWF writer；那些動態結果只建立入口／VRAM／開機 BG0 的證據鏈，且全部綁定 candidate 雜湊，不得回填為 clean 基底結論。clean A9HJ 的目前證據與未完成項目以上一節為準。

## 既有英文 fan translation 審計

公開的 KaioShin patch 是 1.0、2008-03-16 發布、IPS 格式，頁面宣稱完整翻譯，目標 clean ROM 指紋與上述 8 MiB 基準一致。其 readme 提供了可參考的工程時間線：2006-05 完成 script dump、2007-01 VWF code 可用、2007-12 完成 formatting／script insertion、2008-01 完成 menu hacking 並開始 beta test。

公開資料還確認幾項工程風險：

- 英文版引入自訂 VWF；NeoROMhacking 另有 KaioShin 的 16px DQM Caravan Heart VWF 字型條目，但這不是本專案可直接採用的字型或授權證明。
- 技能選擇畫面可能因每幀重畫整個文字 VRAM 而出現 VWF flicker；舊版 VBA／部分 flashcart 的 world-map timing 也有已知風險。
- 有兩個對話框消失問題被作者標成原版 event code 行為，沒有為了修補它而解完整事件碼；Luin 頭髮變黑也被標成原版 glitch。

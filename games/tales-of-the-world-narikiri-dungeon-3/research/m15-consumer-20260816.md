# M1.5 文字消費者與 glyph 邊界（2026-08-16）

本回合只保存 offset、指標分類、寄存器與雜湊等可審核 metadata；完整 ROM、VRAM／IWRAM／palette／OAM dump 與 render 圖均留在 `/private/tmp`，不進 Git。沒有開始翻譯，也沒有把畫面 OCR 當作原文來源。

## 1. 五個資料窗的指標交叉分類

以嚴格 extractor 的 8,938 個 NUL／Shift-JIS record 邊界為集合，`tools/classify_pointers.py` 逐 byte 掃描以下形式：

- 任意 byte alignment 的 32-bit GBA absolute pointer；
- exact file-offset 16／24-bit relative value；
- 以 pointer location 或其後一個 word／halfword 為 base 的 16／32-bit self-relative value。

只有 absolute pointer 會升為 confirmed；relative match 仍標為 provisional，因為單靠 bytes 不能證明 relocation base。

| 資料窗 | records | confirmed absolute | provisional relative |
| --- | ---: | ---: | ---: |
| `0x100000–0x103000` | 173 | 171 | 2 |
| `0x105000–0x10D400` | 1,603 | 1,586 | 15 |
| `0x111000–0x114000` | 387 | 386 | 0 |
| `0x140000–0x1C4000` | 6,532 | 5,861 | 538 |
| `0x1C8000–0x1CC000` | 243 | 0 | 235 |
| **合計** | **8,938** | **8,004** | **790** |

低位 16／24 bits 與同一 absolute word 重疊時不另算 relative alias。分類器本身只輸出 record ID 與 offset；重跑命令如下：

```sh
PYTHONDONTWRITEBYTECODE=1 /usr/bin/python3 \
  games/tales-of-the-world-narikiri-dungeon-3/tools/classify_pointers.py \
  games/tales-of-the-world-narikiri-dungeon-3/roms/base/Tales_of_the_World_Narikiri_Dungeon_3_JP_AGB-B3TJ-JPN.gba \
  --out /private/tmp/tow-nd3-pointers.json
```

## 2. 選定 record 與下一個 static consumer

本回合選定 `sjis:0x146EE0`（file offset `0x146EE0`，GBA address `0x08146EE0`）。它有一個 confirmed absolute reference：

- pointer word：file offset `0x0DD1B9C`（GBA address `0x08DD1B9C`）；
- adjacent direct-pointer table：file range `0x0DD1B84–0x0DD1BB4`，共 12 words；
- 相鄰資料窗 record `0x146EB4`、`0x146EC8` 也落在同一個 direct-pointer table；`0x146F24` 則有另一個 single-word direct reference `0x0A7270`。

這個選擇比只 watch `0x140000–0x1C4000` 起點更精確，且保留了可重現的 concrete record ID。ROM `0x08003444` 附近另有一個 provisional relative-pointer resolver：

```text
0x08003444  push {lr}
0x08003446  r2 = r0
0x08003448  r0 = [r2]
0x0800344A  compare r0 with r1
0x0800344E  r0 = r1 << 2
0x08003450  r1 = r2 + 4 + r0
0x08003454  r0 = [r1]
0x08003456  r0 = r2 + r0
```

這段是下一輪應設 breakpoint、再以 `r0` table base／`r1` index 交叉驗證的 exact callsite 候選；目前沒有把它宣稱為 `0x0DD1B9C` 的 live caller。

## 3. bounded runtime 結果

使用本 session 自己啟動的 B3TJ mGBA 0.10.5 headless process 與獨立 port `2346`，client 使用共用 `core/gba/gdbstub_client.py`。`consumer_probe.py` 先確認：

- ROM identity：title `TOWNARIKIRI3`、game code `B3TJ`、maker `AF`、size 16 MiB、CRC32 `1867CCEF`；
- initial stop：`S02`，reset `pc=0x00000000`、`sp=0x03007F00`；
- settle I/O：`DISPCNT=0x1000`、`BG1CNT=0x1505`；
- KEYINPUT read watchpoint：`0x04000130`，40／40 次 stop 均為 `rwatch`，可重現的第一個 caller snapshot 為 `pc=0x08001914`、`lr=0x0801591B`、`r0=0x04000130`、`sp=0x03007DC4`。

bounded sequence 是 `start:8,none:12,a:8,none:12`。結果是：

- **confirmed runtime input consumer：** KEYINPUT read watchpoint 可命中，並可在每次 stop 後覆寫 active-low input destination register；
- **negative for selected record：** `0x08146EE0` read watchpoint 0 次命中，termination 為 `sequence-exhausted-without-record-hit`；
- **scope：** 這只證明該短序列沒有進入會讀取此 record 的畫面，不證明 record 不會在更深的選單／事件中被使用；
- **post-hit VRAM：** 因沒有 record hit，沒有把任何 VRAM write、decoder 或 glyph attribution 誤掛到這個 record。

這一回合的 JSON 僅在 `/private/tmp/tow-nd3-m15.json`；raw dump 沒有由 probe 寫入 repository。

## 4. VRAM exact-match 與壓縮／轉換界線

既有 core baseline capture 的 title-screen snapshot（`DISPCNT=0x1260`、`BG1CNT=0xD001`）以 GBA BG1 位元解析為 charbase `0x0000`、screenbase `0x8000`、4bpp、OBJ 1D，並用共用 `core/gba/render_vram.py` 產生過 tilemap render。這個畫面沒有與 `0x146EE0` 的 runtime read 建立因果鏈。

對 baseline VRAM 的每個非零、32-byte tile-aligned block 做 ROM exact byte search：

- 全 VRAM 有 806 個 exact tile matches；
- BG1 charbase `0x0000–0x3FFF` 只有 1 個 match，位於 VRAM offset `0x00020`，ROM search 起點落在 `0x774FD9` 附近；
- 同一 tile 在 ROM 有多個重疊／重複候選，不能由此唯一反推出 glyph、codepage 或來源 record；
- selected record 沒有 runtime hit，因此沒有「該 record 的實際 glyph tile」可確認。

這是 **provisional／negative** 的 glyph 證據：圖形資料確實經過 runtime VRAM 路徑，但未命中的 record 沒有可歸因的 ROM→VRAM tile match。和 M1 已確認的 BIOS LZ77／RLE wrapper 命中合併解讀時，應優先保留「壓縮或轉換後才到 VRAM」的風險；不能拿未歸因的 tile match 當文字 source table，也不能用 OCR 反推原文。

## 5. M1.5 結論與邊界

| 證據 | 狀態 | 結論 |
| --- | --- | --- |
| 五窗 pointer cross-classification | **confirmed／provisional** | absolute 與 relative 候選已分層；`0x146EE0` 有 concrete direct reference |
| KEYINPUT read watchpoint | **confirmed-runtime** | 早期 UI polling caller 可重跑，input path 可觀測 |
| selected record read watchpoint | **negative** | 此 bounded 序列未到達 `0x08146EE0` consumer |
| `0x08003444` resolver | **provisional-static** | 可作下一個 breakpoint／caller 驗證點，尚未證明是 selected table 的 live caller |
| codepage、控制碼、glyph decoder | **unconfirmed** | 不可開始翻譯或回插 |
| capacity／pointer rewrite／round-trip | **unconfirmed** | 不可宣稱可逆 builder |

下一輪不再擴充 transport 或 port shim；應以較可靠的早期 menu 導覽或直接在 `0x08003444` 設 breakpoint，記錄 resolved pointer 是否落在 `0x146EE0` 與其相鄰 table，再沿 caller 一層連到 decoder／glyph destination。完成這個 live edge 前，維持「研究完成、翻譯未開始」狀態。

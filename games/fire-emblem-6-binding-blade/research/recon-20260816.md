## 專案內可重跑入口

```sh
python3 tools/recon_afej.py roms/base/AFEJ.gba --json-out work/afej-recon.json
```

該工具是結構掃描器，不是解碼器。它會：

- 解析 GBA 標頭並計算 CRC32、MD5、SHA-1、SHA-256。
- 搜尋少量標準 Shift-JIS UI 探針；零命中只能排除「直接存放這些探針」，不能證明沒有文本。
- 掃描 ROM 位址型 32-bit little-endian 值，列出連續指標候選；未經反組譯／執行期交叉驗證不得稱為字串表。
- 掃描 BIOS LZ77／Huffman／RLE 等標頭候選；標頭命中不是壓縮資料被文本使用的證據。
- 以 4bpp tile 窗口產生字形候選；必須再用畫面、VRAM、實際重複字形與 ROM 原 bytes 比對確認。

輸出報告放在 `work/`；它不應包含解出的日文原文。若後續解碼器產生原文表，檔名必須採 `research/afej-decoded.jsonl`，由 `.gitignore` 保護，不能加入 Git。

## Runtime：已確認的文字／字型消費路徑

### 輸入與觀測方法

- 使用自己啟動的 mGBA 0.10.5 進程與獨立 GDB stub port `2346`；未停止其他 session 的 mGBA，也未修改 ROM。
- GDB read-watchpoint 命中 `KEYINPUT` `0x04000130`，ROM Thumb 輪詢位於 `0x08001908`–`0x0800192e`，輸入處理函式為 `0x08001734`。以暫存器覆寫模擬按鍵只用於到達遊戲流程，沒有寫入 ROM。
- 初始 graphics 觀測另外命中 BIOS LZ77 wrapper `0x0809dcf0`；這證實 graphics 解壓呼叫存在，但目前不把它誤標成文本壓縮或字型來源。

### 文字 buffer 到 glyph object

這條路徑已在乾淨 AFEJ 啟動中命中，記錄的是位址、控制流程與工作記憶體，不提交日文原文：

1. ROM 內的兩位元組字元 map 位於 file offset `0x691644`，GBA address `0x08691644`。read-watchpoint 在執行 `ldrb` 後於 `0x080992e4` 停止；當時 `r0=0x02029404` 指向 EWRAM 文字 buffer，`r2=0x08691644` 指向 ROM map，`lr=0x0809931b`。
2. wrapper `0x08099314` 呼叫 `0x080992dc`。後者逐對比較兩個 byte，找到項目便回傳 glyph index，找不到則回傳 fallback；這是 runtime codepage lookup，而不是只靠靜態 Shift-JIS 命中推測。
3. 實際字元消費函式從 `0x08098c24` 讀取 `r6` 指向的 EWRAM buffer，並在 `0x08098c5c` 呼叫 map lookup。當次 `r6=0x02029404`、`r7=0x086917c0`。
4. 同一函式在 `0x08098c3c` 配置 glyph 渲染物件；`0x08098c60` 的 `strh` 將 lookup 結果寫入物件的 glyph 欄位。對 `object base=0x02023fb8` 的 `object+0x4a=0x02024002` 設 write-watchpoint，實際命中 `T05watch:02024002`；當次 glyph index 為 `0x43`，`r2=0x086916ca` 仍位於 map 區域。

因此目前可安全下的結論是：`EWRAM text buffer → AFEJ two-byte map → glyph index → EWRAM render object` 已證實。尚未把 glyph index 往後追到 4bpp bitmap 的 VRAM／OBJ tile 搬運，也尚未證實劇情、支援、事件及資料表的完整表格邊界；這些仍是 M1 待辦。

### 共用 core/gba baseline 與 VRAM sink

main 的共用 runtime 工具（commit `0455796`）測試為 6/6 通過；本次 AFEJ 使用 `core/gba/capture_runtime.py` 產生的 summary 與 raw dump 留在被忽略的 `work/runtime-core/`，沒有把 ROM／RAM 原文或 PPM 加入 Git。baseline 觀測到：

- `DISPCNT=0x3b00`，為 Mode 0；OBJ mapping bit 為 2D。
- `BG0CNT=0x0d08`（4bpp、charbase `0x8000`、screenbase `0x6800`）、`BG1CNT=0x0e01`（charbase `0x0000`、screenbase `0x7000`）、`BG2CNT=0x0f0a`（charbase `0x8000`、screenbase `0x7800`）、`BG3CNT=0x1f0b`（charbase `0x8000`、screenbase `0xf800`）。
- 標準 capture 的首次 VRAM write 命中 `T05watch:06000000`；這是 graphics 初始化基線，不單獨視為文字證據。共用 `render_vram.py`／`render_oam.py` 已依上述寄存器產生 ignored PPM，baseline OAM 當下沒有可見 sprite。

從 glyph object 往下追時，read-watchpoint 先在 glyph 欄位消費函式的 `0x08098f78` 命中；接著 `0x08099424` 依 glyph index 計算 bitmap 合成位置，呼叫 `0x080995b0`。該 composer 的 live 參數為 `r0=0x020020c0`（EWRAM glyph buffer）、`r1=0x06014000`（VRAM tile 目的區）、`r2=0`。其內部 `0x08099580` kernel 對兩個區域做 bit-plane／tile word 合成：

- 對 `0x06014000` 的 read-watchpoint 命中 `T05rwatch:06014000`，停在 `0x0809959c`。
- 對同一位址的 write-watchpoint 命中 `T05watch:06014000`，停在 `0x080995a8`，對應 kernel 的 `str` 後續位置。

因此目前已取得一條較完整的 runtime 路徑：`EWRAM text buffer → AFEJ two-byte map → glyph index → EWRAM glyph object → 0x08099424/0x080995b0 → VRAM 0x06014000`。這確認了實際字型／bitmap VRAM sink；VRAM 中完整 glyph pool 的來源分區、tile stride、palette bank 及劇情／支援／事件資料表仍需另行建立 ledger。

### M1.5：ROM 指標來源到 EWRAM code-unit buffer

本切片追的是同一個已確認的 EWRAM buffer `0x02029404` 的 producer，而不是從靜態 Shift-JIS 命中反推腳本。新增的 `tools/capture_m15_producer.py` 只輸出位址、索引、雜湊、marker offset 與分支停止點；它透過 `core/gba/gdbstub_client.py` 連到自己啟動的 mGBA `2346` port，不寫 ROM，也不輸出完整 RAM／原文：

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tools/capture_m15_producer.py \
  --port 2346 --timeout 30 --branch-hits 2
```

在 loader 區域 `0x08013acc` 的 Thumb 反組譯中，`0x08013acc`／`0x08013ace` 是函式前的 literal/data halfword；實際 prologue entry 是 `0x08013ad0`。該函式把第一個參數存到 stack frame，取出 literal pointer table `0x080f635c`，作 `table + index * 4`，再把固定目的位址 literal `0x02029404` 傳給 `0x0800384c`。乾淨 AFEJ 啟動的 breakpoint receipt 如下：

| 觀測點 | 實測結果 |
| --- | --- |
| `0x08013b04` 歷史 stop（呼叫 BL 的第二 halfword） | `table_index=3087`、`table_entry=0x080f9398`、`r0=0x080f2256`、`r1=0x02029404`；位置後由 M1.7 證明不是合法 callsite |
| 同一歷史 stop 的 LR | `0x08002b06`；此值後由 M1.7 判定為錯誤 breakpoint 位置造成的 artifact，不作高階 caller provenance |
| `0x0800385e`（wrapper 的 `bx r2` 前） | `r0=0x080f2256`、`r1=0x02029404`、`r2=0x0300323c`（IWRAM worker） |
| `0x02029404` write-watchpoint | `T05watch:02029404;`；同次 stop 的 `r1=0x02029404`、`lr=0x08003863` |
| `0x08013b08`（copy 返回後） | 完整 buffer 的 SHA-256 `792667cef3da14699e533dd04573bb90c7f53a79546519d60a0c328023d5359f`；非零 byte `43`、最後非零 offset `42`、第一個後續零 byte offset `43` |

這條可重跑的資料流因此是：

```text
0x080f635c[index 3087] -> 0x080f2256
    -> 0x0800384c / 0x0300323c
    -> write-watchpoint 0x02029404
    -> return 0x08013b08
    -> renderer reads the same buffer
```

這是至少一條「ROM pointer table／ROM source pointer → EWRAM code-unit buffer」的執行期證明；但 `0x080f2256` 指向的 ROM bytes 尚未被證明是可直接讀取的腳本，現階段只確認它是被這個 loader 送入該 buffer 的 ROM 資料來源。其表示法、是否有壓縮／轉碼，以及 index 3087 所屬的遊戲資料類別仍是 provisional。

#### Terminator、控制 marker 與陰性結果

同一次 `0x08013b08` 後讀取的 buffer 不提交原始 bytes，只保留結構摘要：

- `0x01` 位於 buffer offset `8`；兩位元組 code-unit 序列在 marker 前後仍可見，故 `0x01` 不是這一條消費路徑上的普通 glyph code-unit。
- renderer 在 `0x08098c24` 讀取目前 byte；靜態分支把 `0x00`／`0x01` 這類 `<=1` 的值送往 `0x08098c78` 的非 glyph 路徑。動態 breakpoint 實測 `0x08098c78`：`r6=0x0202940c`（buffer+8）讀到 `0x01`，以及 `r6=0x0202942f`（buffer+43）讀到 `0x00`。
- offset `43` 是 payload 後第一個零 byte，與 renderer 的停止／非 glyph 分支一致；目前把它記為這個 buffer 的高信心 terminator 證據，不宣稱所有文本都只有這一種終止形式。
- `0x04` 在 renderer 有另一條「跳過一 byte」的靜態分支（約 `0x08098c2e`／`0x08098c32`），但本次完整 buffer 沒有觀察到 `0x04`；同樣沒有觀察到 `0xff`。因此 `0x04` 的意義仍是候選控制碼，不能寫成已確認換行。
- `0x01` 目前只證明會走非 glyph／物件處理分支；`0x08003e60` 的相關路徑會清除物件欄位，但尚未以跨場景或輸入停頓實驗區分換行、等待、結束或其他格式控制。不要把 `0x01` 翻成 newline。

本切片把「ROM 指標到 buffer 的 producer」提升為 confirmed，把「source encoding、完整 pointer table／事件表邊界、控制碼語義、可逆回插」保留為 provisional／unknown；沒有開始大批翻譯。

### M1.6：loader／worker 反組譯與 bounded opaque corpus

本切片把 M1.5 的單筆 runtime receipt 交叉提升為一個可重跑的有限 cohort；不把「看起來像指標」直接當成文本表，也不把 code-unit bytes 猜成 Unicode。

#### Loader、caller return 與 table boundary

`0x08013ad0` 的實際 Thumb prologue 可由下列指令語義重現：

```text
str r0,[r7]                         ; loader index input
ldr r0,[literal 0x0202a404]        ; last-index cache
cmp [r7], [0x0202a404]
ldr r0,[literal 0x080f635c]
lsls r1,[r7],#2
adds r0,r0,r1
ldr r1,[r0]                         ; table[index]
ldr r2,[literal 0x02029404]
mov r0,r1; mov r1,r2
bl 0x0800384c
str [r7],[0x0202a404]
```

這證明 entry 是 32-bit `table[index]`，不是從 source bytes 的範圍猜 index。新 receipt 另在 `0x08013ad0` 停止，實測 loader 的第一個參數就是 `3087`；之後在真正的 BL 起點 `0x08013b02` 讀到 stack frame index 仍是 `3087`，並得到 `0x080f635c + 3087*4 = 0x080f9398`、source `0x080f2256`、destination `0x02029404`。舊文所稱 `0x08013b04` 僅是該 BL 的第二個 halfword，已由 M1.7 更正。

對 `0x080f635c` 從 4-byte entry 逐項靜態掃描，index `0..3341` 都是 GBA ROM pointer；index `3342` 的 entry address 是 `0x080f9794`，值為 `0x32303032`，是第一個非 ROM pointer。因此本切片採用已證實的 bounded pointer-entry domain `[0, 3342)`；這是 table layout boundary，不把整個 domain 未經 runtime 分類成劇情、支援或資料表。

歷史 runtime 的 `lr=0x08002b06` 不能再作 return provenance：M1.7 證明當時停在 `0x08013b04` 這個 BL 第二 halfword。`0x08002b04` 仍是另一個 Thumb function（`push {r7,lr}` 後在 `0x08002b06` 配置 stack），其函式 body 到 return 沒有 `BL 0x08013ad0`；真正的 loader return LR 是 `0x08098b15`，可反推出 `0x08098b10`。這項修正取代原本「只記為 caller return LR」的 provisional 表述。

#### IWRAM worker 的 ROM 初始化與轉換語義

`0x0300323c` 的 IWRAM worker 是 ROM `[0x080006e4, 0x08000770)` 的 140-byte exact copy（最後一條 `bx lr` 位於 `0x0800076c`，literal 區從 `0x08000770` 開始）；兩段 code 的 SHA-256 都是 `94e4e735a873c5e51d113858d748d3a02010a16d23e54c7b4b0113f48fd0b7cc`。boot-time write-watchpoint 在 BIOS `CpuFastSet` 執行期間命中 `0x0300323c`，其 source/destination geometry 對應到 ROM `0x080006e4`；runtime function slot `0x03003780` 的值是 `0x0300323c`。因此 worker 不是未驗證的外部常數，而是 AFEJ 啟動時從 ROM 初始化到 IWRAM 的執行碼。

ARM worker 的實際流程是：從 `0x080f6354` root node 開始，以 source byte 的 bit 0、1、…、7 LSB-first 選 node halfword；`r4 = 0x080f300c + child_index*4` 後載入 node word。高位為 0 就繼續沿 tree，遇到高位為 1 的 leaf 時，先輸出 low byte；high byte 非零則再輸出第二 byte，只有單-byte leaf 的 low byte 為 `0x00` 才返回。輸出 leaf 後才把 `r4` 重設為 root，bitstream 會跨 flag byte 延續。這排除了單純 memcpy、BIOS LZ77 或未證明的 bytecode guess，確認目前 cohort 使用的是 custom bitwise tree expansion。

#### Cohort、extractor 與 no-op verifier

新增 `tools/extract_afej_m16.py`，預設處理相鄰且同一 loader/table 類型的 `index 3080..3095`（16 records）。每筆產生 stable `string_id=afej.ptr.NNNN`、table entry/source pointer provenance、compressed source span hash、固定 `0x400` EWRAM output hash、payload/buffer length、marker offsets，以及不套碼頁的 `code_unit`／`opaque_control_byte`／`terminator` tokens。`index 3080..3095` 每筆 decode 後的 source span 都精確接到下一個 pointer entry；這支持 bounded record boundary，但不宣稱它們已屬於哪一種遊戲內容分類。

本機產生的完整結構 corpus 是 ignored `research/afej-decoded.jsonl`，沒有放進 Git。它沒有 `source`／日文 Unicode 欄位，也沒有 FE7、FE8 或外部 TBL 猜碼；完整日文仍未輸出到提交路徑。tree inverse 有 1642 個唯一 leaf outputs，16/16 records 通過 decode→encode 的 compressed source byte-identical verifier。

index 3087 的 bounded 結果是 source span `39` bytes、EWRAM payload `44` bytes、固定 buffer `1024` bytes；新的獨立 mGBA/GDB receipt 以 loader-entry breakpoint、copy-wrapper breakpoint、`0x02029404` write-watchpoint 與 loader-return breakpoint 重跑，runtime output SHA-256 為 `792667cef3da14699e533dd04573bb90c7f53a79546519d60a0c328023d5359f`，與 extractor output hash 相等。runtime 的 logical terminator 是 offset `43`，`0x01` 是 offset `8`；這是 byte/hash equality，不是 Unicode 解碼或回插證明。

為確認 cohort 不是只靠一筆自然啟動資料，另在同一 loader-entry breakpoint 將第一參數安全覆寫成相鄰 index `3086`。它經同一個 `0x08013b02`／`0x0800385e`／`0x0300323c`／`0x02029404` 路徑完成，table entry `0x080f9394` → source `0x080f2241`，runtime buffer hash 是 `beef794ae3343fd335de75d6b481388734a65a0e36478755ada3a75f9376e11e`，logical terminator offset `31`、`0x01` offset `12`。這是 bounded same-caller/worker 交叉驗證；其本機 receipt 仍在 ignored `work/`，不提交 raw buffer。

#### Control marker corpus 與陰性結果

在 16 筆 payload（不把固定 buffer 的 zero-filled tail 計入）統計：`0x00` terminator `16` 筆、`0x01` opaque single-byte token 共 `9` 個、`0x04` `0` 個、`0xff` `0` 個，其他 single-byte opaque token `0` 個。這些統計與 worker leaf width、已知 renderer 的非 glyph branch 一致；它們仍不足以替 `0x01` 命名為換行、等待、結束或其他語義。此次沒有用兩個可達場景宣稱區分 `0x01`，因目前 bounded cohort 尚沒有第二個已證實的 renderer callsite／可觀察行為差異。

因此 M1.6 已證明「ROM table index → custom tree source expansion → EWRAM code-unit/control buffer」並建立可重跑 corpus；Unicode codepage、跨場景控制語義、各內容類別的 caller、完整 script coverage 與安全回插仍是下一個缺口。

### M1.7：高階 caller、正確 BL provenance 與第二場景陰性結果

本切片從 M1.6 的 loader entry `0x08013ad0` 往上追一層，並修正一個會污染 caller 判讀的 Thumb breakpoint 位置。新增的 `tools/trace_m17_callers.py` 重用 `core/gba/gdbstub_client.py`，只輸出靜態 callsite、寄存器／LR、table/source provenance、buffer／VRAM hash、marker offsets 與顯示寄存器；按鍵注入只在本機 mGBA 的 `KEYINPUT` read-watchpoint 上覆寫輪詢暫存器。

#### 靜態 callsite 與 `0x08002b04` 陰性結果

AFEJ ROM 的反組譯可逐指令重現以下關係：

```text
0x08098afc: push {r4,r5,r6,r7,lr}
0x08098b06: adds r7,r0,#0
0x08098b08: ldr  r1,[pc,#...]       ; 0x08691738
0x08098b0a: lsls r0,r7,#2
0x08098b0c: adds r0,r0,r1
0x08098b0e: ldr  r0,[r0]             ; caller_index_table[selector]
0x08098b10: bl   0x08013ad0
```

`0x08098b10` 的 ARM7TDMI 雙半字 Thumb BL halfword 是 `0xf77a, 0xffde`，解碼目標為 `0x08013ad0`，不是依位址鄰近猜測。ROM table `0x08691738` 的 selector `0..7` 靜態值為 `[3080, 3081, 3082, 3084, 3085, 3086, 3087, 3083]`；這是 selector→loader-index 證據，不把 selector 本身命名成章節、劇情或 UI ID。

loader 內呼叫 copy wrapper 的指令從 `0x08013b02` 開始，halfword `0xf7ef, 0xfea3` 解碼目標為 `0x0800384c`；`0x08013b04` 是同一條 ARM7TDMI 雙半字 Thumb BL 的第二個 halfword。M1.5／M1.6 舊 receipt 曾在 `0x08013b04` 設 breakpoint，因而看到 `lr=0x08002b06`；那不是可靠的高階 caller return provenance。現在的 M1.5／M1.6 工具已改用 `0x08013b02`。

`0x08002b04` 的實際函式開頭是：

```text
0x08002b04: push {r7,lr}
0x08002b06: sub  sp,#0x10
0x08002b08: mov  r7,sp
...
0x08002b78: add  sp,#0x10
0x08002b7a: pop  {r7}
0x08002b7c: pop  {r0}
0x08002b7e: bx   r0
```

截至這個函式的 return，反組譯沒有 `BL 0x08013ad0`；因此不能把 `0x08002b04` 命名為 loader caller。M1.7 的真實 caller 證據改由 `0x08098b10` 的 direct BL 與 runtime LR 交叉確認。

這個 output hash 與 M1.6 extractor 對 index 3087 的 hash 相等，仍只是 code-unit／control buffer byte equality，不是 Unicode 或回插證明。本次新 runtime 收據的 loader record 數為 `1`（index 3087）；M1.6 的 16 筆 `3080..3095` bounded corpus 維持既有範圍，沒有因為高階 selector table 的靜態鄰接值而擅自擴大內容分類。

#### 分類與控制碼邊界

- `0x080985d8` 的靜態參數搬運與 controlled LR 形成第二類 caller 證據；它只支持 `pointer_table_text_loader_path` 這個結構分類，不支持劇情、支援、章節事件、單位資料或選單的語義命名。

- confirmed：163 個合法 direct BL、`0x080985d8` 的 prologue/return 邊界、controlled `lr=0x080985f1` → `0x080985ec`、兩筆分欄的 table/source→EWRAM receipts。

- unknown：AFEJ Unicode/codepage、完整劇情／支援／事件／資料表 coverage、可逆 encode／ROM 回插。

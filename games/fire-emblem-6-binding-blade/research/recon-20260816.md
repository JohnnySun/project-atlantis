# AFEJ 唯讀偵察紀錄（2026-08-16）

## 邊界與當前結論

本紀錄只涉及 `games/fire-emblem-6-binding-blade/`。2026-08-16 已使用使用者提供的本機日版 ZIP 唯讀解出 `roms/base/AFEJ.gba`；ROM 與完整原文仍被 Git 忽略，未作提交。以下把本機 AFEJ 實測證據與尚未證實的候選分開記錄，不以公開 patch、完整解包或搜尋摘要替代。

候選資料代碼 `AFEJ` 已由 ROM 標頭 `0xAC..0xAF`、標頭補數與本機雜湊共同確認；它不代表其他區域或其他 revision。

## 專案內可重跑入口

```sh
python3 tools/recon_afej.py roms/base/AFEJ.gba --json-out work/afej-recon.json
```

該工具是結構掃描器，不是解碼器。它會：

- 解析 GBA 標頭並計算 CRC32、MD5、SHA-1、SHA-256。
- 搜尋少量標準 Shift-JIS UI 探針；零命中只能排除「直接存放這些探針」，不能證明沒有文本。
- 掃描 ROM 位址型 32-bit little-endian 值，列出連續指標候選；未經反組譯／執行期交叉驗證不得稱為字串表。
- 掃描 BIOS LZ77／Huffman／RLE 等標頭候選；標頭命中不是壓縮資料被文本使用的證據。
- 以 4bpp tile 窗口產生字形候選；必須再用畫面、VRAM、實際重複字形與 ROM 原 bytes 比對確認。

輸出報告放在 `work/`；它不應包含解出的日文原文。若後續解碼器產生原文表，檔名必須採 `research/afej-decoded.jsonl`，由 `.gitignore` 保護，不能加入 Git。

## 外部工程提供的偵察分區線索

`fireemblem6j` 的公開目錄把文本相關材料分成 `texts/events`、`texts/gamedata`、`texts/misc`、`texts/talks`、`texts/textdefs.txt` 與 `texts/texts.txt`；其 `data/` 另有 `text` 及 `systemlabels_data.h`。這些名稱足以安排本地 ROM 到位後的抽取覆蓋矩陣：劇情／事件、支援、資料表、系統標籤與圖像／介面文字分開驗證；它們不是本機 AFEJ 的地址或內容證明。

FEBuilder 的公開設定說明提到 `translate_textid`、TEXT table extension 與 Text Export。這表示 FEBuilder 的 Text ID／匯出層可作為對照工具，但不能先假定其 ID、表格邊界、碼頁或擴展行為就是日版原 ROM 的原生格式。M1 仍須以 AFEJ 的真實引用者、字串終止、字型讀取和未修改 round-trip 重新證明。

參考：[FE6 `texts/` 目錄](https://github.com/FireEmblemUniverse/fireemblem6j/tree/main/texts)、[FE6 `data/` 目錄](https://github.com/FireEmblemUniverse/fireemblem6j/tree/main/data)、[FEBuilder 設定資料結構說明](https://laqieer.github.io/dw.ngmansion.xyz/wiki/en/guide/febuildergba/the_config_data_structure_of_febuildergba_en.html)。

## Runtime：已確認的文字／字型消費路徑

### 輸入與觀測方法

- 使用自己啟動的 mGBA 0.10.5 進程與獨立 GDB stub port `2346`；未停止其他 session 的 mGBA，也未修改 ROM。
- GDB read-watchpoint 命中 `KEYINPUT` `0x04000130`，ROM Thumb 輪詢位於 `0x08001908`–`0x0800192e`，輸入處理函式為 `0x08001734`。以暫存器覆寫模擬按鍵只用於到達遊戲流程，沒有寫入 ROM。
- 初始 graphics 觀測另外命中 BIOS LZ77 wrapper `0x0809dcf0`；這證實 graphics 解壓呼叫存在，但目前不把它誤標成文本壓縮或字型來源。

### 文字 buffer 到 glyph object

這條路徑已在乾淨 AFEJ 啟動中命中，記錄的是位址、控制流程與工作記憶體，不提交日文原文：

1. ROM 內的兩位元組字元 map 位於 file offset `0x691644`，GBA address `0x08691644`。read-watchpoint 在執行 `ldrb` 後於 `0x080992e4` 停止；當時 `r0=0x02029404` 指向 EWRAM 文字 buffer，`r2=0x08691644` 指向 ROM map，`lr=0x0809931b`。
2. wrapper `0x08099314` 呼叫 `0x080992dc`。後者逐對比較兩個 byte，找到項目便回傳 glyph index，找不到則回傳 fallback；這是 runtime codepage lookup，而不是只靠靜態 Shift-JIS 命中推測。
3. 實際字元消費函式從 `0x08098c24` 讀取 `r6` 指向的 EWRAM buffer，並在 `0x08098c5c` 呼叫 map lookup。當次 `r6=0x02029404`、`r7=0x086917c0`。
4. 同一函式在 `0x08098c3c` 配置 glyph 渲染物件；`0x08098c60` 的 `strh` 將 lookup 結果寫入物件的 glyph 欄位。對 `object base=0x02023fb8` 的 `object+0x4a=0x02024002` 設 write-watchpoint，實際命中 `T05watch:02024002`；當次 glyph index 為 `0x43`，`r2=0x086916ca` 仍位於 map 區域。

因此目前可安全下的結論是：`EWRAM text buffer → AFEJ two-byte map → glyph index → EWRAM render object` 已證實。尚未把 glyph index 往後追到 4bpp bitmap 的 VRAM／OBJ tile 搬運，也尚未證實劇情、支援、事件及資料表的完整表格邊界；這些仍是 M1 待辦。

### 靜態與執行期的交叉界線

標準 Shift-JIS 相容 bytes 在多個 UI／字元資料候選處命中（例如 file offsets `0x3272e0`、`0x3272e8`、`0x336cf0`、`0x105b74`、`0x105b7c`），但這些命中本身不等於完整 codepage 或已定位的劇情表。真正提升為 confirmed 的證據是上面的 runtime map read、renderer call 與 glyph-field write；原文、OCR、完整解碼表與渲染 dump 仍只留本機 ignored research/work。

## 偵察原則

- 不把 FE6 套用黃金太陽的 Huffman、共用碼頁或 `{HH}` 控制碼假設。
- 「字形資料位置已找到」與「每個字形身分已確認」分開記錄；OCR 只能是候選證據。
- 任何使用既有英譯的資料只可作介面／欄位線索，不能作原文、專名或翻譯來源。
- 任何日文腳本、OCR 輸出、渲染圖與 ROM 讀值只留在本機 `research/`／`work/` 被忽略路徑；提交的研究筆記只保存方法、範圍、hash、offset 與短小消歧所需資訊。

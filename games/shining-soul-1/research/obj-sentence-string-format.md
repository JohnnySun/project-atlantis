# OBJ 句子字元代碼序列的儲存格式（session 8）

本檔案記錄第八輪偵察的結果：解出「職業を選んでください」這類完整句子的**字元代碼序列
本身**儲存在 ROM 何處、以何種格式編碼——這是第七輪明確標記為未解決的核心缺口（見
`research/obj-sentence-glyph-loader.md`「未解決：句子本身的儲存位置」一節）。分析結論，
不含遊戲原文大段抄錄，可安全提交。

## 摘要（先講結論）

1. **找到句子字元代碼陣列本身**：「職業を選んでください」的 10 個字元，以
   **NUL（`0x0000`）結尾的 16-bit 代碼陣列**形式，逐位元組原封不動存在 ROM file
   offset **`0x499b1a`**：
   ```
   0x028a 0x03eb 0x002e 0x030d 0x002f 0x003d 0x0009 0x003a 0x000c 0x0003 0x0000
   ```
   「色を選んでください」（顏色選擇畫面，9 個字元）存在 ROM file offset **`0x499b3e`**：
   ```
   0x028b 0x002e 0x030d 0x002f 0x003d 0x0009 0x003a 0x000c 0x0003 0x0000
   ```
2. **解碼公式**（16-bit 小端序代碼 → 字形）：
   ```
   category         = (code >> 8) & 0xF     ; 字型/字符池選擇器（0–15）
   glyph_entry_index = (code & 0xFF) - 1     ; 該池內的字符索引
   ```
   `category == 0` 對應假名（平假名／片假名主表），`category` 為其他值（本輪只實際觀察到
   2、3）對應漢字，用的是另一套（本輪未完整解出的）漢字定址系統——與第七輪「漢字不在主表
   `index*0x80` 定址規則內」的既有負面結果一致，這裡進一步確認漢字連字元代碼的「池」欄位
   都與假名不同，不是巧合。
3. **交叉驗證，兩個獨立畫面完全吻合**：兩句話共用的後綴「選んでください」（7 個字元）在
   兩處代碼陣列裡**逐一位元組完全相同**（`0x030d 0x002f 0x003d 0x0009 0x003a 0x000c
   0x0003`），且「を」的代碼（`0x002e`）也完全相同；唯一不同的只有各自專屬的開頭漢字
   （「職業」的 `0x028a 0x03eb` vs.「色」的單一漢字 `0x028b`，三者的 `category`／
   `glyph_entry_index` 彼此相鄰、合理落在同一個漢字池區段）。這是「同一套字元代碼系統，
   跨畫面共用同一份編碼表」的直接證據，不是各畫面各自的巧合。
4. **`category==0` 的 `glyph_entry_index` 與第七輪主字形表的定址完全自洽**：把七個
   假名代碼解出的 `glyph_entry_index`（45,46,60,8,57,11,2）與第七輪已知的五十音
   `char_idx`（を=44,ん=45,で=59,く=7,だ=56,さ=10,い=1）逐一比對，發現
   **`glyph_entry_index = char_idx + 1`** 恆成立——不是巧合的湊數字，這個 +1 偏移在
   本輪的即時暫存器追蹤裡也獨立出現過兩次（見下方「發現過程」的兩個中繼表），三處互相
   印證。

## 發現過程（由內而外，逐層往上找呼叫者）

第七輪已確認：ROM file offset `0x34d0`（`bl 0x8001154`）是「把單一字符 128 bytes
字形資料搬進 VRAM」的 enqueue 呼叫點，本輪從這裡開始，逐層往上找「是誰決定要傳哪個
字符」。

### 第一層：`0x34d0` 所在函式（file offset `0x3310`）的真正入口

第七輪只反組譯了 `0x34d0` 附近的迴圈本體，未定位函式本身的 `push`/`pop` 邊界。本輪
往回找到真正的函式進入點在 **file offset `0x3310`**（`push {r4,r5,r6,r7,lr}`），
確認這是一個共用的「依 (category, index) 具現化一組 sprite」通用函式——從進入點的
參數拆解可看到它接收 4 個暫存器參數＋2 個堆疊參數，其中一個堆疊參數（`r4` 在函式內部）
是一個「畫面描述結構」指標，透過連續兩層 PIC 風格的相對位移重新定位（`ldr r0,[r4,#4];
adds r0,r0,r4` 等），最終算出 `sb`（提供 sprite 數量與陣列基底）與一個「12-bytes-per-
entry」子表（用某個引數當索引，讀出一個 16-bit 值，再乘以 12，用來進一步位移
`sb`）——這一層本身仍不是字元代碼，是「畫面佈局」層級的間接定址，本輪未完全展開（非
本輪目標）。

### 第二層：對 `0x3310` 設中斷點，即時追蹤呼叫參數

用新增工具（本輪 `/tmp` 臨時腳本，方法已整理進 `trace_sentence_string_source.py`）
對 file offset `0x3310` 的函式入口設硬體中斷點，在職業選擇畫面每一輪重繪時攔截。
關鍵發現：呼叫者傳入的**第 4 個參數（`r3`）**，在 `lr=0x0800e929` 的呼叫序列裡，依序是

```
137, 234, 45, 12, 46, 60, 8, 57, 11, 2
```

**與「職業を選んでください」10 個字元逐一對應、順序完全一致**（`r1`＝固定
`0x8b`／`0x10` 兩種「類別」值，`r0` 是單純每次 +13 遞增的排版座標，`r2` 恆為 0）。
這是第一個確認「有一個逐字元遞增的整數序列」的直接證據，但當時還不知道 137/234/45/…
這些數字本身來自哪裡（是常數表？還是真的有一份逐字元的來源陣列？）。

### 第三層：`0x0800e929` 所在函式（file offset `0xe8bc`）——真正的字串走訪迴圈

反組譯 `lr=0x0800e929` 回推的呼叫點（file offset `0xe924`，`bl 0x8003310`）所在函式，
找到函式真正入口在 **file offset `0xe8bc`**（`push {r4,r5,r6,r7,lr}`），其主迴圈
（file offset `0xe8f0`–`0xe944`）結構是：

```
0xe8f0: (以 r2 = 讀到的 16-bit 值，做各種位元遮罩/移位)
  ...
  r0 = (r2 & 0xf00) >> 6        ; 取 bits 8–11，當成 4-byte 步幅索引
  r1 = *(pool_ptr_table + r0)   ; 查一張「類別→處理表」指標表
  r3 = (r2 & 0xff) - 1          ; 取低 8 位元，減 1
  ... 呼叫 0x8003310(r0=座標, r1=查表結果, r2=0, r3=剛算出的索引) ...
0xe928: r0 += 13（下個字排版座標，超界則換行）
0xe93e: r5 += 2                 ; 來源指標前進 2 bytes
0xe940: r2 = *(uint16_t*)r5      ; 讀下一個 16-bit 值
0xe942: if (r2 != 0) goto 0xe8f0 ; 非 0 就繼續，是 0 就結束迴圈
```

**這就是句子的真正走訪迴圈**：`r5` 是一個 16-bit 寬度、以 `0x0000` 結尾的陣列指標，
每次迭代讀一個 16-bit 值，拆成「類別（bits 8–11）」與「索引（bits 0–7，減 1）」兩部分，
分別當作 `r1`／`r3` 傳給下層的 sprite 具現化函式。函式入口處 `adds r5,r0,#0`
確認 `r5` 的初值就是**這個函式自己的第一個參數（`r0`）**——也就是說，只要找到「誰呼叫
`0xe8bc` 這個函式、傳了什麼 `r0`」，就能直接拿到字串指標本身。

### 第四層：對 `0xe8bc` 函式入口設中斷點，直接讀出字串指標與內容

對 file offset `0xe8bc` 設中斷點，在職業選擇畫面攔截到：

```
r0（字串指標）= 0x08499b1a
halfwords     = 0x028a 0x03eb 0x002e 0x030d 0x002f 0x003d
                0x0009 0x003a 0x000c 0x0003 0x0000
```

10 個非零值＋1 個 `0x0000` 終止符，恰好對應「職業を選んでください」的 10 個字元。
換到顏色選擇畫面（`navigate` 多按一次 A），同一個斷點攔截到**另一個位址**：

```
r0（字串指標）= 0x08499b3e
halfwords     = 0x028b 0x002e 0x030d 0x002f 0x003d 0x0009
                0x003a 0x000c 0x0003 0x0000
```

9 個非零值＋終止符，對應「色を選んでください」的 9 個字元。兩者共用的
「選んでください」尾段（`0x030d 0x002f 0x003d 0x0009 0x003a 0x000c 0x0003`）與
「を」（`0x002e`）逐位元組完全相同，只有開頭的漢字代碼不同（`0x028a 0x03eb`＝
「職業」二字 vs. `0x028b`＝「色」一字），這是本輪最強的交叉驗證——兩個完全獨立、分開
從乾淨開機重跑導覽找到的畫面，解出的共用子字串位元組完全一致。

## `category`／`glyph_entry_index` 欄位驗證

以「職業を選んでください」的 7 個假名（`category==0`）為例：

| 代碼 | category | glyph_entry_index (`code&0xff - 1`) | 對應字 | 第七輪已知 `char_idx`（五十音序） | 關係 |
| --- | --- | --- | --- | --- | --- |
| `0x002e` | 0 | 45 | を | 44 | `entry_index = char_idx + 1` |
| `0x002f` | 0 | 46 | ん | 45 | 同上 |
| `0x003d` | 0 | 60 | で | 59 | 同上 |
| `0x0009` | 0 | 8 | く | 7 | 同上 |
| `0x003a` | 0 | 57 | だ | 56 | 同上 |
| `0x000c` | 0 | 11 | さ | 10 | 同上 |
| `0x0003` | 0 | 2 | い | 1 | 同上 |

七點全部精確符合 `entry_index = char_idx + 1`，零例外。這個 `+1` 偏移量與本輪「發現
過程第二層」看到的 `r3 = (r2&0xff) - 1` 減法運算完全對應（代碼裡存的是
`char_idx+1+1`？不，代碼低 byte 本身＝`char_idx+2`？——這裡容易搞混，實際關係鏈是：
`raw_code_low_byte = glyph_entry_index + 1 = (char_idx+1) + 1 = char_idx + 2`，
即代碼低 byte 直接等於 `char_idx+2`，而不是 `char_idx` 本身。這個「+2」/「+1」的兩層
偏移目前判斷分別來自：(a) `entry_index vs. char_idx` 這一層在第七輪的字形描述池
（ROM `0x469f60 + char_idx*8`，本輪另外驗證過，見下方「附帶發現」）就已經是 +1；
(b) 字串代碼本身在這之上又多加了一層 +1（很可能是把 `0` 保留給某個特殊意義，例如「無
字符/透明」，讓有效字符從 1 開始編號，這是遊戲工程上很常見的慣例）。兩層偏移各自成立、
互不矛盾，只是解碼時要注意別搞混，本工具（`trace_sentence_string_source.py`）的
`decode_string()` 已經把兩層都算進去，直接輸出可比對的 `glyph_entry_index`。

漢字（`category` 2／3）的 `glyph_entry_index` 本輪只記錄數值（職=137、業=234、
色=138、選=12），未進一步解出其定址規則（是否也是 `char_idx+2`、以及漢字池的實際
ROM 位置），留給下一輪；`選` 的 `category=3` 與 `業` 相同、但 `glyph_entry_index`
差異極大（12 vs. 234），說明漢字的分類規則比假名複雜，不能假設同一 `category` 內部
也是線性排序。

## 附帶發現：字形描述池（ROM `0x469f60` 起，8 bytes/格）

在往上追呼叫鏈的過程中（第七輪的「發現 2」以外），本輪額外確認：`0x08001154`
enqueue 呼叫的來源指標（第七輪稱為 `r0`，本輪稱為 `ip`/`r12`），對於假名字符，
精確等於

```
descriptor_addr(char_idx) = 0x08469f60 + char_idx * 8
```

用同一批 7 個已知假名 `char_idx` 值驗證，零自由參數、7 點全部吻合（見下方「證據與
可重跑步驟」的 `trace_glyph_source_array.py` 輸出）。這是**第五張**獨立確認的 ROM
表——與第七輪確認的「字形像素資料主表」（`0x46abe4 + char_idx*0x80`）位置不同、
用途不同：`0x469f60` 這張是**每格 8 bytes 的 OAM 格式描述子**（包含已經算好的
tile-number 等欄位，直接餵給 BIOS 搬移用），`0x46abe4` 那張才是**實際的像素資料**。
兩張表都用同一個 `char_idx`（五十音序）定址，只是各自的 base 與 stride 不同
（`0x469f60`／`8 bytes` vs. `0x46abe4`／`0x80 bytes`），指向同一套字符集的不同
「切面」（描述子 vs. 像素）。

## 教訓（game-agnostic，值得留在 skill 而非只留在本遊戲文件）

- **「找到某個暫存器/呼叫參數是逐元素遞增/變化的整數序列」還不等於「找到了來源資料」**
  ——本輪第二層（`0x3310` 的 `r3` 引數＝137,234,45,…）已經看到一個「逐字元變化的
  整數序列」，如果在這裡就停下宣稱「找到了」，其實只是找到了序列**經過一次函式呼叫
  傳遞後的樣子**，真正的來源（ROM 裡實際的位元組）還在再往上一層的呼叫者手上。本輪
  能夠一路追到底，關鍵是**每次找到一個「看起來像是的」候選後，繼續問「這個值是誰
  算出來 / 從哪裡讀出來的」，直到找到一個函式的參數直接等於一段記憶體位址（而非
  某個暫存器運算的中間結果）為止**。
- **「對呼叫點設中斷點、讀暫存器」比「對記憶體位址設 watchpoint」更適合往上追呼叫鏈**
  ——第七輪已經對 VRAM 目的位址成功用過 watchpoint 技巧，但那只能告訴你「這一刻誰在
  寫這塊記憶體」，往上追「這個值本身是誰算出來的」時，watchpoint 會不斷命中同一段
  複製迴圈內部、很難跳到呼叫鏈的上一層；改成**對函式入口位址設中斷點**，每次命中
  時檢查暫存器參數與 `lr`（回傳位址，直接告訴你呼叫者在哪），是本輪真正逐層向上
  突破的關鍵技巧，值得记录成本 skill 通用的一條方法：**要找「資料的來源」，從已知
  的資料消費點開始，反覆「找到目前這層函式的入口與參數 → 從參數或 `lr` 判斷呼叫者
  在哪 → 對呼叫者的入口再設中斷點」，直到某一層的參數不再是「其他暫存器運算出來的
  值」而是「直接從一塊具名記憶體讀出來的位址／內容」為止**。
- **兩個共用子字串的獨立畫面互相印證，是比單一畫面「看起來合理」更有力的證據**——本輪
  能夠這麼有信心地宣稱已經解出格式，不只是因為公式在單一句子上「湊得出來」，而是因為
  完全獨立導覽到的第二個畫面，其共用尾段的位元組**逐一相同**，這種「同一份底層編碼、
  不同上層內容」的重複結構，是很難用巧合解釋的證據等級，值得在有餘力時主動找第二個
  例子驗證，而不是滿足於第一個「解出來了」的結果。

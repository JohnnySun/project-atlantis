# 存檔選擇畫面 BG 字型表：部分 codepage（第四輪偵察）

本檔案記錄第四輪偵察的結果：從存檔選擇畫面（save-file-select）的 BG2／BG3 tilemap
反查出的 tile-index → 字符對照表，以及在 ROM 中找到的、支撐整個 BG 文字渲染的
1024 格字型表本體。這是**分析結論**，不含任何遊戲原文大段抄錄，可安全提交。

## 方法

1. 用 `games/shining-soul-1/tools/navigate_and_dump.py` 透過 GDB 讀取 watchpoint
   ＋暫存器覆寫（沿用第三輪確認過的技巧）跳過標題畫面、選取單人模式，穩定停在
   存檔選擇畫面（`DISPCNT=0x1d40`，與第三輪記錄一致），並把 VRAM／調色盤／OAM
   dump 存成檔案。
2. 直接讀取 BG2（`screenbase 0xf000`，角色狀態欄）與 BG3（`screenbase 0xf800`，
   FILE 選格）的 32×32 tilemap 16-bit entry 陣列，取出每格的 tile-index（bits
   0–9）與 palette bank（bits 12–15）。
3. 對每個已知會顯示什麼文字的畫面位置（已由 `research/save-select-screen-bg2-
   char-stats-render.png`／`bg3-file-slots-render.png` 等既有渲染圖與本輪重新
   渲染的 `save-select-bg2-fresh-render.png`／`bg3-fresh-render.png` 確認過），
   把對應的 tile-index 個別用正確 palette bank 渲染成小圖核對，而不是用 OCR 或
   統計投票——這批文字的正確答案本來就已知（「FILE 1」「SELECT」「エリア」等），
   所以可以直接建立 ground-truth 對照，不需要猜。
4. 找到多個 tile-index 之後，對其中幾個乾淨、有信心的候選做 ROM 全域精確位元組
   搜尋，確認它們的原始資料位置，發現全部落在同一段 ROM 範圍、且與 tile-index
   有固定的線性關係（`ROM 位址 = 0x1398e8 + tile_index * 32`）——這帶出了下面
   「重大結構性發現」一節。

## 重大結構性發現：BG 字型表本體位置已確認

- **ROM file offset `0x1398e8`** 開始，是一張 **1024 格**（0–1023，剛好是 4bpp
  BG tilemap entry 的 tile-number 欄位能定址的完整範圍：10 bits）、每格 32
  bytes（4bpp、8×8px）的字型表，總長度 `0x8000`（32,768 bytes），結束於 ROM
  file offset `0x1418e8`。
- **已用窮舉逐格比對確認**：存檔選擇畫面實際載入的 VRAM charbase `0x0`
  （`0x06000000`）內容，與這段 ROM 範圍**完全逐位元組相同**，比對範圍是全部
  1024 格（tile-index 0–1023 每一格都比對），第一個不相符的位置剛好落在
  **tile-index 1024**——也就是 10-bit tile-number 欄位能表示的最大範圍邊界，
  不是提早就分歧。這不是巧合式的部分匹配，是整個可定址範圍的完整覆蓋。
  可用 `games/shining-soul-1/tools/extract_bg_fonttable.py --verify-against
  <vram.bin>` 重跑這個驗證（見下方指令）。
- 這 1024 格裡，只有 **tile-index 0–227**（168 格非全零）實際畫了東西，
  228–1023 在這份 ROM 拷貝裡全部是 `0x00` 填充（空白／未使用）。
- **意義**：因為 BG tilemap entry 的 tile-number 欄位直接定址進這張表，
  tile-index 本身在 BG 文字渲染這條路徑上**就是字符代碼**——不存在另一層
  「字符代碼 → tile-index」的間接對照表需要另外去找；這張表本身就是
  codepage（至少對 BG 渲染路徑而言）。
- 這張表與第二輪確認的 OBJ 字型資料（ROM `0x62AA44`–`0x62B8E4`，標題／模式選擇
  畫面的精靈字型）**是兩張不同的表，位置完全不同**——目前確認遊戲裡至少有
  兩套獨立的字型系統（一套服務 BG 渲染、一套服務 OBJ 渲染），對話文字究竟用
  哪一套（或第三套）仍未知。

重跑指令：
```sh
# 擷取存檔選擇畫面的 VRAM／調色盤／OAM dump
/usr/bin/python3 games/shining-soul-1/tools/navigate_and_dump.py --out-dir /tmp/ss1_dump

# 擷取＋驗證＋渲染 ROM 裡的 1024 格字型表
/usr/bin/python3 games/shining-soul-1/tools/extract_bg_fonttable.py \
  games/shining-soul-1/roms/base/Shining_Soul_JP_AHUJ8P.gba \
  --out-bin /tmp/fonttable.bin --out-png /tmp/fonttable.png \
  --palette /tmp/ss1_dump/03_save_select.pal.bin \
  --verify-against /tmp/ss1_dump/03_save_select.vram.bin
# 預期輸出：first mismatching tile = None（1024 格全部比對通過）
```

## 部分 codepage（confirmed vs. 未確認，誠實分級）

字型是**窄體壓縮字型**：多數 Latin 字母是「兩個半形字元塞進一格 8×8 tile」
（例如一格畫 "F" + "I"），只有少數情況是一格一個完整字元（片假名、部分數字、
單一收尾字母）。這代表嚴格的「一個 tile-index 對一個字符」假設**不成立**，
下表照實際情況記錄「這個 tile-index 渲染出什麼」，並標注是否為 packed（一格
兩字）。

## 未解／已知限制

- **「SELECT」四格具體字母邊界未解**：tile 46/47/48/49 合起來顯示「SELECT」
  （6 個字母），但因為底圖是一個帶圓角的實心色塊按鈕（而非單純字母排列），
  無法乾淨切出「每格對應哪 1–2 個字母」，只能確認這 4 個 tile-index 合起來
  代表整個「SELECT」單字，不建議在沒有進一步證據前把它拆成單字母對照表。
- **項目 1（是否為系統通用 codepage，還是單畫面美術表）：本輪未能完成跨畫面
  比對**——目前只成功穩定停在「有 BG2／BG3 內容」的存檔選擇畫面；已重新造訪
  的標題／模式選擇畫面只用 BG1＋OBJ（`DISPCNT=0x1240`），不啟用 BG2／BG3，
  沒有機會比對「同一組字符在另一個畫面是否引用同一個 tile-index」。**畫面內
  部**已有一個直接證據支持是可重用字型（tile 112 的「DE」被 DEF／DEX 兩個
  獨立標籤引用同一個 index），但這只是同一畫面內的證據，不是跨畫面證據。
  下一輪如果能推進到 ROADMAP／README 建議的「角色建立」畫面（低信心判讀
  tile 96–108 疑似其 UI 文字已經在這張表裡），會是很好的跨畫面驗證機會。
- **對話文字系統仍未定位**：這整張表（無論 BG 或 OBJ 版本）目前只證實用於
  UI／選單／按鍵提示等固定短字串，沒有 hiragana、沒有漢字——不能假設它
  也是大量對話文字使用的系統；量體差異巨大（UI 提示字 vs. 整段劇情對白）
  很可能走完全不同的資料結構（例如指標表＋壓縮字串），這部分仍是未解問題，
  與第一～三輪的既有負面結果（沒找到指標表、Shift-JIS 直接掃描落空）並不
  衝突，只是這次的正面結果還沒觸及那個層面。
- 字元數統計（僅計入「高信心」＋「中信心」兩級，且 packed tile 依其渲染出的
  相異字符數計數，不含尚待核對的「低信心」項目、不含純圖示）：約 **32 個
  相異字符**——片假名不重複字有 **13 個**：エ・リ・ア・ケ・ッ・テ・イ・デ・
  ー・タ・ク・モ・ド・ル（「エリア」「ケッテイ」「データクリア」「モドル」
  四個標籤的不重複假名集合，含長音符「ー」；此數字已核對過，若之後改動上表
  請同步更新這裡，避免兩處不同步）；其餘為 Latin 字母／數字：SELECT／FILE／
  PAGE／ATK／DEF／DEX／STR／VIT／INT／Lv 涉及的不重複字母＋句點；數字 1–4
  兩種樣式。這已經達到、甚至略微超過本輪原訂「20–30 個字符」的目標範圍，
  但仍是很小的一張表，遠不足以涵蓋任何實際對話或選單以外的文字。

## 補充發現：BG2 的 tilemap 本身（非字型表）也有一部分是 ROM 內的靜態拷貝

除了字型表（tile-index→點陣圖）之外，另外檢查了 tilemap 本身（screenblock 的
16-bit tile-index 陣列）是否也整段以固定內容存在 ROM 裡（工作項目 2 的「反向表」
情境）。結果**因畫面而異**：

- **BG2**（角色狀態欄，screenbase `0xf000`）：從 tilemap byte offset 64（也就是
  第 2 列，`Lv.`／`エリア`／`ATK`／`DEF`… 那幾列開始的位置）起，有 **202 bytes
  連續逐位元組相同**的內容存在 ROM file offset `0x517d8`——這代表 BG2 這幾列
  UI 標籤的 tile-index 排列本身也是像字型表一樣整段從 ROM 拷貝過來的靜態版面，
  不是程式在執行期逐格計算出來的。
- **BG3**（FILE 選格，screenbase `0xf800`）：對前 20 列逐列在 ROM 內做精確搜尋，
  **完全找不到**任何一列的 64-byte 內容整段存在 ROM 裡。合理解釋是 BG3 的四個
  選格版面高度重複（四個框幾乎一樣，只有數字 1/2/3/4 不同），比較可能是程式
  用一個迴圈、以框線樣板＋當前迭代的數字 tile-index 組出來的，而不是四份各自
  獨立存放的靜態版面——但這只是根據「靜態搜尋找不到」推出的合理猜測，**沒有
  直接證據**（例如還沒有對 `0x0600f800` 設寫入 watchpoint 去實際捕捉是哪段
  程式碼、用什麼邏輯寫入這塊 tilemap）。下一輪如果要繼續往這個方向查，這是
  具體可執行的下一步：對 BG3 的 VRAM 位址設寫入 watchpoint，比對 BG2（應該
  幾乎不會再命中，因為是開機時期一次性搬移）與 BG3（如果真的是迴圈組版，
  應該會在畫面出現前看到多次規律的寫入）的行為差異。

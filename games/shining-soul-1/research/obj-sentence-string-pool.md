# 靜態掃描升級：從「兩個已知句子」到「可枚舉的字串池」（第九輪偵察）

本檔案記錄第九輪偵察的結果：把第八輪解出的字串格式（NUL 結尾 16-bit 代碼陣列，
`category`／`glyph_entry_index` 兩欄位）當成**結構特徵**做全 ROM 靜態掃描，取代逐一
用模擬器追出每個字串的做法。分析結論，只列少量抽樣文字供人工核對格式判讀是否合理，
不是大段原文抄錄，可安全提交。

## 摘要（先講結論）

1. **格式特徵掃描本身確認可行，但單獨使用雜訊極大**：對整個 ROM 已使用範圍
   （`0x000000`–`0x660000`）做「NUL 結尾、`category` 落在小範圍、長度 ≥3」的原始
   結構掃描，`min-codes=4` 時命中 5,823 個候選，其中信心度排序最高的一批幾乎全是
   週期性／等差數列式的假名序列（例如「かくかけかこかさ…」整段重複），是圖形／
   調色盤／其他表格資料湊巧滿足位元組文法的假陽性——與第一輪 Shift-JIS 結構掃描
   的教訓完全一致（見 `README.md`「當前進度」一節）。
2. **重大結構發現：真正的字串不是孤立存在，而是排成連續的「字串池」**：核對第八輪
   已知的兩個句子（`0x499b1a`／`0x499b3e`）在 ROM 裡的鄰接位元組後發現，每個字串
   前面固定有一個小的標頭欄位，字串結束（`0x0000`）後留有若干個零填充 halfword，
   緊接著就是下一個字串的標頭——是一段緊密排列的**字串池**，不是散落各處、需要指標
   表定位的資料。標頭有兩種觀察到的形狀：
   - 純標頭：`[u16 marker]`，`marker` 值＝這個條目要連續讀幾個 NUL 結尾的代碼陣列
     （即「幾行」），本輪觀察到 1–8。
   - 帶 id 的標頭：`[u16 id][u16 type≈0x10][u16 0][u16 0][u16 marker]`，`id`
     看起來像是訊息／群組編號（觀察到同一個 `id` 連續出現兩次，各自一行，猜測是
     「每個 id 有兩種措辭變體」，常見於 RPG 隨機台詞，但只在一小段範圍驗證過，
     未系統性確認）。
3. **用「標頭＋內容＋終止碼」鏈式驗證取代單一 NUL-run 判準，大幅降低假陽性**：真正
   的字串池會連續產生一串合法條目（本輪最長鏈到 108 個條目），偶然的位元組雜訊
   幾乎不會連續湊出這種鏈——多數假陽性只能湊出 1–2 個條目就斷鏈。要求「連續 ≥2–3
   個合法條目」把假陽性壓到可以人工抽樣核對的程度，見下方「方法」。
4. **找到兩個高密度、高信心的真實文字群聚區**（都經過人工抽樣核對、非只看統計數字）：
   - **對話／提示句池，ROM `0x499a04` 起**（第八輪已知的兩個句子就位於此池內部）：
     在 `0x499000`–`0x500000` 這 `0x7000` bytes 範圍內，本輪的鏈式掃描＋可讀性篩選
     （見下方方法）找到 182 個獨立字串池、620 個條目、共 2,150 行，抽樣核對數十條
     全部是文法通順、可辨識的日文（例句見下）。
   - **怪物／敵人名稱表，ROM `0x460b78` 起**：與第七輪確認的 OBJ 主字形表
     （`0x46abe4`）同在 `0x46xxxx` 這個 64 KiB 區段內、但位址在其之前，找到 109 個
     字串池、242 個條目、共 487 行，抽樣核對確認是一批片假名怪物名稱（例：
     ゴブリン、ホブゴブリン、ゴブリンキング、スケルトンメイジ、アイスゴーレム、
     オークソルジャー、オークマスター、ダークナイト、ダークメイジ、マスター
     メイジ、ルーンナイト、シルバーナイト、ミストデーモン、イビルクラウド）。
   - ROM 其餘範圍套用同一套鏈式＋可讀性篩選後仍有 208 個池、504 個條目通過篩選，
     抽樣核對後**判斷幾乎全是假陽性**（雜訊資料湊巧滿足標頭／終止碼文法但內容不
     成文），詳見「假陽性樣本」一節——**篩選後的候選數量不代表信心度，仍需人工
     抽樣**，這點延續第一輪以來的既有教訓，本輪只是再次驗證。
5. **沒有找到指向這個池的指標表**：對三個已知池內位址（`0x08499b1a`、
   `0x08499b3e`、`0x08499a04`）在整個 ROM 做精確的 4-byte 與 3-byte（24-bit 偏移）
   小端序位元組序列搜尋，**全部零命中**——與第八輪「表基底常數 literal pool 搜尋」
   的既有負面結果方向一致。**但這不影響可用性**：因為字串是連續排列、每筆都自帶
   終止碼與（多數情況下）下一筆的位置就緊接在後，只要有一個池的起始位址，就能
   完整走訪整個池，不需要指標表——這是本輪「找到指標表」這個任務目標的替代解法，
   誠實記錄不是完全等價（沒有從程式碼側證實有一個統一的「訊息 ID → 池內位址」
   查表機制，只是外部觀察到資料佈局本身可枚舉）。
6. **`category` 欄位的實際取值範圍比第八輪記錄的更廣**：第八輪兩個已知句子只出現過
   `category` 0／2／3；本輪在字串池裡看到 0–15 全部出現過（`extract_string_pool.py`
   不限制 category，因此能忠實呈現這一點）。這代表 `category` 更可能是一個完整的
   4-bit 字型／資料池選擇器，而非只有「假名／兩種漢字」三種——本輪除了 0（含新增的
   片假名／促音猜測，見下）外，其餘 1、2–15 的字形定址規則**全部仍未解出**，只是
   如實記錄「這些代碼確實存在、會被使用」，不是新的定址成果。

## 方法

### `scan_sentence_strings.py`（新增）：單純結構特徵掃描，供對照基準

按第八輪公式 `category=(code>>8)&0xF`、`glyph_entry_index=(code&0xFF)-1` 解碼，
在 halfword 對齊位置找「≥3 個合法代碼＋`0x0000` 終止碼」的游程。用已知的兩個句子
位址驗證過解碼邏輯正確（見下方「驗證」）。**單獨使用時全 ROM 掃描雜訊極大**（見
上方摘要第 1 點），因此本輪主要把它當函式庫用（`decode_code`／`render_code`），
真正的發現工具是下面兩支。

### `extract_string_pool.py`（新增）：從已知位址走訪整個池

給定一個池起點，反覆解析「標頭→N 行 NUL 結尾代碼陣列→零填充→下一個標頭」，直到
標頭不再合法為止。同時支援上述兩種標頭形狀（純 `marker` 與 `id`-前綴）。

### `scan_string_pools.py`（新增）：全 ROM 鏈式掃描

在每個 halfword 對齊位置嘗試用 `extract_string_pool.py` 的走訪邏輯起頭，只有連續
成功解析出 ≥`--min-chain` 個條目才算命中一個池（預設 3）。這比單一 NUL-run 特徵
精確得多，但仍會在別的規律性資料（例如下面「假陽性樣本」提到的週期性假名表）上
連續湊出短鏈——本輪額外用「每行平均代碼數 ≥2.5」＋「`category==0` 代碼落在已知
假名／片假名範圍的比例」兩個可讀性指標做二次篩選，篩選後仍要人工抽樣核對（本輪
確實對每個高信心區間都抽樣核對過，見下方樣本），不是只看篩選後的數字就採信。

## 驗證：對照第八輪已知的兩個句子

```
$ python3 games/shining-soul-1/tools/scan_sentence_strings.py \
    games/shining-soul-1/roms/base/Shining_Soul_JP_AHUJ8P.gba \
    --start 0x499b00 --end 0x499b60 --min-codes 3 --dump-all
0x499b18  len= 11  ...  [g0][c2:137][c3:234]を[c3:12]んでください
0x499b3c  len= 10  ...  [g0][c2:138]を[c3:12]んでください
```

`[c2:137]`／`[c3:234]` 對應第八輪已知「職」＝137/cat2、「業」＝234/cat3；「を選んで
ください」全部正確解出（本輪渲染函式新增了片假名，見下，故「フ」「ドラゴン」等
片假名詞在後面的樣本裡能直接顯示，不再只是 `[g#]`）。掃描起點比已知字串起點早
2 bytes（多出的 `[g0]`），追查後確認是**每個字串固定的標頭欄位**（見上方發現 2），
不是解碼錯誤——這正是本輪找到字串池結構的起點，見下方「發現過程」。

## 發現過程：從「多出兩個位元組」到整個字串池

逐位元組核對 `0x499b00`–`0x499b70`（見下，僅節錄關鍵位置，非大段原文）：

```
0x499b16: 0x0000   <- 上一句「…ください」的終止碼
0x499b18: 0x0001   <- 新句子的標頭（marker=1，讀 1 行）
0x499b1a: 0x028a   <- 第八輪已知「職」的位置——與 marker 剛好差 2 bytes
  ...（職業を選んでください，10 字）...
0x499b2e: 0x0000   <- 終止碼
0x499b30-0x499b3a: 全 0（零填充，6 halfwords）
0x499b3c: 0x0001   <- 下一句的標頭
0x499b3e: 0x028b   <- 第八輪已知「色」的位置
  ...（色を選んでください，9 字）...
0x499b50: 0x0000
0x499b52-0x499b5a: 全 0（5 halfwords）
0x499b5c: 0x0001   <- 再下一句的標頭（本輪之前完全未知的第三句）
0x499b5e: 0x0303 0x0131 0x002e 0x0329 0x011a 0x000d 0x0014 0x0009 0x003a 0x000c 0x0003
  0x499b74: 0x0000
```

第三句（`0x499b5e`）解碼後是 `[c3:2][c1:48]を[c3:40][c1:25]してください`——含兩個
全新出現的 category（1、3 另一個 index），`を`／`してください`部分完全可讀，是
「請…」句式的另一個實例，直接證實這確實是同一套系統的另一個句子，不是巧合。

再往下（`0x499b80` 起）出現 `marker=2` 的條目：兩個 NUL 結尾陣列背靠背、中間沒有
零填充，各自獨立解碼成通順文字片段——這是「`marker` 值＝這個條目有幾行」這個假設
的直接證據（見上方摘要第 2 點）。往前追（`0x499a48` 附近）與往後追（`0x49a7f0`
附近）都持續看到同一種標頭／終止碼／零填充的重複結構，最終確認這是一段連續延伸
超過 3,400 bytes（僅 `0x499a04`–`0x49a918` 這一段，池的完整範圍見上方摘要）的池。

`0x49a7f0` 之後標頭形狀變成帶 4-halfword 前綴的版本（`[id][0x0010][0][0][marker]`），
`id` 依序觀察到 `9,9,10,10,11,11`——每個 id 恰好連續出現兩次，內容各自是一句完整
但不同措辭的台詞（例如 id=9 的兩行分別是「いらっしゃい、なにか買うのか？」與
「また来てくれよな！」這類招呼語與道別語的組合，符合店員 NPC 兩句對話的猜測，
但**這個「id＝訊息群組、每組兩種措辭」的解讀本輪只到觀察層級，未追蹤程式碼側
是否真的有一個依 id 查表的機制**，如實記錄為推測而非確認結論。

## 假陽性樣本（誠實記錄，篩選後仍會出現）

- `0x4d0bd6`、`0x4c224c`、`0x4ca7a8`、`0x4cbec0`、`0x4cc2e8`、`0x4cc710` 等多個
  位址（`0x4b0000`–`0x4d0000` 一帶）都解碼出**完整重複的五十音／片假名順序字串**
  （例如 `うおうかうきうくうけう…`，把整套假名依序念一遍），且部分位址內容逐位元組
  完全相同——這明顯不是對話，可能是遊戲內部某種「假名順序核對表」或與輸入法／
  排序相關的資料，恰好滿足本輪的標頭／終止碼文法。這批已被人工排除，不計入上方
  「怪物名稱表」與「對話池」的信心統計，但仍計入全 ROM 掃描的原始候選數，供下次
  校準篩選門檻參考。
- `0x0f6c58`、`0x0f7adc`、`0x0f7e24` 等（`0x0f0000` 一帶）解碼出大量 `[c#:N]`
  組合、`category` 分佈在 1–15 全範圍、幾乎沒有可讀假名／片假名字——研判是某種
  數值／參數表（大小接近整齊，`category` 分佈太均勻不像文字）而非文字，同樣人工
  排除。
- `0x05xxxx`、`0x2bxxxx`、`0x63xxxx`、`0x54xxxx` 等零散位置的短鏈（2–4 條目）
  抽樣核對後內容破碎、不成文法，判斷是雜訊。

## 渲染器新增字符（低信心，供人工核對用，非新增 codepage 條目）

`scan_sentence_strings.py` 的 `render_code()` 本輪新增兩種解碼分支，**僅用於讓
掃描輸出更容易人工判讀是否像真文字**，不是新確認的 codepage：

- 片假名（`char_idx` 80–150）：假設與第七輪已知「片假名緊接在平假名後、同一順序」
  的敘述完全成立，套用同一份 71 字順序表。本輪抽樣核對出的多個片假名詞（アイテム、
  ドラゴン、ゴブリン 系列等）內部自洽、無不合理字元，是間接支持證據，但**未像
  第七輪平假名那樣做零自由參數的獨立位址交叉驗證**，信心等級低於已確認的平假名表。
- `char_idx==79`＝「っ」（促音）：僅由「さ+[79]+き」在真實詞「さっき」（剛才）
  裡的唯一一次出現支持，`char_idx==72`＝「ゃ」由「いらっし+[72]+い」在「いらっしゃい」
  （歡迎光臨）裡的唯一一次出現支持——**都只有單一資料點**，如實標記低信心，
  不建議直接當作已確認的 codepage 條目使用。

## 未解決（誠實記錄，供下一輪）

1. **多數 `category` 值（1、4–15）的字形定址規則完全未解**——本輪只是觀察到這些
   代碼在真實字串資料裡大量出現，沒有嘗試定位它們對應的字形表或定址公式，範圍
   遠大於第八輪已知的 `category` 2／3（漢字）。
2. **`id`-前綴標頭裡 `id` 欄位的確切語意未驗證**——只是觀察到「同一 id 連續出現
   兩次、各一行」這個表面規律，沒有追蹤程式碼側是否真有一個依 id 查表或播放
   對應語音／立繪的機制。
3. **對話池的完整邊界未窮盡**——本輪重點驗證的是 `0x499000`–`0x500000` 這個
   `0x7000` bytes 高密度區間，但全 ROM 掃描顯示 `0x4a0000`–`0x4f8000` 一帶仍有
   零星較短的合格鏈（見上方「對話池」數字，182 個池分散在整個 `0x499000`–
   `0x500000` 範圍內，不是完全連續的單一區塊），這代表對話池內部可能還穿插其他
   非文字資料（例如控制碼、分頁資訊），本輪沒有進一步刻劃這個穿插結構。
4. **馬達／怪物名稱表往 `0x462000` 之後品質明顯下降**（見「方法」抽樣結果），
   代表這張表的真實範圍可能比 `109 個池` 的原始統計要窄，需要下一輪更精細地
   劃出邊界，而不是直接引用本輪的粗篩數字。
5. **`marker` 上限（本輪硬編碼 8）是否為真實上限未驗證**——只是觀察值，如果真實
   格式支援更大的行數，本輪的掃描會在遇到更長訊息時提早誤判池已結束。

## 教訓（game-agnostic）

- **已知的兩個真實範例，其「鄰近位元組」本身就值得逐一核對，不要只驗證已知範圍
  內的解碼正確就停手**——本輪最大的突破（字串池結構）完全來自於「掃描起點比
  已知字串早了 2 bytes」這個意料之外的小差異，如果當時只滿足於「解碼出來的內容
  對得上已知句子」就結束，會完全錯過這個標頭欄位、進而錯過整個可枚舉字串池的
  發現。查資料格式時，已知錨點的**前後緊鄰位元組**是免費的額外資訊，值得順手
  核對。
- **「連續多次成功」比「單次符合特徵」更能過濾假陽性**——單一 NUL-run 特徵在
  全 ROM 尺度下雜訊多到無法直接使用（5,823 個候選），但「連續 ≥3 個合法條目
  無縫銜接」的鏈式判準把命中數壓到 499 個、其中多數還能再用可讀性指標二次篩選，
  這個「要求同一結構連續重複」的技巧本身是通用的，值得記錄：**任何「格式特徵」
  掃描，如果目標資料本身是以陣列/表格形式連續排列的，要求連續命中比單點命中的
  過濾力強得多**。
- **結構掃描篩選後的數字依然只是候選，不是結論**——本輪即使套用了鏈式判準＋
  可讀性指標兩層篩選，`0x460000`–`0x470000` 範圍內仍混有明顯劣化的區段
  （`0x462000` 之後），`0x4b0000`–`0x4d0000` 一帶的週期性假名表更是完全通過了
  篩選卻不是文字——這些都要靠人工抽樣渲染／閱讀才能發現，任何自動化指標都只能
  降低人工核對的工作量，不能取代它。

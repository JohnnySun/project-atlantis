# OBJ 句子渲染機制：主字形表（0x46abe4 起）＋共用單字元繪製迴圈（session 7）

本檔案記錄第七輪偵察的結果：解出職業選擇畫面「職業を選んでください」這類 **OBJ（sprite）
渲染完整句子**背後的定址機制——這是先前六輪都只解出 BG／選單用字型表（`0x1398e8`、
`0x1316e8`）之後，第一次找到用於實際句子（比 UI 短標籤資訊量更大）的字形系統。分析結論，
不含遊戲原文大段抄錄，可安全提交。

## 摘要（先講結論）

1. **找到並靜態驗證了一張全新的「主字形表」**：ROM file offset `0x46abe4` 起，每格
   `0x80`（128 bytes＝4 個 32-bytes 4bpp tile＝16×16px 一個字符），**單一線性索引**依序
   排列：平假名清音＋濁音＋半濁音（index 0–70，五十音順）、小字假名（71–79）、片假名
   （約 80–159，同樣順序＋小字）、符號（約 160–176）、全形括號、Latin 大寫 A–Z、小寫
   a–z、數字 0–9、以及結尾若干符號（音符、閃電、問號等，到至少 index 259）。**這是目前
   為止在本遊戲找到規模最大、字符集最完整的一張字型表**，遠超過先前兩張 BG 表（各自只有
   32／71 個字符）。已用 `extract_obj_kana_fonttable.py` 渲染整段（含逐格 index 標註）
   人工核對，圖樣清晰可讀，見下方「證據與可重跑步驟」。
2. **公式已用 7 個獨立點（を、ん、で、く、だ、さ、い 這 7 個平假名的已知 ROM 位址，session
   6 逆向工程找到的）精確驗證，零自由參數**：`glyph_rom_offset(index) = 0x46abe4 +
   index * 0x80`，index＝該字符在標準五十音順序中的位置。
3. **找到並即時追蹤確認了單字元繪製的完整呼叫鏈**：
   - 每個字符的 128 bytes 字形資料透過**單次** BIOS `CpuSet`／`CpuFastSet`（`svc`）搬移
     指令，從 ROM 該字符的位址整批拷貝到 VRAM 對應 OBJ tile 槽位——不是逐位元組手動迴圈，
     也沒有壓縮（與先前確認的 UI／選單字型資料模式一致）。
   - 這個 BIOS 呼叫是透過 ROM file offset `0x1154`（`0x08001154`）這個佇列「push」函式
     enqueue 的——**這正是第三輪偵察測試過、當時因為只在標題畫面等閒置畫面攔截、被判定
     「否定」的候選函式**；本輪改成在存檔選擇→職業選擇這個真正觸發字型載入的畫面切換
     瞬間攔截，第一次證實它確實就是字型（也是所有 OBJ 繪圖）的正確 enqueue 路徑。
   - **唯一的呼叫者**：ROM file offset `0x34d0`（`bl 0x8001154`，回傳位址 `0x080034d4`，
     GDB 讀出的 `lr` 因 THUMB interworking bit 顯示為 `0x080034d5`）。連續攔截約 680 次
     命中，**每一次 `lr` 都是同一個值**——這代表整個職業選擇畫面上會畫出的所有 OBJ
     圖像（角色圖示、「剣士」職業名稱標籤、完整句子「職業を選んでください」共 10 字）
     全部經過同一個共用的、逐一走訪「本畫面要畫的每一格 sprite」清單的迴圈，每格呼叫一次
     同一段程式碼——這是「真正的、可重用的文字/圖塊渲染系統」而非「每個畫面各自手刻
     blit」的直接、高信心證據，正是本輪任務要驗證的核心問題。
4. **句子的位元組編碼本身仍未定位（誠實記錄的負面結果，見下）**：雖然找到了「index→字形
   位址」的算式，也找到了「誰呼叫 BIOS 搬移」，但「哪裡儲存了『這個畫面要畫職/業/を/選/
   ん/で/く/だ/さ/い 這 10 個字』這件事本身（例如一個 10-byte 的字元代碼陣列）」——也就是
   этот句子的原始位元組序列——本輪嘗試多種方法搜尋 ROM／即時 EWRAM／IWRAM 均未找到，見
   「未解決：句子本身的儲存位置」一節。

## 發現 1：主字形表定址公式（靜態，零模擬器依賴，先於任何動態追蹤完成）

取 7 個已知平假名位址，對照標準五十音順序（あ=0, い=1, う=2, ... く=7, ... さ=10, ...
わ=43, を=44, ん=45, が=46, ..., だ=56, ..., で=59, ...）：

| 字 | 五十音 index | 已知 ROM 位址 | `0x46abe4 + index*0x80` |
| --- | --- | --- | --- |
| い | 1 | `0x46ac64` | `0x46ac64` ✓ |
| く | 7 | `0x46af64` | `0x46af64` ✓ |
| さ | 10 | `0x46b0e4` | `0x46b0e4` ✓ |
| を | 44 | `0x46c1e4` | `0x46c1e4` ✓ |
| ん | 45 | `0x46c264` | `0x46c264` ✓ |
| だ | 56 | `0x46c7e4` | `0x46c7e4` ✓ |
| で | 59 | `0x46c964` | `0x46c964` ✓ |

七個點、零自由參數（base 與 stride 一旦固定就沒有再調整任何參數），**全部精確吻合**。

**渲染驗證**（`extract_obj_kana_fonttable.py`，見下方指令）：從 `0x46abe4` 起取
260 格（`0x80` bytes/格），每格解成 16×16px（2×2 tile、OBJ 1D mapping，同
`render_oam_composite.py` 的排列規則），用職業選擇畫面實際 OAM 調色盤（palette bank 15）
上色，輸出成標註 index 的格狀圖——結果**整段圖案清楚讀出**：

- index 0–70：完整平假名五十音（清音＋濁音＋半濁音），與五十音順序**逐格吻合**，且與
  session 5 姓名輸入畫面 BG 表（`0x1316e8`）用的**同一套五十音排列順序**一致（進一步佐證
  這是遊戲全域共用的一套字符排序慣例，不是這張表獨有）。
- index 71–79：小字假名（ゃゅょぁぃぅぇぉっ 等）。
- index 80 起：片假名，同樣先大字後小字排列，可清楚讀出「アイウエオカキクケコ」等。
- index 約 160 起：全形符號（／、＋、－、＝、。、…、「、」、『、』、～ 等）。
- 之後：Latin 大寫 A–Z、小寫 a–z、數字 0–9、少量結尾符號（音符、閃電、問號等）。

完整渲染圖：`extract_obj_kana_fonttable.py` 輸出的 PPM／PNG（本機保存，見下方指令，
未提交 Git——`.gitignore` 排除 `research/*.png`）。

**這是本遊戲目前找到的第三張獨立字型表**，與先前兩張 BG 表（`0x1398e8` UI 表、
`0x1316e8` 姓名輸入平假名表）以及第二輪確認的 OBJ 標題字型（`0x62AA44`–`0x62B8E4`，
僅片假名＋Latin）都不同、位置更遠、字符集更完整——是目前唯一涵蓋「平假名＋片假名＋
Latin＋數字＋符號」全部在單一線性索引空間裡的表，結構上最像是「一般文字渲染」會用的
主字符集，而不是某個特定選單畫面的專用素材。

**漢字不在這張表裡**：職（`0x482424`）、業（`0x48eec4`）、選（`0x487fc4`）用同一公式
反推出的 index 分別是非整數／不在合理範圍（三者對 `0x80` 取餘數互不相同：`0x482424 mod
0x80 = 0x24`、`0x48eec4 mod 0x80 = 0x44`、`0x487fc4 mod 0x80 = 0x44`——業與選餘數相同，
可能是同一張表但不同 base，職則不同），確認漢字是**另一套獨立、本輪未解出的定址機制**，
可能是依 JIS 系統碼位或每字獨立指標，不是這張線性表的延伸。**這是本輪明確未解決的部分，
誠實記錄，不強行套用同一公式**。

## 發現 2：單字元繪製的完整呼叫鏈（動態追蹤確認）

### 方法

1. `trace_sentence_glyph_load.py`（新增工具）：先用既有的 read-watchpoint＋暫存器覆寫
   技巧（第三輪確立）導覽到存檔選擇畫面，然後對 VRAM 目的位址 `0x06010320`（職業選擇
   畫面「職」字第一個 OBJ tile 的目的地，由 `render_oam_composite.py --verbose` 讀出
   實際 OAM tile 編號 25 反推）設**寫入 watchpoint**，同時保留 KEYINPUT 讀取 watchpoint
   用於按鍵注入，按下確認鍵觸發存檔選擇→職業選擇的畫面切換。命中兩次：第一次
   （`r0=0x085e2de4`、`r1=r2=0x06010340`、`r3=0x7c000000`）本輪**未識別**，暫定是
   同一畫面切換過程中另一個子系統的寫入（例如清空／填充該 VRAM 區段），留給下一輪；
   第二次 `r0=0x08482444`（剛好落在「職」字已知 ROM 範圍 `0x08482424`–`0x084824a3`
   內，偏移 `0x20`＝正在搬移中）、`r2=0x060103a0`（剛好等於「業」字 OBJ tile 的目的
   位址）——直接證實**這是一次 128 bytes 的整批 BIOS 搬移**（`CpuSet`/`CpuFastSet`
   常式內部的 src/dst 游標，此時已進行到第 2 個 word），而非逐位元組手動迴圈，也不是
   壓縮資料流。
2. `test_enqueue_during_transition.py`（本輪暫存於 `/tmp`，方法已完整記錄於此、可依
   本節重寫，未存入 `tools/`——見下方「未提交腳本」說明）：對第三輪測試過、但當時判定
   「找不到字型相關命中」的 enqueue 候選函式 `0x08001154` 設**執行斷點**，同樣搭配
   KEYINPUT watchpoint 按鍵注入，在存檔選擇→職業選擇畫面切換的瞬間（而非閒置畫面）攔截。
   結果：連續攔截約 680 次命中（畫面每次重繪都會重新走訪同一組 sprite 清單，所以同一批
   位址反覆出現），**每次命中的 `r0` 都精確等於下列位址之一**：
   - `0x08482424`（職）、`0x0848eec4`（業）、`0x0846c1e4`（を）、`0x08487fc4`（選）、
     `0x0846c264`（ん）、`0x0846c964`（で）、`0x0846af64`（く）、`0x0846c7e4`（だ）、
     `0x0846b0e4`（さ）、`0x0846ac64`（い）——完整 10 字，逐一精確符合 session 5/6
     已確認的「職業を選んでください」逐字 ROM 位址，**無一遺漏、無一誤配**；
   - 另外還有 4 個不在已知句子字元清單內、但同樣穩定重複出現的位址：`0x084d26c4`／
     `0x084d24c4`／`0x084d28c4`（三者僅低位變動，判斷是**動態變化**的角色圖示 sprite，
     猜測是待機動畫的不同影格）與 `0x085df744`（固定不變）、`0x08474904`／`0x08474984`
     （固定、相差 `0x80`，猜測是「剣士」職業名稱標籤的兩個漢字）——這 4 個位址本輪
     **未逐一驗證身分**，只確認它們與句子字元共用同一條呼叫路徑，留給下一輪。
   - **這 14 個「字形來源」命中（10 個句子字元＋4 個上述未識別位址）的 `lr` 全部是
     同一個值**（`0x080034d5`，THUMB interworking bit 已設，對齊後的真正回傳位址是
     `0x080034d4`）——代表職業選擇畫面上這 13–14 個 sprite（圖示＋職業標籤＋句子）
     全部由**同一個呼叫點**逐一呼叫同一個 enqueue 函式繪製，不是各自獨立的呼叫點。
     **這個「同一 lr」的說法只涵蓋這批字形來源命中**：完整攔截清單裡還有其他 `lr`
     明顯不同的命中（例如 `r0=0x03001d40`／`lr=0x08001053`、`r0=0x03002950`／
     `lr=0x08000a53`，OAM／調色盤影子緩衝區搬移；`r0=0x081398e8` 系列／
     `lr=0x08046d9b`，逐格遞增約 `0x1000`，疑似 `0x1398e8` BG UI 字型表被同一佇列
     機制每畫格分批串流進 VRAM——本輪未深入驗證這個附帶觀察，留給下一輪），代表
     `0x08001154` 這個共用 enqueue 函式服務多個彼此獨立的呼叫者／子系統，不是只服務
     這一個文字渲染迴圈。

### 靜態反組譯確認呼叫點

用 capstone（THUMB 模式）反組譯 ROM file offset `0x3498`–`0x3560`，在 `0x080034d0`
處確認：

```
0x080034d0: bl #0x8001154      <- 對應命中的 lr=0x080034d5（THUMB bit 已設）
0x080034d4: ldr r3, [sp, #0x10]
0x080034d6: adds r3, #1
0x080034d8: str  r3, [sp, #0x10]
0x080034da: adds r4, #8
...
0x080034e4: cmp r3, r1
0x080034e6: bhs #0x80034ea
0x080034e8: b   #0x80033a4      <- 迴圈：計數器 r3 未到上限，跳回迴圈本體繼續下一個 sprite
```

`bl 0x8001154` 的目標位址與斷點攔截位址完全吻合，`r3`／迴圈計數器與跳回 `0x80033a4`
的分支結構，直接證實這是一個**走訪 N 個 sprite、逐一呼叫 enqueue 函式**的迴圈——與
即時追蹤看到的「同一 lr、多次命中」現象完全一致，是靜態與動態證據互相印證的結果，
不是單一方法的孤證。

呼叫前（`0x34b2`–`0x34ce`）用位元欄位運算（`lsls`/`lsrs`/`orrs` 組合，從一個結構體
欄位——很可能是這個「sprite 描述項」的欄位——拆出 shape/size/tile 相關位元）組出傳給
`0x08001154` 的 `r0`（來源）／`r1`／`r2`（大小／模式）三個參數，**沒有出現單一乾淨的
「`ldr` 常數表基底 + `lsl #7`（×`0x80`）+ `add`」這種教科書式定址運算**——這代表就算
「index×`0x80`+base」這個公式在資料佈局上完全成立（發現 1 已用 7 點零自由參數驗證），
**產生這個位址的實際運算方式本輪未能在反組譯裡直接對應出來**，可能是先在別處（呼叫這個
迴圈之前）就已經算好、存進這個「sprite 描述項」結構體裡了，也可能是用查表而非乘法完成
——這條「公式在資料佈局上成立」與「公式在程式碼裡如何被算出」之間的落差，如實記錄，
不強行聲稱已找到乘法指令本身。

## 未解決：句子本身的儲存位置（誠實記錄的負面結果）

任務要求「找出哪怕幾個位元組能對應到這句話」——本輪嘗試但未成功，方法如下（供下一輪
避免重工）：

1. **相鄰位置差值掃描**：句子中真正相鄰、都是假名、中間沒有漢字打斷的僅有「で→く→だ→
   さ→い」（原句「職業を選んでください」裡「を」和「ん」中間隔了漢字「選」，並非
   真正相鄰——這是本輪一次會錯意後自行修正的教訓，見下）。取這 5 個字的五十音 index
   （59,7,56,10,1），算出相鄰差值 `[-52,49,-46,-9]`，對 ROM 全檔、即時 EWRAM
   （`0x02000000`，256KiB，職業選擇畫面穩定後擷取）、IWRAM（`0x03000000`，32KiB）
   做滑動視窗掃描，byte／word 寬度、以及乘以 1／4／`0x80` 三種縮放係數都試過，**全部
   零命中**。這代表句子的原始資料**不是**「一串未經任何轉換的字符 index，逐位元組／
   逐 halfword 直接排列」這種最簡單的形狀——可能是有其他欄位交錯（例如漢字用不同寬度
   打斷了假名的連續性，比本輪已修正的判斷更複雜）、可能是壓縮或間接指標、也可能只是
   剛好不在本輪擷取的這兩塊 RAM／這份 ROM 快照範�布內（例如渲染完成後緩衝區已被覆寫）。
2. **Shift-JIS 精確位元組搜尋**：對完整句子「職業を選んでください」與多個子字串（「職業」
   「を選んで」「ください」「選んで」）算出標準 Shift-JIS 編碼，在整個 ROM 內搜尋，
   **全部零命中**——與第一輪偵察「常見日文詞彙 SJIS 搜尋全落空」的既有負面結果一致，
   本輪只是把同一測試套用到這個具體、現在已知一定存在於某處的句子上，結果仍然一致，
   不是新發現，但值得記一筆確認舊結論在新資料上依然成立。
3. **常數表基底的 literal pool 搜尋**：搜尋 ROM 內是否有位置存放小端序 4-byte 常數
   `0x0846abe4`（表基底，供程式碼直接 `ldr rX, [pc,#n]` 載入用）——**零命中**，也試過
   基底加減若干 `0x80` 倍數的鄰近值，同樣零命中。這與上一節「反組譯沒看到乾淨的乘法/
   位址運算」互相印證：這個位址很可能不是以「常數 literal pool＋執行期乘法」的方式
   計算出來的，command更可能是完全在別處（例如一個更早、本輪未追蹤到的「字元代碼→
   完整 32-bit ROM 位址」查表函式）就已經算好，或者這張表的存在本身是本輪從資料佈局
   反推出來的產物，遊戲程式碼實際存取它的方式可能與「index × 固定 stride」這個外部
   觀察角度完全不同（例如程式碼內部維護的是很多個「這個字對應這個指標」的個別項目，
   剛好在 ROM 佈局上排成了等距陣列，而非執行期真的做乘法）。**這是本輪最大的未解之處，
   如實記錄，不誇大成「已找到位址計算指令」**。

## 教訓

- **在動的（emulator）之前先做靜的（algebraic fit）**：本輪最高信心的發現（主字形表
  定址公式）完全不需要模擬器——只是把 session 6 已經記錄下來的 7 個位址，對照遊戲
  既有的標準五十音排序去代數擬合，10 秒鐘算出來的。後續的模擬器追蹤（enqueue 斷點）
  某種意義上只是「確認」而非「發現」——如果先做了模擬器追蹤才做這個代數擬合，效率會
  低很多。這個心得已同步記錄到 `.agents/skills/gba-localization/SKILL.md`。
- **「句子裡某兩個字元位置相鄰」不能只看句子的人類可讀順序，要先確認資料結構裡它們是否
  真的相鄰**——本輪一度誤把「を」與「ん」（人類可讀順序中間隔了漢字「選」）當成資料
  陣列裡的相鄰元素去算差值，幸好在動筆搜尋前發現並修正；如果未來遇到「差值掃描找不到」
  的情況，第一件事應該是重新檢查「這幾個元素在底層資料結構裡真的緊鄰嗎」，而不是急著
  懷疑整個掃描方法或加大搜尋範圍。
- **同一個曾被「否定」的候選，換一個測試時機可能翻案**：第三輪測試 `0x08001154` 時
  只在標題畫面等閒置畫面攔截了 550 次，得出「不是字型 enqueue 路徑」的否定結論；本輪
  改成在真正觸發字型載入的畫面切換瞬間測試，同一個函式立刻被證實就是正確答案。這代表
  「已測試、已否定」的記錄裡，**測試時機／情境本身是否覆蓋到目標事件**跟「測試次數多寡」
  一樣重要，之前的否定結論在記錄時就該同時記下「測試情境」，方便下一輪判斷是否值得
  換個情境重測，而不是照單全收「已否定＝不用再看」。

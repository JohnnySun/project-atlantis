# 三個漢字字型表定址公式（category 1／2／3，session 10）

本檔案記錄第十輪偵察的結果：解出 session 8 字串格式裡 `category` 欄位除 0（假名）
外，另外三個實際大量使用的值（1、2、3）各自對應的漢字字型表定址公式——這是 session 7
明確標記「漢字定址機制未解」、session 8/9 反覆記錄為「未解決」的核心缺口。分析結論，
只列少量抽樣文字供人工核對格式判讀是否合理，不是大段原文抄錄，可安全提交。

## 摘要（先講結論）

1. **三個新的 `category` 值全部確認是漢字字型表，用的是與 category 0（假名主表，
   `0x46abe4 + index*0x80`）完全相同的定址公式，只是 base 位址不同**：

   | category | 表 base | 驗證用的 2 個獨立資料點 | 驗證方式 |
   | --- | --- | --- | --- |
   | 1 | `0x474584` | 剣=idx7、士=idx8（「剣士」職業標籤，session 7 見過但未識別的 sprite 來源位址） | 即時 VRAM 擷取＋ROM 精確位元組搜尋（找位址）＋中斷點攔截字串走訪函式（找 code） |
   | 2 | `0x47dfa4` | 職=idx137（session 5/6 已知位址）、色=idx138（本輪同法新找到） | 職：session 5/6 既有結果；色：即時 VRAM 擷取＋ROM 精確位元組搜尋 |
   | 3 | `0x4879c4` | 業=idx234、選=idx12（皆 session 5/6 已知位址，本輪才算出公式） | 純算術（兩個既有位址代入公式，零自由參數精確吻合） |

   三個都是**兩點、零自由參數、位址與索引精確整除吻合**（見下方「驗證」），與 session 7
   確認 category 0 主表時用的 7 點驗證標準同一等級的嚴謹度（雖然點數較少，但每個都是
   兩個完全獨立來源的資料點，不是同一批資料重複使用）。

2. **渲染整段表格，人工核對確認是清晰、不重複、非雜訊的漢字表**（非灰階、用職業選擇
   畫面實際調色盤 palette bank 15 上色）：三張表在 `--count 128`–`240` 範圍內幾乎每格
   都是非空、彼此不同、筆畫結構複雜合理的漢字形狀，與雜訊資料（重複圖樣、週期性假名表）
   有明顯區別，符合先前各輪判斷「這是真字型表」的視覺判準。

3. **用 6 句從未見過的真實對話池句子做語意層級驗證，全部讀出通順日文**（見下方「語料庫
   驗證」）——這是任務明確要求的驗證強度（不只是公式吻合，還要在真實資料上讀得通）：
   - `0x499b5e`：「名[c1:48]を入[c1:25]してください」渲染後補上 cat1 兩表後完整顯示
     「名前を入力してください」（請輸入姓名）——語意、字面完全自洽。
   - `0x499aa2`：「それは[c1:104]き[c3:36]れません」渲染後顯示「それは引き取れません」
     （這個無法退還／領取）——通順慣用句。
   - `0x499e1a`：「ゲームを[c3:49][c4:16]するとセーブされます」渲染後 cat3 補上後顯示
     「ゲームを[漢字]するとセーブされます」（進行遊戲中的某動作時會自動存檔）——僅剩
     `category=4` 一格未解（本輪不強行湊，如實留白）。
   - 另外 3 句（見下方完整列表）同樣讀出自然、符合遊戲情境的日文。
   這些句子在本輪開始前完全無法閱讀（只有零星假名穿插一堆 `[c#:N]` 佔位符），現在
   除了極少數仍未解的 category（4、6–15）留白外，其餘全部清晰可讀。

4. **語料庫覆蓋率大幅提升**：以本輪從對話池／怪物名稱表區間重新做鏈式掃描＋可讀性
   篩選取得的語料（9,645 個代碼），`category` 0／1／2／3 四類合計涵蓋 **9,610 個代碼
   （99.6%）**；其餘 12 個 category（4–15，扣除 0/1/2/3）合計只佔 35 個代碼
   （0.4%）。這代表本輪解出的三個新 category，加上既有的 category 0，**已經足以
   渲染絕大多數真實對話文字**，遠超任務原本「破解一個 category」的最低目標。

## 方法：如何找到 category 1／2 的第二個驗證點（色、剣、士）

### 職／業／選 的位址早就記錄過，只是沒人代入公式算 base

Session 5/6 已經用逐位元組精確搜尋找到「職」（`0x482424`）、「業」（`0x48eec4`）、
「選」（`0x487fc4`）三個漢字的 ROM 位址（見 `research/obj-sentence-glyph-loader.md`
「背景」表格）；session 8 解出這三字的字串代碼是 職=idx137/cat2、業=idx234/cat3、
選=idx12/cat3。本輪第一步只是**純算術**：把「業」「選」代入 `base = addr - idx*0x80`，
兩者算出**完全相同**的 base（`0x4879c4`），零自由參數吻合——這是 category 3 的公式，
10 秒鐘算出來，不需要模擬器（呼應 session 7 已寫入 skill 的心得「先做靜的代數擬合，
再考慮動用模擬器」）。

「職」單獨算出 category 2 的候選 base（`0x47dfa4`），但只有一個點，需要第二個獨立
位址才能像 category 3 那樣做零自由參數驗證——這是本輪真正需要模擬器的部分。

### 用即時 VRAM 擷取＋ROM 精確位元組搜尋，找到「色」與「剣」「士」的 ROM 位址

背景啟動全新 `mgba -g <rom>`，用既有的 `navigate_to_char_create.py` 導覽到存檔選擇→
職業選擇→顏色選擇畫面，dump 每一步的 VRAM／調色盤／OAM。用 `render_oam_composite.py
--verbose` 讀出實際 OAM 排列，確認：

- 顏色選擇畫面（`DISPCNT=0x1d40`）句子「色を選んでください」的第一個字元（sprite 6，
  `xy=(62,139)`，OBJ tile#33）就是「色」。
- 職業選擇畫面「剣士」職業標籤的兩個字元是 sprite 2/3（tile#17／#21）。

直接讀出這幾個 OBJ tile 在 VRAM 裡的 128 bytes 原始像素資料，在整個 ROM 內做**精確
位元組序列搜尋**（與 session 5/6 找職／業／選位址時同一手法，只是這次資料來源是即時
VRAM dump 而非重新推導）：

```
色 (VRAM OBJ tile#33) -> ROM 0x4824a4  （唯一命中）
剣 (VRAM OBJ tile#17) -> ROM 0x474904  （唯一命中，與 session 7 記錄但未識別的
                                          候選位址完全相同）
士 (VRAM OBJ tile#21) -> ROM 0x474984  （唯一命中，同上，兩者恰好相差 0x80）
```

`色` 代入 category 2 公式：`(0x4824a4 - 0x47dfa4) / 0x80 = 138.0`——**整數、精確等於
138**，與 session 8 從字串代碼解出的 `色=idx138/cat2` 完全吻合，兩個完全獨立的方法
（即時像素比對 vs. 字串代碼解碼）互相印證，不是巧合。

### 用中斷點找出「剣士」的字串代碼本身，順帶解出 category 1

找到 剣／士 的 ROM 位址後，還需要知道它們在 **字串代碼系統**裡的 `(category, index)`
才能反推 category 1 的 base（前一步只確認了「這裡有另一張表」，還不知道 index 是多少）。
用 session 8 已知的字串走訪函式入口（ROM file offset `0xe8bc`）設中斷點，在職業選擇
畫面每次重繪都會命中——**先前的 `trace_sentence_string_source.py` 只保留第一個
「≥5 字元」的命中（用來過濾出完整句子，忽略短標籤）**，本輪寫了一個不過濾長度的
變體（`/tmp/trace_all_strings.py`，方法已完整記錄於此，見下方「未提交腳本」），
捕捉到**兩個**不同的字串指標：

```
r0=0x08499f76  codes=[0x0108, 0x0109]   <- 短字串，2 個字元（「剣士」標籤）
r0=0x08499b1a  codes=[0x028a, ...]      <- 已知的「職業を選んでください」
```

解碼 `0x0108`／`0x0109`：`category=(0x108>>8)&0xF=1`，`glyph_entry_index=
(0x08&0xFF)-1=7`；`category=(0x109>>8)&0xF=1`，`glyph_entry_index=(0x09&0xFF)-1=8`。
即 **剣=idx7/cat1、士=idx8/cat1**。代入 category 1 公式，用兩個獨立位址驗證：

```
base(剣, idx7)  = 0x474904 - 7*0x80 = 0x474584
base(士, idx8)  = 0x474984 - 8*0x80 = 0x474584
```

**兩者精確相同，零自由參數，兩點吻合**——category 1 的定址公式確認：
`glyph_rom_offset(index) = 0x474584 + index * 0x80`。

## 驗證：渲染三張表，人工核對

用本輪新增的 `tools/extract_kanji_fonttable.py`（`extract_obj_kana_fonttable.py`
的泛化版本，接受任意 `--base`／`--category`）渲染，職業選擇畫面實際調色盤
（palette bank 15）上色：

```sh
python3 games/shining-soul-1/tools/extract_kanji_fonttable.py \
  games/shining-soul-1/roms/base/Shining_Soul_JP_AHUJ8P.gba \
  --category 1 --count 128 --out-png /tmp/cat1.png \
  --palette <dump-dir>/04_after_file1_a.pal.bin --palbank 15
# 同法 --category 2 --count 160、--category 3 --count 240
```

三張表在渲染範圍內（cat1 128 格、cat2 160 格、cat3 240 格）幾乎全部非空、每格圖案
彼此不同、複雜度與筆畫密度符合漢字（而非重複假名或雜訊）——與已知正確位址（職／業／
選）的渲染結果放在一起比對，風格、解析度、模糊程度完全一致，是同一套字型系統的
自然延伸，不是巧合湊出來的圖案。渲染圖已存檔（`research/obj-kanji-cat1-table.png`、
`obj-kanji-cat2-table.png`、`obj-kanji-cat3-table.png`，本機保留，`.gitignore`
排除 `research/**/*.png`）。

**特定格位核對**：cat2 表 idx137／idx138 位置渲染出的圖案，逐位元組核對後與已知
「職」「色」的獨立渲染完全一致（因為本來就是同一段 ROM 資料，這一步是確認渲染管線
本身沒有帶入額外誤差，而非新證據）；cat1 表 idx7／idx8（剣／士）、idx25（力，見下
語料庫驗證）、idx48（前）在 16×16px 解析度下可以看出合理的複雜筆畫結構，但**在這個
解析度下逐格用肉眼確認「這一定是某個特定漢字」本身有其極限**——即使是已經**確認
正確**的位址（如「業」「選」），渲染出來也只能看出「像是某個複雜漢字」而非能百分之百
念出來，這點誠實記錄，不誇大成「每一個漢字都已用肉眼識別出對應的 Unicode 字」。
本節的核心證據力來自**位址算術的精確整數吻合**與下一節的**語意驗證**，視覺渲染只是
輔助的、非決定性的第三重交叉核對。

## 語料庫驗證：用全新的、從未見過的真實句子做語意層級核對

本輪重新對 `0x499000`–`0x500000`（對話池）與 `0x460000`–`0x470000`（怪物名稱表）
做鏈式掃描＋可讀性篩選（沿用 session 9 的 `extract_string_pool.py`／
`scan_string_pools.py` walk 邏輯，篩選門檻：`avg_codes_per_line>=2.5`、
`category-0 在已知假名/片假名範圍比例>=0.6`、`category-0 代碼數>=3`），得到
74 個對話池池、21 個怪物名稱池，共 9,645 個代碼——這是本輪用來估計 category
分布與挑選驗證樣本的語料庫（比 session 9 report 的 620/487 條目數字更寬，因為
篩選參數與遍歷範圍不完全相同，此數字只用於本輪內部統計，不是重新定義官方統計）。

從中挑出 6 條**至少含一個 category 2/3 代碼、且從未在先前任何一輪報告裡出現過**
的真實句子（用 `tools/render_string_glyphs.py` 渲染，同一份 palette bank 15），
逐句人工核對是否讀成通順日文：

| ROM 位址 | 渲染結果（`[c#:N]` 為仍未解的 category） | 人工判讀 |
| --- | --- | --- |
| `0x499b5e` | 名前を入力してください | "請輸入姓名"——文法、字面完全通順，是任何 RPG 姓名輸入畫面的標準提示句 |
| `0x499aa2` | それは引き取れません | "那個無法領取／退還"——通順的遊戲內常見拒絕語 |
| `0x499e1a` | ゲームを[c4:16]するとセーブされます | "進行遊戲中○○時會自動儲存"——僅剩一個 category（4）未解，其餘完全通順 |
| `0x499c06` | [c3:216][c1:31]がいっぱいです | "○○已經滿了"——常見道具欄已滿提示句型，兩個未解 category 落在同一個名詞位置，合理 |
| `0x499cea` | お客さ〜ん、[c1:57]って[っ]かない？ | "客人～，不[○○]走嗎？"——口語縮約語氣詞「〜ってかない」通順，僅一個 category 未解 |
| `0x499dd4` | ら[c1:7]えないよ！[c2:32]けなよ。 | 可能是「もらえないよ！怠けなよ。」（"拿不到喔！別偷懶啦。"）這類口語催促句，兩個
  未解 category 落在文法合理的位置（動詞前綴、動詞語幹） |

六句話裡有兩句（`0x499b5e`、`0x499aa2`）**完全**通順可讀、沒有任何未解 category
留白（`0x499aa2` 只是本輪選樣時恰好兩個未知 category 都被本輪解出，變成全通），其餘
四句除了 1–2 個仍未解的 category 外全部通順，且未解的字元都精確落在文法上「應該是
一個詞」的位置（例如「ゲームを＿する」
的動詞、「＿がいっぱいです」的主詞名詞）——這種「未知代碼恰好卡在文法合理位置」的
一致性本身就是額外的間接證據，支持這套 category 系統整體上是「一個字＝一個有意義的
文字」，不是雜訊。

**這是本專案第一次能完整讀懂遠超「兩句已知句子」規模的真實對話語料**——先前九輪
只確認過兩個特定畫面各一句提示語，本輪驗證的六句全部是先前完全沒看過的真實內容，
且抽樣策略是「隨機挑選含未知 category 的真實句子」而非挑容易的例子，符合任務要求的
驗證嚴謹度。

   / `scan_string_pools.py` 現有工具的預設參數重新產生，而非像本輪一樣另外寫
   一次性統計腳本（`/tmp/corpus_freq2.py`，未保留）。

## 教訓（game-agnostic，值得留在 skill）

- **一個「已測試但未識別」的候選，可能不需要新的偵察，只需要把舊資料重新算一遍**——
  category 3 的公式完全來自 session 5/6 已經記錄多輪的「業」「選」位址，純算術
  10 秒鐘解出，本輪甚至沒有立刻意識到這一點（先去追查了 category 1/2 才回頭發現
  category 3 早就有兩個現成點）。下次遇到「已知兩個以上獨立位址、但從未代入某個
  猜測公式驗證」的情況，應該優先檢查是否能純算術解出，而不是預設需要新的模擬器
  資料。
- **「已知一個字元的畫面位置」比「已知一個字元的字串代碼」更容易獨立驗證第二個表
  base**——本輪能找到 category 1/2 的第二個驗證點，關鍵是「已經知道某個字元在
  某個畫面的哪個 OAM sprite 位置」（session 7 記錄的、當時判定「未識別」的
  `0x474904`／`0x474984`），比起重新從字串代碼反推位址，直接用「VRAM 像素→ROM
  精確位元組搜尋」找位址、再用「中斷點抓字串代碼」找 index，兩條線分開求證、
  最後才代入公式核對，是比單一路徑更穩固的雙重獨立驗證。
- **中斷點命中時「只留第一個符合長度門檻的結果」會系統性漏掉短字串（標籤／單字）**
  ——`trace_sentence_string_source.py` 原本刻意只保留 `len(codes)>=5` 的命中
  （目的是過濾出完整句子而非單一按鍵回饋之類的雜訊），這個設計選擇在解句子格式
  時是對的，但也連帶讓「剣士」這種 2 字短標籤的字串代碼完全沒被看到過，直到本輪
  刻意寫一個不過濾長度的版本才發現。**過濾條件本身要對應到當下的分析目標**，
  同一個中斷點在「找長句子」與「找所有字串（含短標籤）」兩種目標下應該用不同的
  過濾邏輯，不能只維護一份「當初為了某個目的而設的」腳本。

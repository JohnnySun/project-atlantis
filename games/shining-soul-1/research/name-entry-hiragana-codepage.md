本檔案記錄第五輪偵察（未寫入文件即中斷）遺留的推進軌跡，經第六輪從乾淨開機**獨立重跑

## 重大結構性發現：姓名輸入畫面用的是第二張、全新的 1024 格 BG 字型表

存檔選擇畫面已知 charbase 0（`0x06000000`）的內容整段對應 ROM `0x1398e8`（第四輪確認，
168 格非空，僅片假名＋Latin＋數字）。本輪對姓名輸入畫面的 charbase 0 內容重跑
`extract_bg_fonttable.py --verify-against`，**比對到 `0x1398e8` 表卻在 tile 1 就不符**
——代表這個畫面的 charbase 0 內容已經被換成了別的資料，不是同一張表。

對姓名輸入畫面 VRAM charbase 0 內容（987 格非空，遠多於存檔選擇畫面的 168 格）在 ROM
內做精確位元組搜尋（先搜第 1 格，再搜前 20 格連續內容做交叉確認），找到：

- **ROM file offset `0x1316e8`** 開始，**逐位元組完整比對全部 1024 格**（`0`–`1023`）
  與姓名輸入畫面的 VRAM charbase 0 完全相同，第一個不符位置同樣剛好落在 tile-index
  1024（定址範圍邊界），與第四輪對 `0x1398e8` 表的驗證方式、結論形狀完全一致。
- 這張新表結束於 ROM file offset `0x1396e8`，與已知的 `0x1398e8` 表起點只差 `0x200`
  bytes（幾乎緊接），兩張表在 ROM 裡實體上相鄰。
- **意義**：VRAM charbase 0（`0x06000000`）**不是一張固定不變的全域字型表**——遊戲在
  不同畫面會把不同的 ROM 字型表整段搬進同一個 VRAM 位址：存檔／職業／顏色選擇畫面用
  `0x1398e8`（UI 短標籤字型），姓名輸入畫面換成 `0x1316e8`（完整平假名字型）。這修正了
  第四輪報告裡「BG tile-index 本身就是字符代碼，不存在另一層字符代碼→tile-index 對照」
  的表述——**這句話本身沒錯，但只在單一畫面內成立；跨畫面比較時，同一個 tile-index
  在不同畫面可能代表完全不同的字符**，因為底層表本身換了。下一輪如果要建立「系統通用
  codepage」，必須先確認正在看哪一張表，不能假設 tile-index 是全域穩定的。

## 大規模平假名 codepage（本輪最大產出）

姓名輸入畫面的 BG1（`screenbase 0xe800`，charbase 0）tilemap 直接畫出一張**標準日文
輸入法五十音鍵盤版面**（あ行～わ行＋濁音／半濁音＋やゆよ＋わをん＋小字＋符號），版面
本身就是已知明文（任何玩過日文遊戲的人都認得這個版面的固定順序），比逐條核對 UI 標籤
的方法（第四輪用法）一次能核對的字符數量高一個數量級，不需要 OCR。

### 字符寬度結構：每個平假名字符＝2×2 tile block（16×16px），不是單一 8×8 tile

與第四輪表（多數字符窄體、2 字元塞 1 tile）不同，這張表的假名是標準全形寬度：每個
字符佔 4 個 tile-index（左上、右上、左下、右下），且經驗證**左下＝左上+32、右下＝
左上+33**（例如「あ」＝左上644／右上645／左下676／右下677，676−644=32，677−645=32）
——這是固定的算術關係，代表底層字型表本身以「32 tile 一列」的方式排版（與 1024
格＝32×32 的正方形排列吻合）。因此下表只記錄每個字符的「左上 tile-index」（記為 T）
作為代表性 codepage 值，完整 4-tile 位置可由 `T, T+1, T+32, T+33` 算出。

  兩者 tile-index 部分重疊但位置不同，注意不要混淆） | 外觀近似完整版「あいうえお」，
  但版面位置在濁音／半濁音欄位之後，也可能是**小字版本「ぁぃぅぇぉ」**（此遊戲窄體
  字型是否會用相同字形表示大小版本尚不確定）。因無法排除歧義，此列全數列為低信心，
  **不建議直接採用「あいうえお」字面值**，下一輪如果找到會用到這些 tile-index
  的實際名字輸入畫面操作紀錄（例如玩家真的選字後看到輸入框內容），可以直接核實。

## 附帶發現：OBJ 渲染的完整句子文字，字形來源不是先前已知的任一張表

職業選擇畫面「職業を選んでください」這句話是用 OBJ（sprite）渲染，不是 BG——每個字
是一個 16×16px（2×2 tile，OBJ 1D mapping）精靈。把這 10 個字對應的 VRAM OBJ tile
資料（各 128 bytes）逐字在 ROM 內做精確位元組搜尋，結果：

| 字元 | ROM 位址 |
| --- | --- |
| 職 | `0x482424` |
| 業 | `0x48eec4` |
| を | `0x46c1e4` |
| 選 | `0x487fc4` |
| ん | `0x46c264` |
| で | `0x46c964` |
| く | `0x46af64` |
| だ | `0x46c7e4` |
| さ | `0x46b0e4` |
| い | `0x46ac64` |

**全部逐位元組原封不動找到，未經壓縮**——這點與先前所有已確認字型資料（OBJ 標題字型
`0x62AA44`、BG 兩張字型表）的模式一致，進一步支持「這款遊戲的固定 UI／選單文字資料
整體上不使用壓縮，直接原始存放」這個累積中的推論（但仍只涵蓋 UI／選單，未涵蓋對話）。

**觀察到的結構**：三個漢字（職／業／選）位在 ROM `0x48xxxx` 一帶，彼此距離很大、不成
固定間距；七個平假名（を／ん／で／く／だ／さ／い）全部落在 `0x46A000`–`0x46E000` 這
約 16KiB 範圍內，且部分位址彼此正好相差 128 bytes 的整數倍（例如 `を`=0x46c1e4 與
`ん`=0x46c264 恰好相差 128 bytes＝1 格）——這暗示這個範圍內可能存在**第三張、獨立於
兩張 BG 表和第二輪 OBJ 表之外的 OBJ 用平假名字型表**，很可能是一張以某種索引（不一定
是 tile-index 本身，也可能是字元代碼）定址、128-bytes-per-glyph 的表；而漢字則可能
落在另一張更稀疏、範圍更大的表（合理猜測是依 Shift-JIS 或 JIS X 0208 碼位定址，因為
漢字數量遠大於假名，需要更大的定址空間）。**這兩個假設本輪都未驗證**，只記錄觀察到
的位址分布，留給下一輪：下一步可行做法是收集更多 OBJ 渲染句子裡的假名字元位址，
確認是否都落在 `0x46A000`–`0x46E000` 範圍內且間距是 128 的倍數，藉此反推表格起點與
定址公式（類似第四輪／本輪對 BG 表用的「已知位置反推線性關係」手法）。

## 額外核對：職業／顏色選擇畫面確認沿用 `0x1398e8` 表；tile 96–108「キャラクタ／
カラーセンタク」猜測未獲支持（誠實記錄一次負面結果）

- **已確認**：對 `04_after_file1_a.vram.bin`／`05_after_second_a.vram.bin` 重跑
  `extract_bg_fonttable.py --base 0x1398e8 --verify-against`，兩者皆**完整 1024 格
  逐位元組比對通過**（`first mismatching tile = None`）——這是第四輪「item 1：是否為
  跨畫面共通的系統級 codepage」問題的第一個正面直接證據：職業選擇／顏色選擇畫面
  （沿用存檔選擇畫面的 BG0/BG2/BG3 版面）與存檔選擇畫面**共用同一張 ROM 字型表**，
  不是各自獨立的美術資料。
- **已檢查但未獲支持**：第四輪在字型表圖片裡目測懷疑 tile 96–108 是「キャラクタ／
  カラーセンタク」（角色／顏色選擇）字樣，本輪讀取職業選擇畫面 BG0（`screenbase
  0xe000`，經確認正確算法：`((BG0CNT>>8)&0x1f)*0x800`）的 tilemap，結果**只有 32×32
  格中的 8 格非空、tile-index 集中在 1–6 這個很小的範圍**（明顯是邊框／裝飾圖案，不是
  文字），完全沒有出現在 tile 96–108 這個範圍。這代表 tile 96–108 究竟用在哪個畫面
  仍未找到，第四輪的目測猜想**沒有被本輪證實**——誠實記錄這個負面結果，避免下一輪
  重複同一個方向的嘗試；「キャラクタ／カラーセンタク」字樣如果真的存在，用的可能是
  另一個尚未檢查的畫面（例如姓名輸入完成後的下一步，或者這幾個字根本不存在，是原本
  目測時的誤讀）。

## 教訓（下輪或其他遊戲適用）

- **同一組 `DISPCNT`/`BGxCNT` 暫存器值不能保證是同一個畫面**——存檔選擇／職業選擇／
  顏色選擇三個畫面的暫存器完全相同，只有靠實際渲染 OAM／BG 內容比對才能分辨。用
  「暫存器快照」當唯一的畫面識別依據是不夠的，必須搭配至少一次內容渲染核對。
- **VRAM 裡看到的字型表位置和內容會隨畫面切換而改變，不能假設某個 charbase 位址
  在整個遊戲執行期間都對應同一張 ROM 表**——第四輪的「tile-index 本身就是 codepage、
  不需要另一層對照」結論本身沒錯，但隱含的「這張表是全域唯一」假設本輪被推翻。這是
  對之前工作的一次誠實修正，不是全盤推翻——第四輪對 `0x1398e8` 表的驗證方法與結論仍然
  成立，只是「這是唯一一張表」的隱含推論需要拿掉。
- **系統性版面（如輸入法鍵盤格）是遠比零散 UI 標籤更高效的 codepage 擷取來源**：本輪
  一次核對動作（71 個標準五十音字元）取得的 confirmed 字元數是第四輪整輪工作量的兩倍
  以上，因為版面順序本身就是已知明文，不需要逐條找「這個字在哪裡出現過」。這個心得比
  第四輪記錄的版本更強（第四輪只確認「已知明文比 OCR 快」，本輪進一步確認「系統性、
  版面固定的畫面比零散明文標籤又快一個量級」），已同步補記到
  `.agents/skills/gba-localization/SKILL.md`。

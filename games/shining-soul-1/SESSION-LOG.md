## 當前進度（第二輪偵察後：字型格式與部分字形資料位置已確認，文字系統仍未完全解出）

第二輪偵察新增 `capstone`（ARM/THUMB 反組譯）與 `mgba --gdb`（即時記憶體觀察）兩項工具，取得第一輪純靜態掃描做不到的正面結果，見下方「第二輪偵察」一節。第一輪的负面結果（見下）仍然有效，未被推翻。

- **ROM 身分已確認**：`file`／自製標頭解析器讀出卡匣標頭 `SHINING SOUL`／game code `AHUJ`／maker code `8P`，標頭補數校驗（0xBD）計算值與 ROM 內實際值一致（`0x2e`），確認標頭未損壞。檔案大小 8,388,608 bytes（8 MiB＝64 Mbit），與目錄檔名「64Mb」宣告一致。
- **雜湊已計算**（未與任何外部資料庫比對，只是本機記錄）：見下表。
- **ROM 實際使用範圍**：以 16 KiB 區塊掃描 Shannon entropy，`0x660000` 之後到檔案結尾（`0x800000`）全部是 `0xFF` 填充，代表卡帶實際內容只佔約 6.7 MiB，其餘是空白容量。
- **文字系統尚未解出**——這是本輪最重要的負面結果，記錄如下，避免下次重工：
  - 對整個 ROM 做「哪些位元組序列本身是合法 Shift-JIS」的結構掃描，命中大量長片段，但人工檢視後幾乎全部是圖形／調色盤／音效等二進位資料湊巧滿足 Shift-JIS 前後導位元組規則的假陽性（重複同一兩三個「字」、字符多樣性低、且落在熵分析判定的圖形資料區間內），不是對話文字。
  - 對常見日文 UI／戰鬥詞彙（`はい`、`いいえ`、`レベル`、`たたかう`、`にげる`、`どうぐ`、`セーブ`、`ロード`、`コマンド`等，含半形／全形變體）逐一以其標準 Shift-JIS 位元組序列在整個 ROM 內搜尋精確匹配，**全部找不到**。這代表文字很可能不是以未壓縮的標準 Shift-JIS 直接存放，而是像黃金太陽一樣走自訂編碼（壓縮、自訂 codepage、或兩者皆有），但目前無法進一步判斷是哪一種——Sega 的自製文字系統目前沒有找到任何公開的逆向工程紀錄可以參考（見下方「外部資料」）。
  - 未找到明確的字串指標表：以「連續多個 4-byte LE 值都落在 `0x08000000`–`0x087FFFFF` ROM 位址空間內」為訊號掃描全ROM，命中的候選全部集中在 `0x000000`–`0x054000`（推測是程式碼區，很可能是 switch-case 跳轉表或字面量池），沒有在較大範圍內找到典型「字串表」形狀（大量、位址遞增、分佈在資料區而非程式碼區）的候選。
  - BIOS 解壓縮呼叫（THUMB `swi` 指令，半字組對齊掃描）確認 ROM 程式碼裡有呼叫 `LZ77UnCompWram`(11次)／`LZ77UnCompVram`(28次)／`HuffUnComp`(15次)／`RLUnCompWram`(16次)／`RLUnCompVram`(10次) 等 BIOS 服務，但這只證明「這些 BIOS 常式有被呼叫」，**不能**證明文字資料走哪一種、甚至是否被這些常式處理——GBA 遊戲用 BIOS LZ77／RLE 壓縮圖形資源非常普遍，這批呼叫點極可能主要服務圖形／音效資料。且此掃描本身有大量假陽性（原始逐位元組掃描曾一度數到 85 次 `LZ77UnCompVram` 候選，改成半字組對齊掃描後降到 28 次，仍未反組譯驗證是否為真指令）。
  - 原始的「壓縮簽章」（magic byte 0x10／0x24／0x30 加合理大小欄位）字組對齊全域掃描噪音極大（LZ77 候選 11,455 個、Huffman 候選 2,298 個、RLE 候選 3,022 個），單獨看毫無意義，只有在能交叉比對「真的被程式碼位址引用」時才有價值——這一步本輪沒有做（需要反組譯，超出第一輪唯讀偵察範圍）。
- **外部資料**：搜尋 romhacking.net、GBAtemp、Shining Force Library 等社群站台，沒有找到任何公開的《光明之魂》（GBA，SS1／SS2）文字格式逆向工程筆記；GBAtemp 上一篇 Shining Soul II 的 ROM hacking 部落格只是宣布專案開始，未含技術細節。目前判斷本作文字系統需要從零開始逆向，沒有現成參考可以站在肩膀上。

## 第二輪偵察（capstone 反組譯 + mGBA GDB 即時記憶體觀察）

工具環境：`capstone` 5.0.x 只裝在 `/usr/bin/python3`（Command Line Tools 版本），**不是** `/opt/homebrew/bin/python3`——之後重跑本節腳本務必用前者，否則會 `ModuleNotFoundError`。`mgba`（`/opt/homebrew/bin/mgba`，0.10.5）用 `-g` 開 GDB remote server（預設埠 2345）；本機沒有 `gdb`，改用 `games/shining-soul-1/tools/gdbstub_client.py`（純 Python、只實作本次需要的封包型別）直接對埠 2345 說 GDB remote serial protocol，`lldb` 完全沒試（`gdbstub_client.py` 一寫成功就直接堪用，未比較 lldb 路線）。本機沒有、也沒有另外取得任何 GBA BIOS dump，全程用 mGBA 內建 HLE BIOS 開機，未使用任何未授權的 Nintendo BIOS 檔案。

### 反組譯結果：BIOS 解壓縮呼叫候選全部無法確認為真指令（強化版負面結果）

`games/shining-soul-1/tools/disasm_swi_calls.py`（新增）對第一輪 `scan_swi_calls.py --align2` 找到的每個 `swi 0x10`–`0x18`（BitUnPack／LZ77／HuffUnComp／RLUnComp／Diff8bit／Diff16bit）候選位址，往回找最近的 THUMB `push {..,lr}` 當函式起點錨點，用 capstone 正向反組譯到候選位址，檢查是否乾淨落在一個 `svc` 指令上。

結果：137 個候選中，128 個「未對齊或不是 svc」、11 個「無法解碼」、只有 **9 個**「乾淨落在 svc 上」。但人工檢視這 9 個的反組譯結果後判斷**沒有一個是真指令**——往回展開的所謂「函式」裡出現大量在 ARM7TDMI（GBA CPU）上根本不存在的指令（例如 `bxns`〔ARMv8-M 專屬〕、`mrrc`／`cdp2`／`stc2`〔ARM 協處理器指令，GBA 沒有協處理器〕），以及跳到 ROM 範圍外或明顯不合理位址的分支。這代表 THUMB 的密集編碼空間（幾乎任何 16-bit pattern 都能解碼成某個合法指令）讓「反組譯不出錯」本身是很弱的判準——這批位元組其實落在圖形／資料區，只是湊巧被解碼成語法合法但語意荒謬的指令序列。**結論：第一輪找到的全部 137 個 BIOS 壓縮呼叫候選，經反組譯覆核後沒有一個能確認是真的、會被執行到的呼叫點**；連帶地，「文字資料經 BIOS LZ77／Huffman／RLE 壓縮」這個假說目前完全沒有直接證據支持（也沒有被排除——只是這條路線用簡單反組譯走不通，需要從進入點做完整的遞迴控制流重建才有機會分辨程式碼與資料，這超出本輪範圍）。

腳本本身的方法論限制寫在 docstring 裡（錨點探測是啟發式、暫存器回溯只認得 `mov`／`ldr [pc,#n]` 的簡單情形），可重跑：

```sh
/usr/bin/python3 games/shining-soul-1/tools/disasm_swi_calls.py \
  games/shining-soul-1/roms/base/Shining_Soul_JP_AHUJ8P.gba
```

### mGBA GDB 即時記憶體觀察：確認畫面渲染、字型格式、部分字形資料的 ROM 位置

流程：`mgba -g <rom>` 背景啟動（無視窗環境下 `screencapture` 回報 `could not create image from display`，代表這台機器沒有可用的螢幕/顯示 session，無法直接截 mGBA 視窗——因此改用 GDB 連線讀記憶體、自己解碼 VRAM 內容並渲染成 PPM/PNG 圖片來做視覺核對，而不是依賴螢幕截圖），`gdbstub_client.py` 連線後 `c`（continue）＋計時＋`\x03`（interrupt）交替，讀 I/O 暫存器（`DISPCNT`／`BGxCNT`）、VRAM（`0x06000000`，96 KiB）、OAM（`0x07000000`）、調色盤（`0x05000000`）。

**重要操作細節（供下次重跑參考，避免重踩坑）**：
- mGBA 的 GDB stub 一個連線失效後**不會**乾淨接受下一個新連線（`connect()` 會逾時掛住）——每次要重連都必須先 `pkill` 掉舊的 mgba 行程、重開一個新的，而不是重用同一個埠。
- 就算同一條連線內，兩個封包**緊接著送**（沒有間隔）有一定機率讓 stub 沒回應（`_read_packet` 逾時）——`gdbstub_client.py` 的 `send()` 已加上送出前 50ms 延遲＋逾時重試一次，加了之後穩定。這代表本節所有結果都是在單一條連線、全程不中斷的情況下跑出來的。

**跑到的畫面**：開機後 run 約 10–30 秒（未按任何鍵），`DISPCNT=0x1240`（mode 0，BG1＋OBJ 啟用，OBJ 1D mapping），VRAM 內容在幾個固定畫面間循環（推測是 title 畫面的雲層背景動畫迴圈，OAM／調色盤在此期間完全不變），判斷此時已到達**標題畫面**（logo＋著作權年份＋按鍵提示），尚未進一步往下（見「未解決」）。

- ✅ **已確認**：BG1（`charbase=0x6000000`／`screenbase=0x600e800`／4bpp）的完整 32×32 tilemap，用本輪新增的 `games/shining-soul-1/tools/render_vram_tiles.py` 依調色盤（`0x05000000`）解碼渲染成圖片，畫面**直接是「SHINING SOUL」標題 logo＋雲層背景＋「©SEGA 2002」**（見 `research/title-screen-bg1-render.png`，已存檔）——這是本專案第一次拿到「渲染出的畫面內容與已知遊戲外觀吻合」等級的證據，不再只是位元組層級推測。
- ✅ **已確認**：GBA 4bpp、8×8px、32 bytes/tile 的標準 tile 格式假設正確——如果格式假設錯誤，解碼出來的會是雜訊而不是可辨識的 logo 圖案；渲染結果的清晰度本身就是格式正確性的證據。
- ✅ **已確認**：OAM（`0x07000000`）目前有 6 個啟用的 sprite（shape=1／size=2＝32×16px＝4×2 tiles，OBJ 1D mapping，palette bank 14），tile 編號 0/8/16/24/32/40，依 OAM 的實際 x/y/tile 排列（而非單純循序畫格子）正確合成後，畫面是**「シャイニング・ソウル」（片假名）在上、「PUSH START」（拉丁字母）在下**（見 `research/title-screen-push-start-obj-render.png`）——這是本輪唯一一處「看到疑似字型資料，且經視覺核對確認真的是文字（片假名＋拉丁字母混排）」的證據，不是猜測。
  - **重要教訓（已修正的錯誤路線）**：分析初期曾把 VRAM offset `0xE800`–`0xF800` 這段資料當成 charblock 裡的一般 tile 像素資料，粗略渲染後主觀覺得像一張完整 ASCII 字母表加片假名表，一度以為找到了整個字型系統。後來核對 GBA VRAM 版面配置才發現：`0x6000000`–`0x6010000`（charblock 0–3）中，screenblock 28–31（也就是位元組 offset `0xE000`–`0x10000`）依照 BG0／BG1 目前的 `screenbase` 設定，其實是**畫面／tilemap 資料**（16-bit 的 tile 編號＋翻轉旗標＋調色盤欄位），不是原始像素——把結構化、遞增的 tilemap entry 位元組硬解成 4bpp 像素，剛好因為數值規律而長得像「有規律的方塊圖案」，在縮圖尺度下誤判成文字表。這不是真的字型資料，該「發現」已撤回。教訓：**先核對 VRAM offset 落在 charblock（tile 像素資料）還是 screenblock（tilemap）範圍，再決定怎麼解碼**——`render_vram_tiles.py` 的 docstring 已記錄這個區分，供下次直接照做。
  - 真正查到片假名＋拉丁字母的，是 OBJ tile 區（`0x6010000`–`0x6018000`，這段沒有 screenblock 混用問題，恆為像素資料），且是用 OAM 的實際 sprite 排列（而非單純方格）合成才第一次看對，純方格排列（`--cols 8`）合成的中間結果其實是破碎、看不太懂的「PUS.. H ST.. HK1」——這也記錄下來，提醒**渲染 OBJ tile 資料一定要照 OAM 的實際擺放方式合成，單純按 tile 編號順序排格子會把字元拆散、误导判斷**。
- ✅ **已確認**（ROM 來源，部分）：組成「シャイニング・ソウル／PUSH START」畫面的 48 個 OBJ tile（VRAM `0x6010000`–`0x6010600`）逐格在 ROM 內做精確位元組搜尋，40/48 格（扣除 5 格全零、3 格疑似落在無關資料區的假陽性短匹配）在 ROM `0x62AA44`–`0x62B8E4`（約 3.7 KiB 範圍內，非完全連續）**找到逐位元組相同的原始拷貝**，且觀察到重複字元（如兩個「S」）在 ROM 裡對應**同一個**來源 tile、於執行期被複製到 VRAM 兩個不同位置——這是「每個字元一份共用原始字形、依需要拷貝到畫面對應位置」這種正常字型系統的典型特徵，不是逐畫面各自畫一張獨立點陣圖。**這批 tile 資料是逐位元組原封不動被拷貝進 VRAM，沒有經過 LZ77／Huffman／RLE 解壓縮**（若經壓縮，VRAM 內容不會與 ROM 內容逐位元組相同）——這與本節「BIOS 壓縮呼叫候選全部無法確認」的反組譯負面結果方向一致（至少這批資料確定不是靠 BIOS 解壓縮常式產生的）。
  - **尚未找到**：是哪段程式碼把 ROM `0x62AA44` 附近資料搬進 VRAM `0x6010000`——在 ROM 全域搜尋「word-aligned 4-byte LE 值落在 `0x0862A000`–`0x0862C000`」找不到任何命中，代表載入常式不是靠簡單的絕對位址常數池指標（可能是 halfword 對齊、runtime 加法算出、或透過某種索引表間接引用）；也還沒有找到「哪個位元組＝哪個字元代碼」的對照表（codepage），只確認了字形圖案本身存在、位置、格式。
- ⚠️ **未解決／不確定**：嘗試用 `gdbstub_client.py` 的 `write_mem` 直接寫 `KEYINPUT`（`0x04000130`）模擬按下 START／A 鍵（十次短暫 continue＋改寫交替，希望撐過按鍵邊緣觸發判定），想借此跳過標題畫面進入選單／對話等真正需要文字系統渲染任意字串的畫面，但畫面（`DISPCNT`、VRAM hash 循環模式）在模擬按鍵前後完全沒有變化。無法判斷是（a）mGBA 每畫格都用真實主機輸入狀態覆寫掉這個位址、我們的寫入根本沒撐過一個畫格，還是（b）此時遊戲邏輯本來就還不接受輸入（例如固定長度的不可跳過開場動畫尚未跑完），還是（c）其他原因。**這是本輪最大的未竟事項**——目前只確認了標題畫面的靜態字形資料，還沒有拿到任何「同一批字形 tile 被組成第二種、不同的字串」這種更強的「這是可重用字型」證據（雖然「シャイニング・ソウル／PUSH START」內部已有重複字元共用來源 tile 的證據，一定程度上支持是真字型而非純美術點陣圖，但只看過一組字串仍嫌單薄）。

以上三支新工具（`disasm_swi_calls.py`、`gdbstub_client.py`、`render_vram_tiles.py`）都在 `games/shining-soul-1/tools/`，全部唯讀（`gdbstub_client.py` 的 `write_mem` 是唯一寫入操作，只寫模擬器的執行期記憶體，不寫 ROM 檔案本身）。

## 第三輪偵察（跳過標題畫面成功；找到字型載入路徑但未找到 codepage）

工具環境同第二輪（`mgba` 0.10.5、`/usr/bin/python3` 的 capstone、`gdbstub_client.py`）。本輪對 `games/shining-soul-1/tools/gdbstub_client.py` 新增了 watchpoint（`Z`/`z` 封包，讀/寫/讀寫三種）、暫存器寫入（`P` 封包）、以及會阻塞等待非同步 stop-reply 的 `cont_and_wait()`，取代單純的「寫記憶體＋短暫 continue／interrupt 交替」。這批協定細節（欄位格式、成功／不支援的回應）是直接對照 mGBA 0.10.5 原始碼 `src/debugger/gdb-stub.c` 核對過的，不是從通用 GDB remote protocol 文件猜的——mGBA 的 stub 是部分實作，值得下次直接看程式碼再用。

### 根因確認：直接寫 `KEYINPUT` 為什麼從第一輪就注定無效

對照 mGBA 0.10.5 原始碼 `src/gba/io.c`（已核對，非 `master` 分支臆測）`GBAIORead()` 函式的 `REG_KEYINPUT` case：

```c
case REG_KEYINPUT: {
    ...
    if (gba->keyCallback) {
        gba->keysActive = gba->keyCallback->readKeys(gba->keyCallback);
        ...
    }
    uint16_t input = gba->keysActive;
    ...
    gba->memory.io[address >> 1] = 0x3FF ^ input;
}
```

這段程式碼在**每一次**遊戲程式碼讀取 `KEYINPUT` 時都會重新執行，把 `gba->keysActive`（來自實際主機輸入來源，這台無顯示 session 的機器上恆為「無按鍵」）重新寫回 `gba->memory.io[]`。也就是說，`gdbstub_client.py` 的 `write_mem` 對 `KEYINPUT` 位址的任何寫入，都會在遊戲程式碼下一次讀取該暫存器時被無條件覆寫——這不是時間掌握或位元極性的問題（上一輪懷疑的方向），而是**架構性地不可能透過記憶體寫入模擬按鍵**：GDB 的 `m`/`M` 封包只能碰到 `gba->memory.io[]` 這個「快取」，碰不到真正決定其值的 `gba->keysActive`／`keyCallback`（那是模拟器行程自己的 C 結構欄位，不在 GBA 位址空間裡，GDB stub 的目標記憶體空間也搆不到）。這個結論已對照兩個版本的原始碼（`master` 與確認正在使用的 `0.10.5` tag）核實，兩者程式碼一致。

### Goal 1 成功：用讀取 watchpoint＋暫存器覆寫跳過標題畫面，一路推進到存檔選擇畫面

既然寫記憶體行不通，改用讀取 watchpoint（`Z3`）盯住 `KEYINPUT`（`0x04000130`），在遊戲程式碼**執行讀取指令那一刻**（`gba->memory.io[]` 剛被寫入正確值、CPU 尚未把它讀進暫存器完成之前）用 `P` 封包直接覆寫「剛讀到這個值的目的暫存器」（本例是 `r1`），連續覆寫多個畫格（模拟「按住」），再放手讓後續幾個畫格自然讀到「放開」的值（製造完整的按下→放開邊緣，同時涵蓋「持續按住判斷」與「邊緣觸發判斷」兩種遊戲邏輯寫法）。

**重要操作細節（下次重跑必讀）**：
- 遊戲一開機（`pc=0`）就有 KEYINPUT 讀取——但那是開機／系統初始化階段的讀取（本輪在 `pc=0x0800077a`／`lr=0x0800103f` 這個位址捕捉到，開機後僅約 0.1–0.3 秒內就會命中），此時 `DISPCNT` 還在開機動畫的中間過渡狀態（本輪見過 `0x4012`，mode2，明顯是不同於標題畫面的另一個過渡畫面，很可能是 SEGA／片頭 logo 的縮放動畫），對這個讀取覆寫暫存器**完全沒有效果**——遊戲邏輯此時大概率還在跑固定長度、不讀取／不處理輸入的開場流程。**必須先讓模擬器自由跑到確認的穩定標題畫面（`DISPCNT == 0x1240`，第二輪已確認的值）再設 watchpoint**，本輪用「`c` 幾秒＋`interrupt` 檢查 `DISPCNT`＋不符合就再 `c`」的迴圈做到這件事，實測約 5 秒（機器全速執行，非依賴真實時鐘）就能穩定到達 `0x1240`。
- 命中的 KEYINPUT 讀取指令位址（`pc=0x0800077a`）在標題畫面穩定狀態、乃至於後續所有畫面，都是**同一個位址**——這是遊戲引擎一個共用的「每畫格讀一次輸入」工具函式，不是每個畫面各自寫一份輪詢邏輯，所以同一套 watchpoint／覆寫手法可以直接套用到後續畫面，不需要每個畫面重新定位輪詢點。
- 覆寫值：`KEYINPUT` active-low，10 個有效位元，「沒按」讀回 `0x3FF`；本輪用 `0x3FF & ~0x09`（同時按 Start 位元3與 A 位元0）模擬「按下 Start 鍵進入下一步」，後續用 `0x3FF & ~0x01`（單按 A）模擬「確認／選取」。每次覆寫維持 20–30 個連續畫格再放手，實測足夠讓遊戲的邊緣判斷或持續判斷都能感應到。

**確認跑到的畫面（依序，皆已渲染＋人工核對，非猜測）**：
1. **模式選擇畫面**（`research/mode-select-screen-obj-render.png`，OBJ tile 合成，用 OAM 實際座標／形狀／調色盤欄位而非單純方格排列）：標題「シャイニング・ソウル」縮小移到上方，下方新增兩行可選項目——「シングルプレイモード」（單人遊玩模式，橘色高亮＝目前選取項）與「マルチプレイモード」（多人遊玩模式，綠色＝未選取）。這批文字使用**與標題畫面「PUSH START」不同的全新片假名字形 tile**（VRAM OBJ tile 編號 44–67，原本只用到 0–47），證實 OBJ 字型系統確實是「共用同一批渲染機制、依畫面動態載入不同字符」的可重用字型，而不是每個畫面各自的專屬美術點陣圖——這正是第二輪報告裡標記為「證據偏弱、只看過一組字串」的缺口，本輪已補上第二組獨立字串。
2. **存檔選擇畫面**：`DISPCNT` 變為 `0x1d40`（BG0／BG2／BG3／OBJ 四層同時啟用，之前的標題／選單畫面只用 BG1＋OBJ），BG0（screenbase `0xe000`）目前為空／未使用內容，BG2（screenbase `0xf000`，`research/save-select-screen-bg2-char-stats-render.png`）顯示 4 組角色狀態預覽，各自有「Lv.」「エリア」（區域／地圖）「ATK」「DEF」「DEX」「STR」「VIT」「INT」等英文縮寫＋日文標籤混排的屬性欄位（模板尚未填入實際數值，符合「空白存檔」的預期），BG3（screenbase `0xf800`，`research/save-select-screen-bg3-file-slots-render.png`）顯示「FILE 1」「FILE 2」「FILE 3」「FILE 4」四個存檔格與「SELECT」「PAGE」等純 ASCII 字樣，格子本身是純色矩形 UI 元件（非文字）。四個 BG 共用同一個 charbase（`0x0`），只是 screenbase 不同——這代表整組 UI 文字／圖塊共用同一份 4bpp tile 字符資料，佐證這是統一的文字＋UI 渲染系統，不是分散、各自為政的美術資源。

### Goal 2：找到字型／圖塊搬入 VRAM 的真實呼叫鏈，但「codepage 索引邏輯」仍未找到（誠實記錄一次錯誤路線）

**先記錄一次繞路**：一開始直接對已知的字型 tile 目的位址之一 `VRAM 0x06010000` 設寫入 watchpoint（`Z2`），命中後回溯發現來源是 ROM `0x0846fee4`（不是已確認的字型範圍 `0x62AA44`–`0x62B8E4`）——追查後這是**雲層背景動畫**的其中一格畫面，每約 10 個畫格重繪一次同一份 32 bytes（8-word）資料到同一個 tile 槽位，恰好與字型 OBJ tile 集合共用位址空間但屬於不同子系統。這代表第二輪報告裡「40/48 格...找到逐位元組相同的原始拷貝」時被排除的那 8 格假陽性裡，至少有 1 格（`0x6010000` 本身）其實正是被這個背景動畫覆寫的槽位，不是字型系統的一部分——這修正並非推翻第二輪的字型位置結論（那 40 格本身仍然成立），只是釐清了哪些 tile 編號屬於哪個子系統。改成直接對**已確認的字型來源** ROM `0x0862AA44` 設**讀取** watchpoint 後，才穩定命中真正的字型搬移路徑（約 3.5 秒內命中，遠比寫入 watchpoint 卡在背景動畫迴圈快得多）。

**已確認**（透過即時單步追蹤，非靜態猜測）：
- 字型 tile 資料透過**真正的 `swi`（BIOS CpuSet／CpuFastSet）指令**搬入 VRAM，不是簡單的 CPU 迴圈手動複製，也不是本輪之外任何形式的自訂壓縮——單步追蹤清楚看到 PC 落在 ARM 異常向量 `0x00000008`（SWI vector）。這與第二輪「137 個壓縮相關 swi（`0x10`–`0x18`）候選全部無法確認」的負面結果**不衝突**：此處用的是搬移／填充類 BIOS 服務，根本不在第二輪掃描的 `0x10`–`0x18`（壓縮專用）範圍內，兩者是互補而非矛盾的發現。**具體 swi 立即值已直接讀取 ROM 位元組＋capstone 反組譯確認、非推測**：ROM file offset `0x503bc`–`0x503bf` 是 `svc #0xc; bx lr`（`CpuFastSet`），`0x503c0`–`0x503c3` 是 `svc #0xb; bx lr`（`CpuSet`）——兩個都是「一條 svc 立刻接 `bx lr`」的極小包裝子程式（wrapper stub），不是 swi 指令本身所在的迴圈主體。
- 這兩個 swi wrapper 是被一段可反覆執行的**通用「傳輸佇列」迴圈**（ROM file offset 約 `0x11a0`–`0x11fe`）用 `bl` 呼叫的：迴圈走訪一個 12-bytes-per-entry 的陣列（每筆＝來源指標＋目的指標＋模式／長度欄位），依 entry 的 mode 欄位高位決定呼叫 `bl 0x80503bc`（file offset `0x11c4`，小型/固定大小傳輸）還是 `bl 0x80503c0`（file offset `0x11e6`，一般傳輸），執行完後歸零佇列長度。（先前一版文件把 `0x080011c6` 誤寫成「swi 呼叫本身發出的位址」——那其實是 `bl` 呼叫指令的位置，swi 真正所在位置是上一句確認的 `0x503bc`／`0x503c0`；已訂正。）這個迴圈同時服務**至少兩種資料**：本輪観察到的字型 tile 搬移，以及背景雲層動畫的逐格重繪（見上方繞路記錄）——換言之這是遊戲引擎共用的「VBlank 佇列化 VRAM／OAM／調色盤更新」機制，不是字型專屬的載入器。
- 反組譯（`file offset 0x1140`–`0x1220`，`/usr/bin/python3` + capstone，THUMB 模式，已用 `cpsr` 的 T bit=1 核對過模式判斷正確）看到這段迴圈本身結構清楚（`bhs`／`bge`／`blo` 分支、`bl` 呼叫、`ldr`/`str` 存取 12-byte entry），品質遠高於第二輪對壓縮 swi 候選的反組譯（那批因為錨點是猜的，反組譯出大量 GBA 不存在的協處理器指令；這次錨點是即時追蹤出來的真實執行位址，反組譯結果乾淨自洽，沒有出現任何不合理指令）。

**未確認／已測試但否定的假設**（誠實記錄，避免下次重工）：
- 原本猜測 ROM `0x08001154`（一段看起來像「把 (src,dst,mode) 三個參數存進佇列 entry」的小函式）就是字型專屬的 enqueue／推入呼叫點，在該位址設中斷點後連續攔截**150 次**呼叫，`r0`（來源指標）**沒有一次**落在已確認的字型 ROM 範圍（`0x0862AA44`–`0x0862B8E4`）內——全部是 OAM 影子緩衝區（`0x03001d40`→`0x07000000`）、調色盤影子緩衝區（`0x03002950`→`0x05000000`）之類每畫格固定執行的「影子緩衝區→硬體」搬移，與字型無關。改成直接在傳輸佇列迴圈頂端（`0x080011b4`）設中斷點、每次命中都窺視 `[r4]`（entry 的來源欄位）連續攔截 **400 次**，同樣沒有看到字型範圍的來源值。這代表：**字型 tile 的搬移確實有經過這個共用佇列迴圈**（已用讀取 watchpoint 直接證實過一次，錯不了），**但目前找到的「推入」函式候選（`0x08001154`）測試後被否定，不是字型使用的推入路徑**——可能是另一個獨立的推入函式，也可能字型搬移在開機極早期只發生一到兩次、不落在本輪攔截的畫格範圍內，尚未查明。**這是本輪明確標記為「已測試、未證實」的一條假設，不當成結論使用**。
- 因此，「哪一段程式碼決定要把哪個字型 tile（對應哪個字元代碼）排進佇列」——也就是 ROADMAP 步驟 3 要找的「字元代碼→字形 tile 索引」codepage 對照表——**仍未定位**。本輪找到的是它下游的通用搬運機制，不是它本身的決策邏輯。下一輪建議直接從上方「Goal 1 意義」提到的 BG2／BG3 tilemap tile-index 序列反查，可能比繼續往上追這條呼叫鏈更快。

### `gdbstub_client.py` 協定備忘（供下次直接照做，不必重新對照原始碼）

- `Z<type>,<addr-hex>,<kind-hex>` / `z<type>,...`：`type` 0/1＝中斷點，2＝寫入 watchpoint，3＝讀取 watchpoint，4＝讀寫 watchpoint；成功回 `OK`，不支援的 type 回空字串（不是錯誤碼，呼叫端要對兩種都判斷）。
- `P<regno-hex>=<value>`：`value` 是暫存器 4 bytes 的**小端序**（ARM target 位元組序）hex，跟 `g` 封包讀出來的格式一致，**不是**直接把數值當十六進位數字編碼——寫 `write_register()` 時務必用 `value.to_bytes(4,'little').hex()`，不要直接 `f'{value:08x}'`。
- `c`（continue）不會立即回應；等到中斷點／watchpoint 命中才會收到非同步的 `T05...;` 封包（watchpoint 命中會附 `watch:`／`rwatch:`／`awatch:` 加位址）。這個封包本身仍是標準 `$...#xx` framing，可以直接用既有的 `_read_packet()` 消化，只是要给一個遠比一般指令回覆更長的逾時（`cont_and_wait()` 已內建）。
- **中斷點／watchpoint 命中後，如果不先 `s`（single step）一次就直接再 `c`，會立刻在同一個 PC 上重新命中**（尤其是寫入 watchpoint 卡在一個緊湊複製迴圈裡時，會看起來像「暫存器完全不變」，很容易誤判成單步沒有生效——其實是同一個未跨過的指令被反覆重新命中）。命中後一律先 `s` 一次再繼續，除非明確要利用這個特性連續攔截同一個輪詢點（例如本輪對 KEYINPUT 讀取的做法，那裡的重複命中是預期行為，因為每次都是新的一個畫格）。

## 第八輪偵察（解出句子字元代碼序列本身的儲存格式——任務指定的核心缺口已完成）

完整分析、逐層追蹤過程、解碼公式與可重跑步驟見專門的
`research/obj-sentence-string-format.md`（分析結論，不含遊戲原文大段抄錄，可提交），
此處只摘要重點。本輪目標：第七輪明確留下的唯一未解問題——「職業を選んでください」這句話
**字元代碼序列本身**存在 ROM 何處、以何種格式編碼（相對於第七輪已解出的「代碼→字形位址」
定址公式）。

**已確認、高信心**：

1. **找到句子字元代碼陣列本身**：以「單字元/中斷點入手，逐層往上追呼叫鏈」的方法（見
   research 文件「發現過程」，從第七輪已知的 enqueue 呼叫點 `0x080034d0` 開始，往上
   追了兩層呼叫者），找到真正的字串走訪迴圈（ROM file offset `0xe8f0`–`0xe944`，所屬
   函式入口 `0xe8bc`）：`r5` 暫存器是一個指向 **NUL（`0x0000`）結尾的 16-bit 代碼陣列**
   的指標，每次迭代 `ldrh r2,[r5]; ...; adds r5,#2` 讀一個字元代碼、前進 2 bytes，直到
   讀到 `0`。對職業選擇畫面的這個函式入口設中斷點，直接讀出 `r0`（函式自己的第一個參數，
   等於 `r5` 初值）＝ ROM file offset **`0x499b1a`**，內容逐一對應「職業を選んでください」
   10 個字元；顏色選擇畫面同法找到「色を選んでください」在 `0x499b3e`（9 個字元）。
2. **解碼公式**：`category = (code>>8)&0xF`（字型／字符池選擇器，0＝假名，觀察到的漢字
   用 2／3，其餘未見）、`glyph_entry_index = (code&0xFF) - 1`（池內索引）。用「職業を
   選んでください」裡 7 個假名（を／ん／で／く／だ／さ／い）驗證：`glyph_entry_index` 與
   第七輪已知的五十音 `char_idx` 精確滿足 `glyph_entry_index = char_idx + 1`，七點
   全部吻合，零例外。
3. **雙畫面交叉驗證**：「職業を選んでください」與「色を選んでください」共用的尾段
   「選んでください」（7 字元）在兩個獨立位址的代碼陣列裡逐位元組完全相同，「を」的代碼
   也相同，只有各自專屬的開頭漢字不同——這是「同一套字元代碼系統跨畫面共用」的直接證據。
4. **附帶發現第五張獨立 ROM 表**：往上追呼叫鏈過程中，額外確認 enqueue 呼叫的來源指標
   （即第七輪的 `r0`）對假名而言精確等於 `0x08469f60 + char_idx*8`——一張**每格

## 第十二輪偵察（第一份本機原文表＋第一批可提交翻譯帳本——文字系統偵察轉入實際翻譯階段）

前十一輪把文字系統解到能讀懂 99.97% 的真實對話代碼，但「知道每個代碼對應哪個 ROM 位址的
像素資料」跟「知道那個像素資料是哪個 Unicode 字」是兩回事——本輪任務要求把這個落差第一次
攤開來看：建一個真正逐代碼解碼成文字的抽取器，而不是像前幾輪那樣只做視覺渲染＋人工核對。

**新增 `tools/decode_strings.py`**：重用（不重寫）`extract_string_pool.walk_pool()`／
`scan_string_pools.looks_like_header_start()`／`scan_sentence_strings.decode_code()` 等
既有函式，走訪對話池（`0x499000`–`0x500000`）與怪物名稱表（`0x460000`–`0x46abe4`——**本輪
收窄**，原始 `0x460000`–`0x470000` 範圍會掃進第七輪確認的 OBJ 主字形像素表本體
`0x46abe4` 起，圖形位元組湊巧滿足池標頭文法，產生大量 `\nあ`／`ぐぷ` 這類單字元雜訊

**三層信心分級**（任務明確要求的「preserve the distinction」）：
1. **confirmed**——假名主表 `char_idx` 0–70（第七／八輪 7 點零自由參數驗證）＋
   12 個個別驗證過的漢字身分（剣／士／職／色／業／選／了／失／別／妨／害／難，見
   `tools/decode_strings.py` 的 `KANJI_MAP`，每個都附出處）。**這不是解出的漢字碼表**——
   四張漢字表（`category` 1–4）本身合計已知有上百格非空的像素資料（第十／十一輪），
   但目前只有這 12 個索引額外被追蹤到實際 Unicode 身分，其餘全部落回 unmapped。
2. **provisional**——片假名（`char_idx` 80–150，第七／九輪僅有版面順序描述、非位址交叉
   驗證的假說）、促音「っ」（`char_idx` 79，單一資料點）、以及**本輪新發現**的長音符
   「ー」（`char_idx` 247：`0x00f9` 在第十一輪已核實的真實句子「ゲームを終了すると
   セーブされます」代碼陣列裡出現兩次，位置精確對應「ゲーム」「セーブ」裡的長音符，

   每筆用到這層的記錄，`provenance` 都會附註「CONTAINS PROVISIONAL-TIER GLYPH(S)」，
   翻譯／校對時應知道這比純假名句子少一層驗證。
3. **unmapped**——其餘全部，輸出 `{unmapped_glyph:<category>:<glyph_entry_index>}`，

認得的字符（含 provisional 層）而非純平假名比例」判準的每行雜訊過濾器後，降到 218 筆。

**skill 使用心得（已同步構思，若日後修訂 skill 文件時可採用）**：「已知字形像素位置」
與「已知字形的 Unicode 身分」這兩件事的落差，在字型定址工作本身（第七–十一輪）感覺
不明顯——因為驗證漢字定址公式時，只需要 2 個獨立位址zero-free-parameter 吻合就能
「確認整張表」，但那只確認了「表存在、公式對」，不代表表裡其餘上百格的字身分被知道。
真正把這個落差變得無法忽視的時刻，是**第一次要把代碼陣列變成可以拿去翻譯的實際文字**
（本輪的任務）——這之前的所有「渲染整句核對通順」都還是人眼看圖，不需要程式知道每個
字是誰。這對其他遊戲的啟示：字型定址工作完成不等於「可以開始建原文表」，中間還有一道

數 / 該 category 已知非空格數」這種比例單獨追蹤，而不是被「定址公式已解出」的成就感
掩蓋掉。

## 第十三輪偵察（OCR＋語料庫統計投票擴充漢字身分對照，翻譯批次二）

本輪任務：第十二輪明確標記的最大缺口——五張漢字像素表（`category` 1–4）合計已知
上百格非空資料，但只有 12 個索引有確認的 Unicode 身分，導致 88.5% 的解碼記錄至少
帶一個 `unmapped_glyph` 佔位符。本輪執行 `.agents/skills/gba-localization/SKILL.md`
「Two separate problems」一節文件化、但本遊戲前十二輪從未實際跑過的
「render-whole-string + OCR + corpus-wide statistical alignment」手法，這是本專案第一次
在黃金太陽以外的遊戲上真正執行這個模式。全程未啟動 mGBA（顧問建議：OCR 不需要調色盤，
灰階／二值渲染即可，跳過模擬器同時讓「使用前先清孤兒行程、結束前清自己行程」這條規範
自動滿足——本輪開始與結束時 `ps aux | grep mgba` 皆為空）。

### 渲染校準：LANCZOS 平滑縮放大幅優於 NEAREST 最近鄰

新增 `tools/ocr_render_lines.py`，把任意 NUL 結尾代碼陣列渲染成灰階 PNG（任何非零
4bpp 像素值＝黑墨，白底，不依賴調色盤/mGBA）。用 9 句已由人工核對過完整原文的既有
句子（`0x499b1a`／`0x499b3e`／`0x499b5e`／`0x499aa2`／`0x499e1a`／`0x49cd60`／
`0x49d594`／`0x49da64`／`0x49e42c`，來源：第七～十一輪 research 文件）當校準用的
ground truth，掃過 `{4,5,6,7,8} 倍縮放 × {正常,反相} × {NEAREST,LANCZOS}` 共 60 張
渲染圖跑 Apple Vision OCR，用正規化 Levenshtein 距離對已知原文評分。**結論**：對原始
1 倍二值渲染做 LANCZOS 平滑縮放，比對已放大圖做 NEAREST 最近鄰縮放的平均誤差低了
一半以上（最佳 LANCZOS 組合 ≈0.20，最佳 NEAREST 組合 ≈0.26）；縮放倍率 5/6/7 統計上
難以區分（0.21–0.24），黑字白底些微優於白字黑底。最終採用 `scale=6、LANCZOS、黑字
白底`，但**即使是最佳組合，OCR 對這套自訂點陣字型的正規化編輯距離中位數仍高達
0.229**（見下）——這不是可信度足夠直接採信單句的品質，全程仰賴「跨語料庫累積投票」
而非任何單句讀出結果。

### 語料庫準備與投票：新增三支工具

`tools/ocr_prepare_corpus.py`（不重用既有的 `decode_strings.line_passes_filter()`——
那個過濾器要求「≥60% 的 category-0 代碼已經認得」，這對本輪目的是循環論證：正是想找

結構性過濾（至少 1 個 category 1–4 代碼、至少 2 個已確認假名錨點、排除 4 個已知
「高位異常」代碼），對兩個已知語料範圍（對話池、怪物名稱表）逐行走訪，5,262 行中
選出 267 行。`tools/ocr_render_lines.py --lines-file` 批次渲染，`swiftc -O` 預先編譯
`core/ocr/vision_ocr.swift`（避免每次呼叫都重新編譯的秒級開銷）後一次呼叫辨識全部
267 張圖（25 秒）。`tools/ocr_align_vote.py` port 自
`games/golden-sun-the-lost-age/tools/infer_ja_codepage.rb`（唯讀，未修改；黃金太陽

`(category, glyph_entry_index)` 二元組；「已知」判定重用 `decode_strings.decode_glyph()`
本身（confirmed／provisional 皆視為錨點）；NFKD 分解（濁音／半濁音假名的正規分解，
兩邊都要做，否則が／ぱ 這類字全部對不上）與代價矩陣（相符 0、未知位置對到合理候選
0.15、對到不合理候選 0.8、已知位置衝突 1.5，插入/刪除 1.0）原樣照搬；品質門檻沿用

p70–p80 之間，200/267 行通過）。220 個 `(category, index)` 位置獲得至少 1 票。

### 驗收：先做外形肉眼核對，再做語意上下文核對——兩層檢查各自抓到不同種類的假陽性

**第一層（`tools/ocr_contact_sheet.py`，ROM 像素 vs. 系統字型渲染候選字並排）**：
只對「≥4 票且過半數候選佔比 ≥75%」的位置產生對照表（比參考實作／顧問建議的
「≥3 票、≥60%」門檻更嚴——第一次用 0.6 門檻掃時已經看到假陽性，見下），逐條肉眼比對
ROM 實際點陣圖案與候選字（用 Hiragino Sans GB 渲染，簡體字型但常見漢字字形與日文
漢字通用）是否形似。**本層排除**：`category` 0（假名）候選全數排除——兩個不同
`char_idx`（166、234）都近乎一致投給「ー」（長音符），但兩者 ROM 點陣實際都是短勾狀
筆畫，完全不像已確認 `char_idx=247` 那個真正的水平長音符圖案，判斷 Vision 對辨識不出的
筆畫有偏向猜「ー」的傾向，任何票數都不可信；片假名「イ」「ツ」候選同樣因為外形明顯
不符被排除；`(1,184)` 候選「口」雖然 3/3=100%，但 ROM 圖案是幾乎全空、只有一個小點，
明顯不是方框狀的「口」——提醒「小樣本 100% 一致」不等於「有意義的訊號」。

**第二層（比第一層更關鍵，也是本輪最重要的方法論收穫）**：把通過第一層外形核對的
27 條候選（18 個 category 1＋8 個 category 3＋1 個人工上下文覆核條目，見下）暫時
寫入解碼器、重新解碼整個語料庫，**逐句重讀新出現的乾淨句子找語意問題**（顧問建議：
「一個字讀錯二十次會產生二十張一致但錯誤的票」——純粹統計不出這種系統性誤讀，只有
把解碼結果放回句子脈絡裡讀才抓得到）。這一層額外揪出 4 個 `category` 3 條目，全部
外形肉眼核對時沒看出問題、票數與比例也達標，但代入真實句子後語意破碎：
- `(3,19)`「加」（4 票 75%）：所有真實出現都是「…を加すために」「…加したのですか」，
  但「加す」「加した」不是合法動詞變化（「加える」的過去式是「加えた」，沒有「加した」
  這個形式）。
- `(3,26)`「油」（6 票 100%）：所有出現都緊接在名詞/代名詞後、助詞前——「ボク油の手で」
  「あなた油だけです」「士油が」——這正是複數/群體語尾（類似「達」）該出現的位置分佈，
  「油」（油）完全無法文法上放進這個位置。
- `(3,56)`「飲」（4 票 100%）：出現在「…に大ダメージ」（對…造成大量傷害）、
  「…の防御力が下がる」（…的防禦力下降）——「飲」（喝/飲料）不可能承受傷害或擁有
  防禦力數值，真正字符更可能是「敵」「魔物」「族」一類名詞。
- `(3,216)`「背」（3 票 75%）：唯一乾淨出現是「[X]物がいっぱいです」（[X]物已經滿了）
  ——「背物」不是日文詞，但「荷物」（行李/物品）完美吻合，而且「荷」正是 OCR 自己
  票選時的第二名候選（1/4 票）——正確答案很可能當時就在票數清單裡，只是不是多數。

這 4 條**直接從 `KANJI_MAP_OCR_PROVISIONAL` 移除，不補上肉眼猜測的替代字**（本專案
一貫原則：寧可留白，不猜）。相對地，同一次重讀也帶來一個**非投票、上下文覆核**的

### 高頻未解位置直接像素判讀：category-0 主表的 punctuation／Latin 區塊（char_idx 151 起）

151 之後（緊接著已確認的片假名區 80–150）從未被檢視過——因為前十三輪的翻譯需求全部集中在

**方法**：這段區域不需要 OCR——直接渲染 `char_idx 151`–`260` 整段為帶座標標籤的網格圖

符號／全形／半形 Latin 字母／數字的標準區塊，形狀本身遠比漢字明確、不像漢字有「看起來像
但其實是另一個字」的混淆風險（例如「Ｕ」跟「Ｖ」形狀差異一望即知，不會有 OCR 誤讀那種
「同一個錯誤重複二十次」問題）。每個候選在「像素形狀」之外，額外用真實語料庫上下文交叉

本輪是新階段的第一次：前十四輪全部是唯讀偵察，本輪第一次嘗試把翻譯文字實際「寫回」ROM 並在

### 找空間：對五張字形表的可定址範圍（index 0–254）做逐格全零掃描

字串代碼格式（第八輪）`glyph_entry_index = (code & 0xFF) - 1` 意味著不論表本身實際多大，
透過正常字串機制能定址到的範圍上限是 index 254（`code` 低位元組頂多 `0xFF`）——這比第十／
十一輪推算出的「表格容量約 308 格」（相鄰表 base 的間距 / `0x80`）小得多，容量裡 254 之後的
部分（如 category 0 的 255–307）物理上存在於 ROM、也能被 `extract_kanji_fonttable.py` 這類
唯讀工具直接讀到，但**透過字串代碼機制永遠無法定址到**，因此對「插入新字形要放哪裡」這個問題
沒有實用價值，本輪對五張表全部只掃描 index 0–254：

| category | base | 0–254 內全零（空白）的 index | 空白格數 |
| --- | --- | --- | --- |
| 0（假名主表） | `0x46abe4` | 253–254 | 2 |
| 1 | `0x474584` | 0 | 1 |
| 2 | `0x47dfa4` | （無） | 0 |
| 3 | `0x4879c4` | 0 | 1 |
| 4 | `0x4913e4` | 0、**40–254** | 216（其中 40–254 連續 215 格） |

結論：五張表裡只有 **category 4 的 index 40–254**（215 格連續空白）是有實用規模的空間，
與第十一輪「category 4 表在 index 39 後乾淨截止、语料庫實際只用到 index ≤30」的既有記錄完全
吻合（不是新發現，是把舊發現量化成「可插入多少新字」的具體數字）。其餘四張表在可定址範圍內
幾乎全滿（category 2 甚至一格不剩），這是本輪對「選項 (a)：既有表 stride 內找空位」這個任務
指定的第一個調查方向的直接、量化答案——**只有 category 4 這一張表有意義，且容量有限
（215 格，遠不足以容納一套完整翻譯所需的漢字集，通常需要數百到近千個不同漢字）**。

任務原本列出的選項 (b)（ROM `0x660000`–`0x800000` 的 `0xFF` 填充區，第一輪已確認的約 1.6 MiB
空白容量）與選項 (c)（覆蓋既有除錯／罕用字串槽位）本輪都沒有用到——選項 (a) 在 category 4 就
已經有夠用的空間支撐這次 proof of concept，不需要動用選項 (b)（需要額外解出 IWRAM category
查表如何在開機時被填入才能真正把新 base 接上第 5–15 類）或選項 (c)（會顯式犧牲某段既有內容）。
但 215 格對「一整套翻譯」而言遠遠不夠，選項 (b) 的路線是下一步真正要走的方向（見下方「可規模化
設計需要什麼」）。

### 取字形像素：GNU Unifont 的 16×16 CJK 點陣，尺寸與本遊戲格式完全吻合，無需縮放

`extract_kanji_fonttable.py` 的 `decode_glyph_2x2()`（第七輪起沿用至今）確認每個字形槽是
128 bytes＝4 個 32-byte 4bpp 8×8 tile，以 `[左上,右上,左下,右下]` 順序拼成 16×16px——這正好
是 `vendor/fonts/unifont/unifont-17.0.05.hex.gz`（本專案既有素材，`core/fonts/
extract-unifont-subset.rb` 已在別處使用過）對寬字元（CJK）codepoint 的原生點陣尺寸
（64 hex 字元＝32 bytes＝16 列×16 bit），**不需要任何縮放，1:1 對應**——這是本輪選擇 Unifont
而非 `vendor/fonts/` 下其他點陣字型（`fusion-pixel-font`／`ark-pixel-font`，尺寸不明確是否
剛好 16×16）的直接原因。

调色盤方案：本輪連上 mGBA（見下）即時 dump 職業選擇畫面的調色盤，並對 category 0–3 四張已知
表的全部非零像素值做頻率統計，發現本遊戲字形固定用兩色風格——調色盤 index 2（深藍，約 58% 的
非零像素，幾乎都在字形外緣）與 index 1（白，約 42%，幾乎都在純內部像素），另有 index 12／13
（灰階）較少見、判斷是另一種本輪未重現的立體塗裝手法。轉換規則：對 Unifont 的 16×16 單色點陣
做「4-連通邊緣偵測」（有任一相鄰背景像素或落在邊界＝外緣，寫 index 2；否則＝內部，寫 index 1）。
Unifont 在這個解析度下筆畫幾乎都只有 1px 寬，實際轉換結果因此幾乎全部落在 index 2（外緣色）——
不是 bug，是 Unifont 筆畫寬度本身導致「內部」像素幾乎不存在，色彩仍然正確、字形依然清晰可讀
（見下方渲染結果）。

### mGBA GDB stub 在這台共用機器上的新教訓（值得寫進 skill）

本輪連線比過去任何一輪都更不穩定——同一時間這台機器上還有其他至少 3–5 個不相關遊戲的
mGBA/GDB session 同時在跑（不同 agent 的並行工作，非本輪產生，**本輪確認過這些行程都不是
Shining Soul I 的孤兒行程，全程沒有 kill 任何不相關的行程**）。具體症狀：
- `mgba -C ports.qt.gdbPort=<port> -g <rom>` 這個第二／三輪文件裡沒特別強調、但先前 session
  疑似依賴過的參數組合，本輪實測**完全沒有效果**——無論 `-C` 指定哪個埠，`-g` 實際監聽的
  埠恆為預設 `2345`（用 `socket.bind()` 直接測試埠是否真的被佔用來確認，比 `lsof`／`ps`
  更可靠——這台機器上 `lsof -i :<port>` 對其他行程持有的埠常常回報「空」，即使該埠確實在
  監聽，判斷是 sandbox 的可見性限制，不能信任 `lsof` 的陰性結果）。因此本輪全程改用預設埠
  `2345`。
- 就算用預設埠、也乾淨重啟了 mGBA 行程，**GDB stub 是否真的進入監聽狀態本身仍會偶發失敗**
  （進程存活、吃 CPU，但 `connect()` 逾時，且用原生 socket `bind()` 測試同一個埠也確認「沒有
  任何東西在監聽」——不是連線被拒絕，是真的沒有服務在那個埠上）。這與已知的「同一條連線用完
  不能乾淨接受下一個連線，要整個重開行程」問題（第二輪已記錄）是**不同的**新症狀——這次連
  「第一次連線」都會偶發失敗，重試（kill＋重開＋再試一次連線）就會恢復正常，本輪判斷是這台
  機器目前的高並發負載造成 Qt 事件迴圈啟動 GDB 執行緒的時機出現競態，不是本遊戲或本輪腳本的
  邏輯問題。**教訓：在共用、高並發的機器上，mGBA GDB stub 連線失敗要先重試（kill 舊行程、
  乾淨重開、再連一次），不要假設第一次連不上代表腳本或位址錯誤**——本輪原本一度懷疑是不是
  ROM 本身被寫壞了，額外多花了一輪「先不連線、只做 `bind()` 探測」的除錯才確認純粹是啟動時序
  問題，跟本輪寫入的 115 bytes ROM 修改完全無關（後續乾淨啟動即穩定重現、且開機後正常到達
  title 畫面，證明 ROM 本身沒有損壞）。

### 可規模化設計需要什麼（留給下一輪的具體待辦，任務明確要求先寫下、不在本輪嘗試解決）

本輪證明了機制本身可行，但用的方法有明確、已知的規模上限，如實列出：

1. **新字形空間**：category 4 的 215 格空位遠不足以承載一整套翻譯所需的漢字集
   （通常需要數百至近千字才能覆蓋一款 RPG 的完整劇情文字，即使只算「不重複漢字數」）。
   真正可規模化的路徑是啟用 category 5–15（第十一輪已確認这 11 類目前完全沒有接上任何
   字形池，IWRAM `0x030065f0` 查表值恆為 NULL）：每類最多可再放 255 格，11 類合計上限
   2,805 格，數量上足夠。**但**這需要先解出 IWRAM 查表本身是在開機時**從哪裡、被哪段程式碼**
   填入的（第十一輪只確認了查表的執行期內容與位置，沒有追過它的初始化來源）——這是純粹的
   程式碼面問題（不是資料格式問題），需要用第八輪「往上追呼叫鏈」那類技巧，從「IWRAM
   `0x030065f0` 是誰、在開機哪個時間點寫入」入手，找到後才能決定新表要放在 ROM 何處（選項
   (b) 的 `0x660000+` 空白區）、以及如何讓查表在開機後改指向新 base——這是一個**修改程式碼
   邏輯**的補丁，而不是本輪這種純資料插入，複雜度與風險都更高（有讓遊戲在其他情境下崩潰的
   風險，需要更完整的回歸測試）。
2. **字元→字形槽位分配策略**：一旦有新表可用，需要一個系統化流程，掃描全部翻譯批次
   （`translations/*.jsonl` 的 `targets.zh-Hans`／`zh-TW` 文字）收集「實際會用到的相異漢字
   集合」，逐字分配穩定的 `(category, index)`，避免像本輪這樣手動、逐字硬編碼——可參考黃金
   太陽 `build_zh_tw_trial.rb` 的 `new_glyph_ids` 按需分配模式（`new_glyph_ids[character]
   ||= ...`），但目標表結構完全不同（那邊是可變長度的 Huffman 索引擴展表，這邊是固定 stride
   陣列），不能照搬程式碼，只能借用「按需分配、不重複」的思路。
3. **字形美術品質**：本輪的 Unifont＋邊緣偵測二色轉換是「能動、夠讀」但談不上精緻的權宜做法
   ——`vendor/fonts/` 下的 `fusion-pixel-font`／`ark-pixel-font`（本輪未使用、未確認尺寸是否
   剛好 16×16）或找一套專為 16×16 GBA 解析度設計的點陣中文字型，畫面觀感會更接近遊戲原生
   字形的精緻度。
4. **字串長度改變的一般化處理**：本輪能安全地把 10 字元字串縮成 2 字元，是因為手動確認過
   「原字串＋既有零填充」的總預算（34 bytes）夠用；一套真正的建構器需要對**每一個**要翻譯的
   字串都做這種預算檢查（不夠時要嘛截斷、嘛找地方安置更長的字串），而「找地方安置更長字串」
   在這款遊戲上比黃金太陽困難得多——第九輪已確認**不存在指標表**，字串池是逐一走訪、位置
   固定的，任意搬動一個字串的位址在不修改「走訪邏輯」本身的情況下可能行不通（黃金太陽的
   Huffman＋指標表設計天生就支援字串變長搬家，這款遊戲的設計沒有這個彈性）。這是任務要求
   誠實記錄、留給下一輪的最大不確定性，本輪特意選了「縮短」這個安全方向來規避它，不代表
   問題已解決。

### 根因與修正：struct 不是「一個字組」，是 6,176 bytes 的完整前綴

直接 dump 既有 category struct 比對後確認：`+0` 到 `+0x1820` 是一整段真實資料結構
（6,176 bytes，其中 2,494 bytes 非零）——`word[0]=0x1820`（到像素表的偏移）、
`word[1]=0x9820`（像素表結束，即 `0x8000` bytes ＝ **256 個字形槽位**），其後是一長串
每 3 個字組一筆的逐字形中繼資料。**五個既有 category 的這段前綴逐位元組完全相同**
（SHA-256 比對確認）。

第十六輪只寫了 `word[0]`，其餘 6,172 bytes 留在 `0xFF` 填充狀態，渲染器讀到垃圾中繼資料
就把整個 OBJ 圖層搞爛。修正方式因此非常單純：**整段前綴照抄一份既有的**，並把宣告的
256 槽像素區先零填充（與既有表未使用槽位的狀態一致）。`build_cn_glyph_category5_poc.py`
已改為如此，並新增兩道防護——前綴必須五者一致才允許照抄、前綴宣告的槽數必須等於 256，
兩者任一不符即中止，不預設「反正一樣」。

### 環境教訓：mGBA GDB 埠是**編譯期常數**，這是連續多輪「卡住」的真正機制

第十五輪已記錄「`-C ports.qt.gdbPort=<port>` 完全沒有效果，`-g` 恆為 2345」這個現象，
本輪找到確切原因：`src/debugger/debugger.c:60` 把埠**寫死**在原始碼裡
（`GDBStubListen(&debugger->gdb, 2345, ...)`），只有 Qt 前端（`platform/qt/GDBController.cpp`
用 `m_port`）才吃設定值——而 Qt 前端需要顯示 session，這台機器沒有。所以 SDL／headless
路徑上**埠不可能用參數改**，只能改原始碼重編。

這直接解釋了本專案（以及這台機器上其他遊戲的並行工作）反覆出現的「背景跑滿逾時、無進展」：
多個 agent 的 mGBA 全部搶同一個 2345 埠，搶輸的那個 `-g` 靜默失敗（log 只有一行
`Debugger: Couldn't open socket`），但**行程照常全速跑**，客戶端則對著一個沒有服務的埠
等到逾時。本輪實測還觀察到另一個加乘因素：不加 `-l 0` 時 mGBA 預設會逐筆輸出
`GBA BIOS: SWI:` 追蹤，實測**一分鐘寫出 346 MB log**，把模擬器拖慢到連「開機到標題畫面」
這種 20 秒條件都會逾時。

**下一輪照做**：複製一份 mGBA 原始碼、把 `debugger.c:60` 的埠改成自己專用的值、重編
（本輪用 24567，建置於 `/private/tmp/ss1-mgba-24567-src/build/sdl/mgba`；`cmake` 需加
`-DCMAKE_POLICY_VERSION_MINIMUM=3.5`，否則新版 cmake 會拒絕舊的 `cmake_minimum_required`），
啟動一律帶 `-l 0`，並用 `SDL_VIDEODRIVER=dummy` 無顯示執行。**不要 `pkill mgba`**——這台
機器上同時有其他遊戲的 agent 在跑，本輪全程未終止任何非自己啟動的行程。

### 前置問題先解決：新 category 的逐字形中繼資料會不會因索引而異？

新 category 的 struct 前綴是整段照抄 category 0 的，也就是**假名的中繼資料被套用在漢字上**。
在大量配置槽位之前必須先界定這件事——否則可能等幾百個字形都插好才發現排版錯誤。

**實驗**（比空想更快也更硬）：把**同一個字形**同時放進 category 5 的索引 0、127、254
（category 0 在高索引區對應的是半形 Latin／標點，如果中繼資料編碼字寬，高索引槽就會渲染成
窄體），在同一個畫面上並排渲染。結果（`research/session20-metadata-index-probe.png`）：

- 三個 sprite 的 VRAM tile 資料**逐位元組完全相同**
- sprite 幾何（shape／size／調色盤）完全相同
- x 座標 101／114／127，**前進距離一律 13px**

**結論**：中繼資料在整個可定址範圍（0–254）內**與索引無關**，槽位可以自由配置。這是實驗界定，
不是把那 3 個字組解碼出來——它們實際編碼什麼仍然未知，但已經不擋路。

附帶量到一個對排版關鍵的數字：**13px 前進距離正是原文日文用的距離**（基準 ROM 的
「職業を選んでください」10 個字，x 間距逐一量測全部是 13）。

### 通用編碼器 `tools/build_translation_rom.py`

管線：帳本工作記錄 → 相異字元集合 → 槽位配置 → 字形插入 → 就地改寫字串 → 輸出 ROM。

- **預算計算**：每筆記錄的 `string_id` 是 `<pool>:<hex offset>`（條目標頭位置），用既有的
  `extract_string_pool.walk_pool` 走到**下一個**條目標頭，兩者之差就是可安全覆寫的位元組數，
  餘量零填充（第十五輪已驗證這樣不會波及下一個條目）。實測職業選擇畫面那筆算出 34 bytes，
  與第十五／十六輪手工用的數字完全一致。
- **fail-closed**：放不下就跳過並列出原因，絕不溢出。首次實跑 23 筆中 21 筆寫入、2 筆跳過
  （一筆條目 `marker` 宣告 2 行但譯文只有 1 行；一筆需要 16 bytes 但預算 14）。
- **配置**：70 個相異字元全部裝進 category 5，剩 2,735 格。

**實機驗證**：職業選擇畫面「請選擇職業」、顏色選擇畫面「請選擇顏色」（
`research/session20-encoder-jobselect-zh-tw.png`、`session20-encoder-colorselect-zh-tw.png`）。

### 字寬：第一次端到端渲染就抓到的真實缺陷

第一版輸出的中文**每個字與鄰字重疊**（`research/session20-encoder-overlap-15px.png`）。
量測後原因很明確：

| 來源 | 墨水寬度 |
| --- | --- |
| 遊戲自己的漢字（cat1／2／3 各取樣約 60 格） | 最大 **13px**（平均 12.9） |
| 遊戲自己的假名（cat0） | 8–12px |
| GNU Unifont CJK | **15px** |

遊戲的字形是**照著 13px 前進距離設計的**，Unifont 不是。編碼器因此預設把字形以
LANCZOS＋門檻壓縮到 13px 墨水寬（`--ink-width`，0 可停用；用 LANCZOS 而非最近鄰是沿用第十三輪
的既有結論）。壓縮前後對照見 `research/session20-condense-comparison.png`——壓縮後字距恢復
正常且字形仍清晰可辨。**教訓：字形點陣「尺寸吻合」（16×16 對 16×16）不等於「排版吻合」，
真正要對齊的是墨水寬度與前進距離。**

另外修掉一個 POC 從未觸發的 bug：`hex_to_bits` 把字寬寫死成 16，遇到 Unifont 的半形字形
（1 byte/row）就丟 `negative shift count`——POC 只用過全形漢字所以從未遇到。現在寬度由資料
推導，較窄的字形置中補進 16px 格子。修正後重跑 POC，輸出與修正前逐位元組相同。

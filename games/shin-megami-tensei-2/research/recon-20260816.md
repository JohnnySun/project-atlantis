# A5TJ 工程偵察紀錄（2026-08-16）

## 範圍與證據界線

本紀錄只保存可審核的身分、偏移、計數、執行期寄存器與解碼假設；不保存 ROM、完整日文原文、VRAM/OAM 二進位 dump 或渲染圖片。所有 runtime dump 都在本機暫存目錄產生，沒有加入 Git。

## ROM 身分

| 欄位 | 結果 |
| --- | --- |
| header title | `DDS_2` |
| header game code | `A5TJ` |
| maker | `EB` |
| revision | `0` |
| size | `8,388,608` bytes |
| CRC32 | `af40cc99` |
| MD5 | `57af4ca36d8036a483ae0d98c27bf544` |
| SHA-256 | `819a6a19a40bfbe7608f4b813dc18285c827f64e1523561ffe8e10ce8ab5991e` |
| header complement（早期報告） | stored `0x4a`; calculated `0x7c`; mismatch |
| ROM tail | last non-`FF` offset `0x7f2eff`; `53,440` bytes of `FF` tail |

ZIP 成員 CRC32 與 raw ROM CRC32 一致。上列 `0x7c` 是早期
`tools/recon_static.py` 將公式寫成 `0x19 - sum` 所造成的錯誤報告，不是 ROM
內容差異。M1.36 已改用正確的 `-(sum(header[0xa0:0xbd]) + 0x19) mod 256`
公式，並由共用 `scripts/gba-rom-identity.py` 在未使用
`--allow-invalid-header` 下重驗：stored/calculated 都是 `0x4a`，size、game
code、CRC32、SHA-256 也全部 match，exit/status 為 `0`/`pass`。mGBA 的可執行性
仍不取代這個 identity gate。

## 第一輪靜態掃描

`tools/recon_static.py` 對整個 8 MiB 候選執行，結果如下：

- 12 個常見日文 Shift-JIS sentinel 全部為 0 次精確命中。
- 合法 Shift-JIS lead/trail 規則的 6-pair 以上片段有 1,554 段；最長 192 pairs。這是二進位資料的語法假陽性，尚不足以當作文字區。
- GBA 位址樣式候選數量依 4-byte alignment 為 57,726、18,441、13,786、16,980；沒有經執行期引用或字串形狀驗證，不能當作指標表。
- `0x10/0x11/0x20/0x30` 候選壓縮 header 在各 alignment 都很多，符合「magic + 24-bit size」的規則本身噪音過高，不能據此判定文本壓縮。
- 可列印 ASCII runs（最少 8 bytes）有 14,956 段；其中包含地圖／設施等 ASCII 標籤，但尚未證明是本作主文字表。

因此目前沒有把 Shift-JIS、ASCII、GBA 指標或 BIOS 壓縮候選誤認成文本格式。

## 有界 runtime 回合

環境為已準備好的 mGBA 0.10.5 headless GDB session，專用 port `2367`。本回合沒有再編譯或修改 mGBA；emulator binary、ROM 與 dump 均在 repo 外。

### 輸入消費

對 `KEYINPUT` (`0x04000130`) 設定 GDB read watchpoint `Z3,4000130,2`。穩定命中點為 PC `0x080a9a0a`，命中時 LR `0x080a9737`、SP `0x03007e44`；附近 THUMB 指令先由 `0x04000130` 讀 halfword，再更新本作的輸入狀態欄位。GBA active-low 值為：無按鍵 `0x3ff`、A `0x3fe`、Start `0x3f7`。

在 watchpoint stop 後覆寫目的暫存器的值，連續維持 Start 讀值再釋放，成功讓畫面離開開機 logo 狀態。這證明的是「遊戲程式讀取 KEYINPUT 的消費點與按鍵狀態轉換」，不是透過 GDB 直接寫 I/O 快取偽造主機輸入。

### VRAM/OAM 狀態轉換

logo 穩定狀態與 Start 後狀態的非零 byte 統計如下；這些是 memory dump 的統計，不是資源數量：

| 狀態 | VRAM | palette | OAM | I/O |
| --- | ---: | ---: | ---: | ---: |
| logo / idle | 3,192 | 289 | 128 | 897 |
| Start 後 | 4,226 | 61 | 311 | 471 |

Start 後讀到 `DISPCNT=0x7f00`、`BG0CNT=0x8004`、`BG1CNT=0x820d`、`BG2CNT=0x840e`、`BG3CNT=0x4607`。OAM 0–45 為 46 個可合成 sprite，其餘 entries 為 disabled；使用 OBJ VRAM base `0x10000`、4bpp、OAM 實際座標與 1D tile mapping 合成後，得到穩定的文字影像。

### 文字消費結果

從 Start 後的 VRAM、OBJ palette slice 與 OAM dump，以專案既有的通用 `render_oam_composite.py`（只做標準 GBA OAM/tile 解碼）按 OAM 真實排列合成，畫面出現遊戲內三行日文免責文字。這是目前最強的 M1 正面證據：文字已經被遊戲載入到 OBJ tile/palette/OAM 路徑並在實際畫面組合出來。

但這一證據只到「畫面消費者」層級，沒有宣稱已解出文字 source table 或 codepage。另對 OBJ VRAM `0x06010000` 設 `Z2,6010000,4` 做 20 秒 bounded write-watchpoint，stub 接受設定但沒有命中；這表示 DMA 或目前 watchpoint 覆蓋範圍仍未捕捉到搬移 PC，不能把任何猜測的 ROM 偏移／搬移 routine 寫成結論。

## 目前結論與風險

已確認：ROM 身分、可執行性、KEYINPUT 執行期讀取點、Start 狀態轉換、GBA display memory 讀取方式、OBJ/OAM 文字畫面消費結果。

尚未確認：主文本總量、惡魔／技能／道具／劇情資料分區、codepage、字串終止與控制碼、指標／bank、壓縮與解壓縮引用、字寬／換行規則、可逆回插位置。這些缺口必須由本作後續的靜態／runtime 交叉證據填補，不得從其他遊戲格式推定。
